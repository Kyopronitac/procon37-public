# 初期P3の並列探索

## 基準と設計

共通基準はcommit `dcec0d5138d4c555302ec6be508bda7d3c1e488a`、内容ハッシュ `ca0218f665388632f0b365414c6ef80acb6ec7626193190c9c5ce483521c8d7a` です。他の並列候補と保護された対戦相手の実装は参照していません。

制御スレッド1本と常駐探索スレッド14本を使います。各探索は基準版の焼きなまし、経路ビーム、補給計画、翌日比較を独立に実行します。乱数seed、冷却周期数、温度倍率、ビーム途中候補の時間重みを変えて候補の多様性を確保します。全探索の提出候補には同じ得点・燃料の評価式を使用します。

制御側が公開エンジンのGameと実際の採用履歴を保持し、毎日そのコピーと取得済み種類を各探索へ渡します。前回の回答が却下された場合は待機を適用します。半分の探索には前回採用案の経路を初期候補として渡し、残りは各探索の初期候補を保持して実観測で再評価します。グラフとRefCellのキャッシュは各探索の内部だけで扱い、スレッド間には経路列・座標だけを渡します。

採用前に全候補を公開エンジンで検証します。累計種類数を最優先し、その値が同じ候補を探索評価値で比較します。小盤面の翌日比較が有効な場合は基準版の翌日種類数評価を含めます。同じ評価値なら公開エンジンの種類数・日別種類数・玉数、その後に探索番号で決めます。

要求には共通の絶対締切を設け、制御用に10～600msを残します。各探索の内部でも基準版の91%予算を適用します。遅れた回答を別要求へ使わず、期限内の有効候補がなければ待機を返します。110ms以下の要求は制御側で履歴を同期し、探索を起動せず待機します。

## ビルドと起動

候補ディレクトリを作業ディレクトリとして実行します。

```sh
PATH=/home/jikky/.cargo/bin:$PATH cargo build --release -p solver -j 2
PROCON37_P3_WORKERS=14 target/release/solver 0 0 2 0
```

固定設定は探索seed 0、到達性重み0、ビーム時間重み2、翌日アーカイブ重み0、`PROCON37_G007_FUTURE_WEIGHT=0`、`PROCON37_G007_RESERVE_WEIGHT=15`です。探索ごとのbeam係数は指定値に0.5・0.75・1・1.25・1.5・2・3を乗じます。温度倍率は0.6・0.8・1・1.2・1.6・2・3、冷却周期数は6・9・12・16・20・24・32です。14本では7通りを2系列のseedで使います。

`PROCON37_P3_WORKERS`を指定しなければ14本です。指定値は1～14に制限され、例えば999を指定しても探索14本＋制御1本です。スレッド生成箇所は`solver/parallel.rs`の単一ループだけで、探索内に追加スレッドや非同期ランタイムを起動する処理はありません。再選択時は前の探索を終了してから新しい探索を作成します。

親が配置する固定条件はteam 3、VOIDLINUX-3、CPU `4-7,12-15,20-23,28-30` です。開発側ではSSH配置・正式評価を実施していません。

## 軽量検証

```sh
PATH=/home/jikky/.cargo/bin:$PATH cargo test --release -p solver -j 2 -- --nocapture
```

基準由来の回帰7件と、新規JSON Lines統合1件を実行します。統合テストは車種選択と5日分の回答、前回答の却下、1msの追いつき要求、観測車種の変更を含みます。すべての計画を公開エンジンで検証し、`/proc/<pid>/status`を1msごとに読み取って実スレッド数を調べます。環境変数には上限を超える999を指定し、実測最大15本を確認します。これは正式成績の評価ではありません。
