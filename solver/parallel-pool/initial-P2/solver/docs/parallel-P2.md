# 並列 pool 初期 P2

## 基準と構成

固定した単一スレッド基準から作成した独立ビルド版です。

- 基準 commit: `dcec0d5138d4c555302ec6be508bda7d3c1e488a`
- 親が記録した基準内容 hash: `ca0218f665388632f0b365414c6ef80acb6ec7626193190c9c5ce483521c8d7a`
- 配置予定: VOIDLINUX-3、チーム 2
- CPU 集合: `0-3,8-11,16-19,24-26`
- 内部スレッド: 制御 1 ＋探索 14、合計最大 15

探索スレッドを 14 本だけ生成し、各要求をチャネルで配ります。各スレッドの経路グラフ、メモ、`Rc` はスレッド内に留め、共有するのは通常の値データと Mutex で保護した最良解だけです。Tokio や Rayon の実行基盤は起動しません。110ms 以下の要求は制御スレッドが処理します。再度 select を受信した場合は旧ワーカーを終了・join してから次の pool を作ります。

## 探索方針

車種選択はワーカー番号を車両数で割った余りを補給車候補とし、各候補の初日と、予算が許す範囲の翌日・翌々日を試算します。基準の初日評価＋翌日評価×0.5＋翌々日評価×0.25で役割を比較し、最良候補の初期計画も引き継ぎます。

日別探索では同じ採用済み履歴から 14 個の独立探索を開始します。乱数、焼きなまし温度、ビームの時刻減点を変えます。温度倍率は 0.55〜2.6、ビームの倍率は 0〜2.5 です。当日の共通評価で最良となった解を約 16384 反復ごとに交換します。現在の探索経路は直ちに置換せず、基準実装の再始動境界で最良案へ復帰することで、途中の別解探索も継続します。共有時は補給車とノード座標の一致を確認します。

小盤面で基準の翌日種類数確認が動く場合は、最終比較にも翌日の種類数×1000 を含めます。その後、最良候補の履歴・採用計画・翌日初期案を制御側へ戻します。次の観測では実際に提出した計画だけを公開エンジンで再生します。却下時には待機計画を再生し、採用されなかったワーカーの履歴は使いません。

内部探索に渡す締切とは別に、制御側で最大 350ms の返答余裕を取ります。期限までに完成した候補から選び、完成候補がない場合は有効な待機計画を返します。古い要求の結果は ticket で識別して破棄します。ワーカー内の panic は捕捉し、スレッドを増設せず次の要求を処理します。

## ビルドと起動

この候補のルートを cwd とします。

```sh
PATH=/home/jikky/.cargo/bin:$PATH cargo build --release -p solver
./target/release/solver 0 0 2 0
```

引数は基準と同じ順で、探索 seed、到達性重み、ビーム時刻重み、翌日 archive 重みです。正式初期案は引数 `0 0 2 0`、または引数省略で固定します。将来同時探索重みは 0、終端燃料重みは 15 に固定し、基準の開発用環境変数による変更を受けません。CPU 固定とリモート配置は親が担当します。
