# 生成ケースの難易度調整

ここで評価した生成器は **hex-udon-v19**。現行v24では、取り込みを有効にすると4 seedに1件の[練習場の取り込みケース](../../../common/fixtures/arena/README.md)を追加している。幅広い条件20%・制約が厳しい条件80%とし、基準ソルバでの上限未達率は調整用45.6%・確認用48.3%だった（2026-09-21）。

- 入力生成の規則 → [generator.md](generator.md)
- テスタの入口 → [../README.md](../README.md)
- 基準ソルバ → [../../solver/README.md](../../../solver/README.md)

## 目的と評価指標

サンプルに似た特徴と入力の多様性を保ち、基準ソルバで日別種類数の上限に届かない生成ケースを、全体の **45〜55%** 含めることを目指す。公式の生成分布を推定した割合ではない。

| 指標 | 定義 |
| --- | --- |
| 日別種類数の上限 | 問題の系列数 × 日数 |
| 上限未達 | `score.dailyBrands` が上限より小さい。少なくとも1日は全系列を獲得できていない |
| 上限未達率 | 上限未達の生成ケース数 ÷ 評価した生成ケース数 |
| 試合全体の全系列獲得 | `score.uniqueBrands` が系列数と等しい。日別種類数とは分けて確認する |

公式サンプル3件は未達率の集計から除外する。WA・TLE・REを難しいケースとして数えず、まず全件ACを確認する。
目標は3形式を合わせた集合に適用する。各形式や少数のseedで、常に同じ割合になることは要求しない。

## v19の混合率変更

幅広い条件を8%から20%へ増やし、制約が厳しい条件を80%とした。各区分のステップ数・燃料・混雑の抽選範囲と、盤面の生成規則はv17と同じ。
各形式4,096件、計12,288件で、幅広い条件は19.8〜20.6%、最小値始まりは79.6〜80.5%だった。

GUI/CUIの生成結果の一致、自動テスト51件、Clippy、フォーマット検査を確認した。

- 現在の生成規則と日程の分布 → [generator.md](generator.md)

### 難易度の計測結果

2026-09-21、v17と同じseed集合で比較した。調整用・確認用とも、上限未達率は目標の45〜55%に収まった。

| 集合 | v17の上限未達 | v19の上限未達 | 新規実行 / 入力一致による再利用 |
| --- | ---: | ---: | ---: |
| 調整用：seed 3〜59 | 31/57（54.4%） | 26/57（45.6%） | 11 / 46件 |
| 確認用：seed 3000〜3119 | 64/120（53.3%） | 58/120（48.3%） | 12 / 108件 |
| 合計 | 95/177（53.7%） | 84/177（47.5%） | 23 / 154件 |

全177件がACで、試合全体の全系列獲得・フォールバック0件を確認した。
変更された23件はすべて日別種類数の上限に達し、うち11件はv17では未達だった。

| 形式 | 調整用の上限未達 | 確認用の上限未達 |
| --- | ---: | ---: |
| 1回戦 | 11/19（57.9%） | 18/40（45.0%） |
| 準決勝 | 11/19（57.9%） | 23/40（57.5%） |
| 決勝 | 4/19（21.1%） | 17/40（42.5%） |

目標は3形式を合わせた集合に対するもので、形式ごとの差は残る。今回の結果では、幅広い条件20%と全体の難易度目標を両立できた。

### 計測方法と記録

基準ソルバはv17と同じ実行ファイル（下記SHA-256）を使い、`PROCON37_SEED=0`、車種選択・各日の探索とも既定55秒で実行した。他の `PROCON37_` 設定は指定していない。新規23件を最大23ケース並列で実行した。
問題全体がv19の生成結果と一致する154件は、v17の実行記録を再利用した。集計後にも、全177件の保存された問題と現行生成器の出力の一致を確認した。
確認用はv17で使った集合の再評価であり、v19に対する新しいseedでの独立検証ではない。時間制探索のため、再実行時の得点は変動しうる。

記録は `.tester/experiments/generator-v19/` に保存した。

| 記録 | 内容 |
| --- | --- |
| `measurement-plan.json` | 各ケースの問題・入力の変更有無・v17の元記録 |
| `calibration-summary.json` / `validation-summary.json` | 得点・判定・再利用の内訳・元記録 |
| `verified.json` | ソルバのSHA-256、全177件の入力照合、集計、変更23件の得点比較 |
| `measurement-finished.json` | 新規23件の実行終了・探索seed・経過時間 |
| `growth-summary.json` / `profiles.json` | 日程と条件区分の分布 |
| `input-changes.json` / `gui-cui.json` | v17との入力比較・GUI/CUIの一致 |

## v17の結果（混合率変更前）

調整用・確認用とも目標の45〜55%に収まった。確認用は設定を固定した後、未使用のseedで実行した。

| 集合 | AC | 上限未達 | 未達率 |
| --- | ---: | ---: | ---: |
| 調整用：seed 3〜59 | 57/57 | 31/57 | 54.4% |
| 確認用：seed 3000〜3119 | 120/120 | 64/120 | 53.3% |

調整用・確認用は全177件を新規実行し、全件で試合全体の全系列獲得・フォールバック0件を確認した。保存した問題がv17生成器の出力と一致することも全件確認した。

| 形式 | 調整用の上限未達 | 確認用の上限未達 |
| --- | ---: | ---: |

確認用では1回戦・決勝が約半数となり、準決勝は難しめだった。形式別の難易度差は残っている。

## v17でサンプルを基に見直した点

### スポットの道路への出入口

v16はサンプルより、1つのスポットに多くの道路セルが接していた。
道路への隣接率だけでなく、出られる方向の多さも移動しやすさに影響するため、次の2点を変更した。

- 起点のスポットに接する1〜2セルから外へ道路を伸ばし、そのスポットの周囲を回り続けない。
- 道路面積が不足した際の延長は、スポットに接していないセルから始める。

別経路が同じスポットに接することは許す。すべてのスポットは引き続き道路に隣接し、3セル以上の道路に接するスポットも残る。

### 地形比率と外周配置

| 特徴 | サンプルの観測 | v17の変更 |
| --- | --- | --- |
| 地形比率 | 山地は約18〜31%、平地は約22〜35%と盤面ごとに異なる | 平地・山地・池にそれぞれ3〜5の重みを抽選し、比率に幅を持たせる |
| 道路面積 | 約24〜30% | 面積目標の抽選範囲を23〜27%から23〜31%へ広げる |
| 外周のスポット | 最外行・最外列に7〜12個 | 外周を意識した配置を60%から80%に増やす。一様配置20%も残す |

地形の1〜2セル単位の配置と、最終比率15〜38%の検査は維持する。大きな塊を作ることで移動を難しくする変更ではない。
80%はサンプルとの配置比較を基に選んだ抽選確率であり、得点からケースを選別する割合ではない。
日程・燃料・混雑・系列数の抽選規則はv16から変更していない。369組のseed・形式で、問題の差が盤面・スポット・車両配置に限られることを確認した。

### 配置の比較

生成側は各形式のseed 3〜122、120件の平均。各欄は **サンプル / v16 / v17** の順。

| 形式 | スポットに接する道路セル数 | 外周のスポット数 | 最寄りの別系列までの移動時間 |
| --- | --- | --- | --- |
| 1回戦 | 1.63 / 2.05 / 1.51 | 8 / 5.5 / 5.8 | 5.9 / 4.5 / 4.8ステップ |
| 準決勝 | 1.75 / 2.16 / 1.53 | 7 / 7.3 / 7.7 | 6.3 / 5.5 / 5.7ステップ |
| 決勝 | 1.31 / 2.25 / 1.56 | 12 / 8.7 / 10.1 | 8.6 / 6.1 / 6.4ステップ |

移動時間は各スポットから別系列への最短時間を求め、スポットごとに平均した値。混雑前の地形上で計算し、補給や車両間の連携は含めない。
道路の出入口と地形比率の幅はサンプルに近づいたが、特に決勝の移動時間には差が残る。サンプルは各形式1件のため、特定の数値に全ケースを固定せず、分布と得点の両方で確認する。

### 燃料上限の比較

サンプルの燃料上限は、初日ステップ数の1.25倍・1.67倍・1.875倍だった。
これを参考に、厳しい条件の燃料上限をS〜floor(1.25S)からS〜2Sへ広げる候補も比較した。盤面・日程・混雑・系列数は同じに保った。

| 燃料の範囲 | 上限未達 | 未達率 |
| --- | ---: | ---: |
| S〜floor(1.25S)（採用案v17） | 31/57 | 54.4% |
| S〜2S（比較候補v18） | 17/57 | 29.8% |

比較候補は目標の45〜55%を下回ったため、採用しなかった。全57件がACで、入力が完全に一致する7件の記録を再利用し、変更された50件を新規実行した。この比較での幅広い条件は8%で、燃料上限はS〜3Sだった。v19でも区分ごとの燃料上限は同じ。
サンプルの値を参考に分布を見直しつつ、従来の難易度目標と両立する変更を採用する。

### 公式サンプルの再計測

同じ実行ファイル・探索seed・既定55秒で、公式サンプル3件も再実行した。全件AC・試合全体の全系列獲得・フォールバック0件。

| 形式 | 日別種類数 | 上限との差 |
| --- | ---: | ---: |
| 1回戦 | 51/60 | 9 |
| 準決勝 | 85/90 | 5 |
| 決勝 | 120/120 | 0 |

今回の決勝サンプルは上限に達した。以前の移植検証では118/120であり、時間制探索の実行条件によっても変動する。サンプルの得点そのものを固定の生成目標にはせず、盤面の特徴と複数seedの結果を併せて評価する。

## 再検証

基準ソルバをビルドして実行ファイルを固定し、リポジトリのルートから実行する。現在の生成器を使うため、過去の版を再現するコマンドではない。
並列数28は今回の32CPU環境での設定。実行環境に合わせて変更する。

```sh
cargo build --release -p solver -p tester

# 調整用。公式サンプル3件を含む60件を実行する
PROCON37_SEED=0 target/release/tester run 60 --no-build \
  --solver /absolute/path/to/solver --jobs 28 \
  --label calibration --output-dir .tester/evaluation/calibration

# 確認用120件。各ケースの表示出力も別ファイルに保存する
mkdir -p .tester/evaluation/validation
printf '%s\n' {3000..3119} |
  xargs -P 28 -n 1 sh -c '
    PROCON37_SEED=0 target/release/tester run --seed "$1" --no-build \
      --solver /absolute/path/to/solver --jobs 1 --label validation \
      --output-dir .tester/evaluation/validation \
      >".tester/evaluation/validation/seed-$1.log" 2>&1
  ' _
```

未達率は有限個のseedでの実測値であり、常に45〜55%となる保証ではない。
実時間で探索を打ち切るため、同じ探索seedでも実行環境によって得点は変動する。
再調整する場合も、調整用と確認用のseedを分け、得点だけでなく日程・燃料・混雑・配置の分布を確認する。
