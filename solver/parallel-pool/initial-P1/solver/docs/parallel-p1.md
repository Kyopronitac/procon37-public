# 初期P1：独立探索と翌日比較

固定基準 `dcec0d5138d4c555302ec6be508bda7d3c1e488a`、内容ハッシュ `ca0218f665388632f0b365414c6ef80acb6ec7626193190c9c5ce483521c8d7a` から構築した初期候補です。基準の探索・公開判定エンジンだけを利用しています。

## 起動

候補ディレクトリで `PATH=/home/jikky/.cargo/bin:$PATH cargo build --release -p solver` を実行します。起動引数は `solver 1701 0 2 0`。引数なしでも同じ設定です。

`PROCON37_P1_THREADS` は制御を含めた総スレッド数で、既定15、許容値は1〜15に固定しています。上限を超える指定は15へ切り詰めます。P1の配置はVOIDLINUX-1、team1、CPU集合 `4-7,12-15,20-23,28-30` です。CPU固定は親のランチャーで行います。

## 探索

制御1本と最大14本の探索ワーカーを使います。Tokio等の実行ランタイムは起動しません。全ワーカーをjoinしてから次のフェーズを開始し、ワーカー内に並列処理を作りません。経路グラフと可変キャッシュはワーカー固有で、共有可変状態を持ちません。

選択では補給役をワーカー番号順に割り当て、通常の7台以下なら各役を2本以上で試算します。初日の探索に予算の約60%を使い、残りで2日目・3日目を試算します。基準と同じ初日＋翌日×0.5＋翌々日×0.25で選びます。初日の計画をウォームスタートとして保持し、選択段階では実履歴を進めません。

日別探索では14本を独立乱数で走らせます。ビーム途中候補の終了時刻重みを0〜6の範囲で分散させますが、最終評価の重みは共通です。各ワーカーには直前に採用した計画、取得種類、内部Game、引き継ぐ経路をコピーし、却下された計画は全ワーカーで待機へ置き換えます。受信した交通状態を同期します。

翌日があり要求時間が6秒以上なら約75%を当日に配分します。当日評価の最良値から120以内の候補について、残り時間でそれぞれ翌日を並列試算します。当日評価＋翌日の種類数×1000＋翌日新規種類数×100000で比較します。翌日の玉数は候補間比較へ加えません。翌日ルートの補給地点を座標で写し、実要求では再評価します。最終日は公開エンジンで得た種類数・日別種類数・玉数の辞書順で選びます。

基準にある各ワーカー内の候補アーカイブと翌日同時探索は、この並列方式では無効です。1500ms未満の要求、単一スレッド設定、通常と異なる少数車構成は基準の直列処理へ戻します。110ms以下の追いつき処理も維持しています。全フェーズの期限には共通の開始時刻を使い、通常要求から4%以上の余裕を確保します。
