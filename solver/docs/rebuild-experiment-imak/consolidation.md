# 記録用ソースの単一ファイル化と検証

2026-09-24に、[基準実装と4回の再構築](algorithms.md)の記録用ソースと資料を追加した。
既存の `main.rs`・分割された `solver/*.rs`・ルートの `Cargo.toml`・`Cargo.lock` は変更していない。
通常のソルバ開発とビルドは従来の構成を使い、記録用ソースは独立した `solver/docs/rebuild-experiment-imak/` に置く。

## 出典との照合

各版のコミットから `main.rs` と参照先のRustモジュールを読み取り、外部モジュール宣言を同名のインラインモジュールへ展開した。
テストと実験用のRustモジュールも含め、各コミット内の対象Rustファイルが全件収録されていることを確認した。

| 記録 | 出典 | 統合元のRustファイル数 |
| --- | --- | ---: |
| `solver01.rs` | `cc3277f` | 18 |
| `solver02.rs` | `cbeaafd` | 4 |
| `solver03.rs` | `c42d3ec` | 4 |
| `solver04.rs` | `6961e7b` | 6 |
| `solver05.rs` | `6fd85e7` | 7 |

変換はモジュールの展開、出典コメントの追加、Rustfmtによる整形だけである。
再構築3では、単体テストの `include_str!` が同じ公式サンプルを読むよう、移動後の相対パスを `../official/` から `../../../official/` に更新した。
元コミットから再展開・再整形した本文が、保存した単一ファイルの本文と完全一致することを全5版で確認した。
探索処理・定数・乱数処理・テストの書き換えは行っていない。

[source-manifest.json](source-manifest.json) に完全なコミットID、統合元ファイルのSHA-256、記録ソースのSHA-256、構成上の変換内容を保存している。
このハッシュは今回の記録作成時点の内容を表す。

## ビルド・単体テスト

記録用ワークスペースのreleaseビルドと既存テストを実行した。
共通の `tester` 依存を利用し、ルートの開発用 `solver` とは別のバイナリ名でビルドする。

```sh
cargo build --release --offline --manifest-path solver/docs/rebuild-experiment-imak/Cargo.toml --target-dir target --bins
cargo test --release --offline --manifest-path solver/docs/rebuild-experiment-imak/Cargo.toml --target-dir target --bins
cargo fmt --manifest-path solver/docs/rebuild-experiment-imak/Cargo.toml -- --check
```

| 記録 | 成功 | 失敗 | 既定で対象外 |
| --- | ---: | ---: | ---: |
| 基準実装 | 25 | 0 | 3 |
| 再構築1 | 1 | 0 | 0 |
| 再構築2 | 4 | 0 | 0 |
| 再構築3 | 9 | 0 | 0 |
| 再構築4 | 11 | 0 | 1 |
| 合計 | 50 | 0 | 4 |

対象外の4件は原実装で `#[ignore]` が付いた手動速度測定・保存リプレイを用いる実験である。
合流待機、燃料不足、循環する合流順、在庫集計、独立シミュレータとの照合、保存計画の再利用などの通常テストは成功した。

ルート側の通常ビルド、`cargo clippy --offline -p solver --all-targets -- -D warnings`、Rustfmt、`git diff --check` も成功した。

記録用全版に対するClippyの `-D warnings` は、基準実装の `collapsible_if`・`manual_range_contains`・`needless_range_loop` と、基準実装・再構築3の `items_after_test_module` により失敗する。
前者は保存したコードの記法、後者はテストの位置に関する診断で、外部テストモジュールのインライン化でも現れる。
出典との対応を保つため、記録用コードの書き換えや警告抑制は追加していない。
当時の検証資料に書かれたClippy成功記録は当時の分割構成・検査条件によるものである。

## テスタ経由の短縮確認

ディレクトリ集約前の記録ソースで、各実装についてseed 0〜5（公式サンプル3件・生成問題3件）を実行した。
全5版・合計30件がAC。CE・WA・TLE・RE・警告は0件だった。
各リプレイで、車種選択が受理され、提出した全日計画が変更されずに採用されたことも確認した。

- 生成器: `hex-udon-v19`、形式自動、探索seed 0。
- 要求時間: 車種選択・日別回答とも2000 ms。
- 並列数: 各版で6ケース。実装間は順番に実行した。
- `PROCON37_`・`SOLVER_` 系の環境変数は継承しなかった。
- 保存先: `/tmp/procon37-solver-records-vxvmkbdf/`。通常のフルテスト履歴とは分離した。

機械可読な結果、ケース別の得点、実行ファイルのハッシュ、Rustのバージョンは [consolidation-results.json](consolidation-results.json) に保存した。
生のログとリプレイは上記の一時保存先にある。バイナリハッシュもその測定時点のもので、配置変更後の再ビルド成果物のハッシュではない。
`rebuild-experiment-imak/` への集約後は、全ソースのビルドと単体テストを再実行して相対パス・依存関係を確認した。

これは記録ソースの通信・合法性の確認であり、本番制限時間での性能比較ではない。
開発用ソルバの挙動は変更していないため、本番60件の再測定は行わず、過去の正式な性能結果を各版の資料に保存した。
記録用ビルドでは全版に共通のthin LTO・codegen-units=1を使用するため、旧版の当時のビルド条件やバイナリとの同一性は主張しない。
