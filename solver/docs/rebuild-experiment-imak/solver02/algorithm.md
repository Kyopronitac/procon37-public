## 1. 処理の流れ

ソルバは[JSON Lines通信仕様](../../../../tester/solo/docs/protocol.md)に従い、同じプロセスでタイプ選択と各日の計画要求を処理する。
探索は1スレッドで動く。乱数は第1引数のseedから初期化したxorshift64を使い、要求間で状態を引き継ぐ。
実時間で打ち切るため、同じseedでも計算機の負荷によって探索回数や結果は変わる。

```text
タイプ選択要求
  → 車種の組合せごとに全日程をシミュレーション
  → 最良の組合せを回答し、内部シミュレータを初期化

日別計画要求
  → 前日の採否を反映して内部シミュレータを進める
  → 受信した車両状態・日付と照合
  → 当日の道路状態から端点間経路を前計算
  → 焼きなましで当日の候補を探索
  → 有効な場合は最大2日先までシミュレーション
  → 移動と待機の命令列へ変換し、回答
```

日別探索の候補評価では、移動区間と合流を単位に時刻・燃料・訪問店舗を計算する。
全ステップのシミュレーションは候補ごとには行わず、タイプ選択、先読み、前日計画の反映で `tester::engine::Game` を使用する。

## 2. 候補と状態の表現

主な構造体は [solver/mod.rs（単一ファイル内）](../solver02.rs) にある。

| 構造体 | 内容 |
| --- | --- |
| `Candidate` | 車両ごとの停車先列 `routes`、合流一覧 `meetings`、経路モード `modes` |
| `Meeting` | 巡回車 `car`、補給車 `supply`、合流地点 `node`、使用中かを示す `active` |
| `Context` | 問題、当日の観測、前計算経路、車種別の車両一覧、当日のステップ数、試合で獲得済みの系列 |
| `Evaluation` | 評価値、実行可能性、獲得系列、各車の終了時刻・燃料・終着地点・訪問店舗、合流待ち時間 |
| `SearchMemory` | 先読みで得た翌日の候補。次回の日別探索の初期候補に使用 |

### 停車先と合流の識別子

`routes[i]` は車両 `i` の停車先を `u8` で並べた列であり、まだ移動方向の列ではない。

- `0..64`：通常の端点番号。訪問操作で追加するのは店舗の端点。
- `64 + id`：合流番号 `id` への参照。地点は `meetings[id].node` から取得する。

巡回車の列には店舗と合流が混在し、補給車の列には合流だけを置く。
一つの合流は、担当する巡回車と補給車の列に1回ずつ現れる。削除時は両方の参照を消す。

```text
巡回車0: 店舗A → 合流0 → 店舗B
巡回車1: 店舗C → 合流1
補給車2: 合流0 → 合流1

合流0 = { 巡回車0, 補給車2, 地点P }
合流1 = { 巡回車1, 補給車2, 地点Q }
```

実装の固定長領域は車両8台、合流16件。訪問店舗は `u32`、系列は `u64` のビット集合で保持するため、店舗32件、系列番号0〜63を表現できる。
初期候補ではすべての列が空で、経路モードは0。命令列へ変換すると全車両が終日待機する。

## 3. 端点間経路の前計算

[solver/paths.rs（単一ファイル内）](../solver02.rs) の `Paths::new` が当日の経路表を作る。
端点は問題に記載された順の店舗に、まだ端点に含まれない各車の現在地を追加したもの。
同じ現在地は重複追加せず、各車の開始端点を `initial` に保存する。
上記の表現範囲では端点数は最大40となる。

### 地形と道路状態

六方向の隣接マスを辺とするグラフを作り、水域への移動を除く。
時間と燃料は**移動元のマス**で決まるため、逆向きの移動と同じコストになるとは限らない。

| 移動元の地形 | 移動時間 | 巡回車の燃料消費 |
| --- | ---: | ---: |
| 平地（0） | 2 | 1 |
| 道路（1）、道路状態0 | 1 | 2 |
| 道路（1）、道路状態1 | 2 | 2 |
| 道路（1）、道路状態2 | 4 | 2 |
| 山岳（2） | 3 | 2 |
| 水域（3） | 通行不可 | — |

道路状態は当日の観測 `state.traffics` から取得する。各日の探索や予行演習で `Context` を作るたびに前計算し直す。
補給車にも同じ移動時間を使うが、候補評価では補給車の燃料を減らさない。

### 3種類の重み

端点ごとに、次の重みでDijkstra法を3回実行する。`t` は1移動の時間、`f` は燃料消費を表す。

| モード | 辺の重み | 狙い |
| --- | --- | --- |
| 0 | `1024t + f` | 時間を強く優先し、同じ時間なら燃料を抑える |
| 1 | `16t + 8f` | 時間と燃料の両立 |
| 2 | `4t + 8f` | 燃料をより重視 |

各端点対について、選ばれた経路の実際の時間 `time`、燃料 `fuel`、通過店舗のビット集合 `spots`、移動方向列 `moves` を `Edge` に保存する。
`spots` には出発点・到着点の店舗も含める。重み付き距離そのものを回答の所要時間には使わない。
経路表は `(mode * 端点数 + from) * 端点数 + to` で参照でき、探索中に同じ区間の最短経路を計算し直す必要がない。

巡回車ごとに一つのモードを選び、その日の全区間に適用する。補給車は常にモード0を使用する。
探索対象はこの3種類の経路であり、すべての時間・燃料の組合せや区間別のモードは列挙しない。
合流地点も端点に限られ、任意の通行可能マスには置かない。

端点数を `N`、通行グラフの頂点数を `V`、辺数を `E` とすると、最短経路計算は概ね `O(3N(V + E) log V)`。
これに、各端点対の経路復元と移動方向列の保存が加わる。通行可能な端点同士が接続されていることを前提とし、到達不能な場合は実装のassertに達する。

## 4. 合流を含む候補の評価

`Context::evaluate` は各車の時刻を0、燃料を観測値、現在地を開始端点で初期化する。
開始地点が店舗である巡回車は、その店舗を訪問集合に加える。
続いて全車両の列を繰り返し走査し、処理できる停車先から進める。

### 通常の訪問

経路表から現在地と次の店舗を結ぶ `Edge` を取得し、時間を加算する。
巡回車は燃料を減らし、通過店舗を訪問集合に加える。最後に現在地を到着端点へ更新する。
明示的に訪問先へ指定していない店舗も、途中で通過すれば得点の対象になる。

### 合流時刻と待機

合流は、巡回車と補給車の**両方の次の停車先が同じ合流**になった時点で処理する。
片方に未処理の訪問や別の合流があれば、その処理が終わるまで保留する。

1. 両方の車両を合流地点まで進め、到着時刻を計算する。
2. 合流時刻を `max(巡回車の到着時刻, 補給車の到着時刻, 1)` とする。
3. 到着時刻との差を車両ごとの待機時間に保存し、両方の時刻を合流時刻へそろえる。
4. 巡回車の補給直前の燃料不足を記録してから、燃料を上限まで回復する。
5. 両方の列のカーソルを進める。

例えば巡回車が時刻12、補給車が時刻17に着く場合、巡回車だけが5ステップ待ち、両車とも時刻17から次へ進める。
開始地点で直ちに合流する場合でも、最低1ステップを経て補給する。
補給のための固定の追加時間は設けず、早着した側の待機で時刻を合わせる。

一巡してもどの列も進まなければ、合流の順序に循環がある。
例えば同じ2台に対して、巡回車が「合流0→合流1」、補給車が「合流1→合流0」の順を要求する候補は完了できない。
この場合は `feasible = false`、`quality = merit = -1e12` の評価を返す。

### 時間・燃料の制約

全停車先の処理後、次の違反量を計算する。`H` は当日のステップ数、`t_i` は車両 `i` の最終停車先での時刻。

```text
overtime = Σ_全車両 max(t_i - H, 0)

fuel_debt = Σ_全合流 max(-補給直前の巡回車の燃料, 0)
          + Σ_巡回車 max(-日末の燃料, 0)

feasible = (overtime == 0) かつ (fuel_debt == 0)
```

区間の途中では燃料は減るだけなので、補給直前と日末の残量から不足を検出する。
補給前に足りなかった燃料を記録しておくことで、合流時に満タンへ戻した後も違反を見落とさない。

この計算で補給するのは、候補に明示した合流だけである。
実際の命令実行中に補給車と予定外の地点で出会って補給される場合があるが、その効果は探索中の燃料見積もりには含めない。
そのため、実際には実行可能な候補でも燃料不足と評価することがある。整合テストでは実燃料が見積もり以上であることを確認する。

### 獲得系列と玉数

訪問店舗を車両ごとのビット集合で保持するため、同じ巡回車が同じ店舗を何度通っても1回として数える。
店舗 `s` を訪問した巡回車の台数を `v_s`、在庫を `stock_s` とすると、当日の玉数の見積もりは次の通り。

```text
B = Σ_店舗 min(v_s, stock_s)
```

巡回車の訪問集合から系列のビット集合を作り、和集合を当日の獲得系列 `brands` とする。
評価器は各車が在庫を取る順序を再現せず、店舗ごとの訪問台数と在庫から合計を求める。

## 5. 評価関数

日別探索では、制約を満たす候補同士の比較に `quality`、焼きなましの遷移判断に罰則込みの `merit` を使う。

| 記号 | 意味 |
| --- | --- |
| `U` | 当日獲得する系列のうち、試合でまだ獲得していない種類数 |
| `D` | 当日獲得する種類数 |
| `B` | 当日の玉数の見積もり |
| `t_i` | 車両 `i` の最後の停車先までの時間。合流待ちを含み、日末に埋める待機を含まない |
| `f_i` | 巡回車 `i` の日末の燃料見積もり |
| `F` | 巡回車の燃料上限 |

```text
quality = 2000U + 1000D + 4B + future - 0.015 Σ_全車両 t_i
merit   = quality - 180 overtime - 180 fuel_debt
```

未獲得の系列を1種類得ると `U` と `D` の両方が増える。
最後の項は、獲得内容などが同じなら早く巡回を終える候補を優先する。
これらは探索用の重み付き評価であり、試合の種類数・日別種類数・玉数を厳密な辞書順で比較する処理ではない。

### 翌日へ備える項

最終日は `future = 0`。それ以外の日は各巡回車について次を加算する。

```text
near_i  = min_補給車j time(mode=0, 補給車jの終着地点 → 巡回車iの終着地点)
reach_i = min_補給車j fuel(mode=1, 巡回車iの終着地点 → 補給車jの終着地点)

future = Σ_巡回車i [60 max(f_i, 0) / F
                   - 1.2 near_i
                   - 2 max(reach_i - f_i, 0)]
```

燃料を残すこと、補給車が短時間で近づけること、巡回車自身も補給車へ到達できることを評価する。
`near_i` と `reach_i` は向きと経路モードが異なり、最小値を与える補給車が同じである必要はない。
補給車が存在しない場合は両方に1000を使う。
ここで使うのは当日の経路表であり、この項自体は翌日の交通状態をシミュレーションしない。

## 6. 日別の焼きなまし探索

`search_with` は探索中の候補 `current` と、発見済みの実行可能候補のうち最良の `best` を別に保持する。
まず空の候補を評価し、先読みからの初期候補 `warm` があれば、実行可能かつ `quality` が空の候補より高い場合に採用する。

```text
best = 空の候補、または有効で評価の高い warm
current = best

期限まで128反復ずつ実行:
    next = currentを複製して一つの変更操作を適用
    nextを評価
    nextが実行可能でqualityがbestより高ければbestを更新
    meritの差と温度に従ってcurrentをnextへ置き換える
    20,000反復ごとにcurrentをbestへ戻す

bestを返す
```

時間や燃料の制約を破る候補も `current` としては保持できる。
一時的に悪化させた後で訪問や補給の配置を変え、別の実行可能な候補へ移るためである。
回答として返す `best` は `feasible` を満たす候補に限定する。

### 温度と受理条件

反復番号を `k` とすると、温度は次の式で決まる。

```text
phase = (k mod 20000) / 20000
T = 400 × 0.005^phase
Δ = next.merit - current.merit

Δ >= 0 なら受理
Δ < 0 なら確率 exp(Δ / T) で受理
```

温度は約400から約2へ下がり、20,000反復ごとに400へ戻る。同時に探索位置も `best` へ戻す。
コードには40,000反復改善しなかった場合の復帰条件もあるが、20,000反復ごとの復帰でそのカウンタもリセットされる。
期限を確認するのは128反復の区切りなので、探索の終了時刻には最大1バッチ分の遅れが生じうる。

### 変更操作

まず巡回車を一様に選び、次に0〜15の分岐を一様に選ぶ。
表の確率は分岐の選択率であり、対象がない場合や条件を満たさない場合は何も変わらない。

| 分岐 | 選択率 | 変更 |
| --- | ---: | --- |
| 0〜3 | 4/16 | 巡回車の任意位置に店舗を追加 |
| 4〜5 | 2/16 | 巡回車の停車先を削除。選ばれた停車先が合流なら、そのうち1/4の確率で両車から削除 |
| 6 | 1/16 | 巡回車の列の2要素を交換 |
| 7 | 1/16 | 巡回車の列の区間を反転 |
| 8 | 1/16 | 通常の訪問を別の巡回車の任意位置へ移す。同じ車両も選択対象 |
| 9 | 1/16 | 空き番号を使って合流を追加し、両方の列へ挿入 |
| 10〜11 | 2/16 | 選んだ合流の地点を変更 |
| 12 | 1/16 | 選んだ合流を、巡回車または補給車の列の別位置へ移す |
| 13 | 1/16 | 通常の訪問先を別の店舗へ置き換える |
| 14 | 1/16 | 巡回車の経路モードを0〜2から選び直す |
| 15 | 1/16 | 選んだ合流の担当補給車を変更し、その補給車の列へ挿入 |

店舗追加では、同じ地点の停車先がその車両の列にすでにあれば追加しない。
追加と車両間移動には、移動先の列の長さが `店舗数 + 8` 未満という条件も付ける。
ただし置換や車両間移動などで同じ店舗が重複することはあり、得点の重複計上は訪問ビット集合で防ぐ。

合流追加では補給車を一様に選ぶ。挿入位置の直前に停車先があれば2/3の確率でその地点を合流地点とし、それ以外は全端点から選ぶ。
合流地点の変更では、2/3の確率で担当巡回車の列から選んだ停車先の地点、それ以外は全端点を使う。
合流番号を選ぶ変更操作は0〜15から選ぶため、未使用番号を引いた場合は変更しない。
交換・反転などで合流順が循環することがあるが、評価時に実行不可能と判定する。

## 7. タイプ選択

`select` は車種を表すビットマスクを列挙する。各ビットの値が0なら巡回車、1なら補給車を表す。
車両数を `n` とすると、対象は補給車が1台以上、`floor(n / 2)` 台以下の組合せ。
同じ台数でも初期位置ごとに役割が異なるため、台数だけでなく車両への割り当てを探索する。

1. 組合せの順序を乱数でシャッフルする。
2. 初回は各組合せを新しい `Game` で全日程試す。日別探索の予算は1日25ミリ秒。
3. 完走した試行だけを採点し、同じ組合せの試行では最高得点を残す。
4. 2巡目以降は得点上位6組合せに絞り、1日100ミリ秒で全日程の試行を繰り返す。
5. 全試行で最も高い得点を得た組合せを回答する。

```text
selection_score = 1,000,000 × 試合全体の種類数
                +     1,000 × 日別種類数の合計
                +             玉数の合計
```

この比較も重み付きの整数値を用いる。同じ組合せの試行結果を平均せず、最良の試行を採用する。
予行演習の各日には、その日までの移動からシミュレータが作った道路状態と実際の燃料残量を使う。
タイプ選択で作った日別計画は本番の初期候補には渡さず、本番の日別要求で改めて探索する。

25／100ミリ秒は経路前計算後の焼きなましの時間枠で、前計算とシミュレーションの時間は別途かかる。
要求全体の期限を優先し、日別探索の終了期限を全体の期限以下に制限する。期限に達した時点で残りの試行を打ち切るため、初回に全組合せを試せる保証はない。
完走できなかった試行やシミュレーションに失敗した試行は採点しない。

候補となる組合せがない1台構成では巡回車1台を返す。
それ以外で得点の更新がなかった場合の初期回答は、最後の車両だけを補給車とする構成である。

## 8. 実験用の最大2日先読み

`SOLVER_LOOKAHEAD=1` かつ翌日がある場合にだけ動作する。既定では無効。
ここでいう「2日先」は**当日を実行した後、翌日と翌々日まで**を見る意味で、当日を含む2日間ではない。
残り日数が少なければ深さを短くする。

### 当日候補の保存

当日の経路前計算が終わった時点で残り時間を求め、その40%を当日の探索に使う。
この探索では、最良候補の更新時と2,048反復ごと、および終了時に実行可能な候補を保存する。

- 保存数は最大20件。
- 全車両の終着端点配列 `end` と当日の系列集合 `brands` が同じなら、`quality` の高い方だけを残す。
- 新しい組合せを追加した時に `quality` 順に並べ、先頭20件を保持する。同じ組合せの更新はその場で置き換える。

重複判定には燃料・終了時刻・経路そのものを含めない。
終着地点が同じでも系列集合が異なれば別候補として残る一方、両方が同じで燃料配分だけが違う候補は比較して一つにまとめる。

### 先へ進めて比較する手順

残りの時間で保存候補を繰り返し評価する。候補ごとに内部の `Game` を複製し、当日計画を実行してから最大2日先まで日別探索とシミュレーションを行う。
将来の日別探索からさらに先読みを呼ぶことはない。

経路前計算後の当初残り時間を `R`、保存候補数を `P`、将来日数を `depth` とすると、将来1日あたりの探索時間枠は次の通り。

```text
slice = min(500ミリ秒, 0.6R / (max(P, 1) × depth))
```

各探索は要求全体の期限でも制限する。経路前計算とシミュレーションには別途時間を使う。
同じ当日候補でも将来探索の結果は試行ごとに変わり、平均ではなく最高の評価を得た試行を採用する。
途中で期限を迎えて予定の深さまで進めなかった試行や、シミュレーションに失敗した試行は比較から除く。

### 先読みの評価値と翌日への引き継ぎ

`D0, D1, D2` を当日・翌日・翌々日に実際に増えた日別種類数、`B0, B1, B2` を各日の玉数とする。
見ない日の項は省略し、次の評価値で当日の候補を選ぶ。

```text
rank = 1,000,000 × シミュレーション終了時の試合全体の種類数
     +    10,000 × (D0 + 0.9D1 + 0.7D2)
     +        20 × (B0 + 0.2B1 + 0.1B2)
     +       0.1 × (最後に探索した日のquality % 1000)
```

最後の項は `quality` の剰余による小さな補助評価であり、燃料だけを表す値ではない。
将来の獲得がよければ、当日の `quality` が最高ではない候補も選ばれる。
完了した先読み試行がなければ、最初の40%の探索で得た `best` をそのまま使う。

採用した試行の翌日候補を `SearchMemory.warm` に保存し、次の日の探索開始時に現在の観測で再評価する。
実行可能かつ空の候補より評価が高ければ初期候補に使い、その後も通常の探索で改善する。
引き継ぎ候補は使用後にいったん消し、新しい先読み結果が採用された場合に再設定する。
先読みを既定で無効とした短縮比較の結果は[検証記録](validation.md)に記載している。

## 9. 命令列、期限、実状態との照合

### 移動方向列への変換

`Context::materialize` は、停車先の列を実行用の `Plan` に変換する。
各区間の `Edge.moves` を順に連結し、合流地点に着いた直後に、評価時に求めた待機を負数の命令として挿入する。
最後に `H - t_i` ステップの待機を追加して、各車の計画の所要時間をその日のステップ数にそろえる。
移動命令は方向0〜5で、所要時間は地形・道路状態で決まるため、配列の要素数自体がステップ数とは限らない。

### 回答期限

[main.rs（単一ファイル内）](../solver02.rs) は入力行の読み取り後、JSONを解析する前に時刻を記録する。
通常の計算予算は `timeLimitMs - 1500` ミリ秒で、`SOLVER_BUDGET_MS` が指定されていればその値を使う。
正確には、負の差を0に切り上げる減算 `saturating_sub` を使って次のように計算する。

```text
requested = SOLVER_BUDGET_MS または timeLimitMs.saturating_sub(1500)
budget = max(1, min(requested, timeLimitMs.saturating_sub(50)))
deadline = 入力行の読み取り後の時刻 + budget
```

JSON解析や前日の反映、当日の経路前計算もこの予算に含む。
通常の60秒要求では58.5秒を計算に使い、残りを送受信と終了処理の余裕とする。
期限は処理の区切りで確認しており、前計算やシミュレーションの途中に強制割り込みは行わない。

### 前日計画の反映

回答した計画は `pending` として保持し、次の日別要求を受けた時に内部シミュレータへ反映する。
前日が受理されていれば、その計画を実行し、見積もった系列集合を獲得済み集合へ加える。
`previousAccepted = false` の場合は、内部シミュレータでは代わりに終日待機を実行し、前日の予定系列は加えない。

その後、内部シミュレータの車両状態と日付を受信した観測と照合する。
一致しなければ `state differs from local simulation` で終了し、一致した場合だけ探索へ進む。
この照合は車両状態と日付が対象で、観測全体の比較ではない。当日の経路前計算には受信した観測の道路状態を使う。

回答JSONは要求の `requestId` を付けて標準出力へ書き、直ちにflushする。
探索回数・車種・燃料・所要時間などの診断は標準エラーへ出す。
なお、日別ログの `merit` 欄に出力している値は、実装上は罰則を引く前の `quality` である。

## 10. 整合性の検証範囲

[solver/tests.rs（単一ファイル内）](../solver02.rs) の `synchronized_routes_are_accepted_by_independent_simulator` は、生成seed 0〜8の全日程について短時間探索した計画を独立したテスタのシミュレータで実行する。
車種は最後の1台だけを補給車に固定し、各日の探索時間は15ミリ秒としている。

確認するのは、計画を実行できること、日別種類数の増分が評価器と一致すること、各車の終着地点が一致すること、巡回車の実燃料が見積もり以上であること。
このテストだけでタイプ選択や先読みの強さ、すべての問題での最適性を保証するものではない。
本番の制限時間で行った60ケースの合法性・得点比較・実行時間は、別途[検証記録](validation.md)と[集計データ](full-comparison.json)で確認できる。
