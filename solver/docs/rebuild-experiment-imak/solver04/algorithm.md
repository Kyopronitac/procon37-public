## 1. 処理の構成

| 層 | 主な関数・型 | 役割 |
| --- | --- | --- |
| 通信と状態管理 | [main.rs（単一ファイル内）](../solver04.rs) | 要求を受信し、期限を設定。観測と内部状態を照合して計画を送信 |
| 複数日の探索 | [planner.rs（単一ファイル内）](../solver04.rs) の `select`・`plan`・`rollout` | 車種候補の比較、最大3日の先読み、翌日以降の初期解の保存 |
| 1日の探索 | [search.rs（単一ファイル内）](../solver04.rs) の `Context`・`optimize`・`polish` | 訪問列を評価し、焼きなましと改善近傍の列挙で更新 |
| 経路の前計算 | [paths.rs（単一ファイル内）](../solver04.rs) の `Paths` | 移動時間、燃料消費、通過店舗、出力用の方向列を保持 |
| 状態遷移の検証 | テスタの `Game::play_day` | 実際の移動・収集・補給をシミュレーションし、翌日の状態を生成 |

探索器内部の高速評価は、明示した合流による補給だけを使う保守的な判定である。
先読みでは計画を実際にシミュレーションするため、経路途中で偶然起きる補給なども次の日の状態に反映される。
高速評価だけで試合全体の成績を決定しない。

## 2. 1日の探索状態

### 2.1 訪問列 `Tour`

`Tour(Vec<Vec<Stop>>)` は車両番号ごとの訪問列を持つ。
`Stop` の各要素は次の意味を持つ。

| フィールド | 意味 |
| --- | --- |
| `point` | `Paths.points` の地点番号。生成する訪問・合流先は店舗に限定 |
| `mode` | 直前の地点からこの地点までに使う経路モード（0〜3） |
| `meeting` | 0なら通常訪問、1〜23なら合流ID |

通常訪問は巡回車に置く。合流は同じID・同じ地点を巡回車と補給車に1つずつ置く。
経路途中の店舗も収集対象になるため、得点を得るすべての店舗を訪問列に明示する必要はない。
補給車の訪問列は合流だけからなり、収集のための通常訪問は持たない。

挿入操作には列長40の制限があり、合流追加時には対象巡回車の合流数を4未満に制限する。
ただし、後半列の交換などすべての操作で再検査する上限ではないため、列長40・合流4を全候補共通の不変条件として扱わない。

### 2.2 `Context` と `Evaluation`

`Context` はある日の `Game` を参照し、経路、巡回車・補給車の番号、在庫マスク、系列変換表を保持する。
`Evaluation` は各車の経過時間、残燃料、終着地点、訪問店舗集合と、得点・違反量を保持する。
車両別の配列は長さ8、店舗集合は32ビットで表現する。

`Memory.collected` は過去に収集イベントが起きた**店舗**の集合である。
`Context::new` で店舗から系列へ変換し、獲得済み系列集合 `seen` を作る。
系列IDの値をそのままビット位置には使わず、問題内の系列を0からの番号へ圧縮する。

## 3. 経路の前計算

### 3.1 地点と辺の費用

`Paths.points` の先頭は問題中の店舗順で、その後に店舗と重複しない車両の現在位置を追加する。
`starts[a]` が車両 `a` の開始地点番号になる。
各地点から六角格子の隣接6方向へDijkstra法を実行する。

1辺の費用は**移動元セル**で決まり、通行不能地形への移動は生成しない。

| 地形コード | 移動時間 | 巡回車の燃料消費 |
| --- | ---: | ---: |
| 0 | 2 | 1 |
| 1 | 混雑状態0・1・2に対して1・2・4 | 2 |
| 2 | 3 | 2 |
| 3 | 通行不可 | — |

補給車も同じ経路表を参照するが、高速評価では燃料を差し引かない。
道路の混雑状態は、その日の `Game::traffic()` から取得する。
先読みで日を進めるたびに `Context` を作り直し、変化した混雑を経路へ反映する。

### 3.2 4種類の重み付き最短経路

時間を `t`、燃料消費を `f` とし、各辺の費用を `w_t t + w_f f` とする。

| `mode` | `w_t` | `w_f` |
| --- | ---: | ---: |
| 0 | 100 | 1 |
| 1 | 100 | 35 |
| 2 | 100 | 100 |
| 3 | 1 | 100 |

これは加重和による経路選択であり、時間・燃料の厳密な辞書式最小化や全Pareto最適経路の列挙ではない。
同じ距離では前駆頂点を更新しないため、通過店舗数を同距離の優先条件にはしていない。

各区間を `(from * 地点数 + to) * 4 + mode` で参照し、次を保存する。

- `Leg.time`：移動時間の合計。
- `Leg.fuel`：巡回車の燃料消費合計。
- `Leg.spots`：移動先・途中セルにある店舗の集合。区間の出発セルは含めない。
- 別配列の方向列：最終的な `Plan` を生成するときに使う。

開始セルの店舗は `initial_masks` で別に加算する。
同じ地点への長さ0の区間でも、開始位置での収集を落とさない。
頻繁に読む区間評価値と可変長の方向列を分け、探索時の参照量を抑える。

## 4. 合流のスケジューリングと制約

### 4.1 訪問列を進める順序

各車に未処理の先頭位置 `heads[a]` を持つ。
通常訪問なら即座に区間を進め、合流なら同じ合流IDが別の車の先頭に現れるまで待つ。
両者の先頭が揃った時点で、それぞれの合流地点までの移動を評価する。

到着時刻を `t_a, t_b` とした合流時刻は次式になる。

```text
meeting_time = max(t_a, t_b, 1)
```

早く着いた車に待機を挿入し、両車の経過時間をこの値へ揃える。
巡回車はここで燃料上限まで補給される。
`1` は日の開始直後の同一セルで時刻0の給油を仮定しないための下限であり、
すべての合流で到着後に追加1ステップを課す意味ではない。

両車の合流地点が異なる場合や、同じ車種同士の合流は `None` を返して棄却する。
未処理の訪問が残っているのにどの車も進められない場合も棄却する。
これにより、循環する合流順や相手のない合流を探索の受理対象から外す。

### 4.2 違反量

区間を進めるたびに巡回車の残燃料から区間燃料を引く。
負になった分を違反量 `V` に加え、探索状態上の燃料は0へ戻す。
すべての訪問処理後に、各車の時間超過 `max(終了時刻 − 日別ステップ数, 0)` も `V` に加える。

燃料不足・時間超過は罰則付きで探索できるが、合流順を解決できない候補は採点自体をしない。
提出候補は `V = 0` のものだけを保存する。
偶然の補給を燃料不足の解消に使わないため、実際には走れる計画でも高速評価が違反と判定する場合がある。

### 4.3 出力への変換

`materialize` は同じ評価処理に出力用配列を渡し、方向列と待機命令を生成する。
待機は待ち時間の負数で表現し、合流前の調整と日末の余り時間を埋める。
変換時に合流順が解決可能であることと `V = 0` を検査する。

## 5. 得点と翌日の状態価値

以下では `u` をその日に得る未獲得系列数、`d` を当日の系列数、`q` を玉数、`P` を翌日向けの状態評価とする。

### 5.1 訪問台数と在庫の集計

巡回車ごとの店舗集合を作り、同じ車の再訪問は1回として扱う。
`levels[k]` は「少なくとも `k + 1` 台が訪れた店舗」の集合である。
車両の集合 `mask` を追加するときは、大きな `k` から次の更新を行う。

```text
levels[k] |= levels[k - 1] & mask
levels[0] |= mask
```

在庫が `k + 1` 以上ある店舗集合を `stocks[k]` とすると、玉数は次式になる。

```text
q = Σ popcount(levels[k] & stocks[k])  （k = 0..7）
```

これは各店舗の `min(訪問台数, 在庫)` の総和と一致する。
店舗ごとの訪問台数を整数で数え直す処理を、ビット演算に置き換えている。

### 5.2 系列集合

`levels[0]` を8ビットずつの4部分に分け、各部分を256要素の表で系列集合へ変換する。
4つの集合のORを `B` とすると、次のように集計する。

```text
d = popcount(B)
u = popcount(B & ~seen)
```

表は `Context::new` で構築するため、店舗数や系列IDの並びに依存せず使える。

### 5.3 状態価値 `P`

最終日は `P = 0` とする。それ以外の日は、巡回車ごとに次を加算する。

```text
P_a = 5 sqrt(f_a / F) − 0.07 max(n_a − 0.75 f_a, 0)
P   = Σ P_a
```

`f_a` は終着時の残燃料、`F` は燃料上限。
`n_a` は補給車の終着位置から巡回車の終着位置までのモード0経路時間の最小値で、補給車がなければ1000とする。
残燃料の余裕を評価し、残燃料に対して補給車が遠い配置を避けるための近似指標である。
翌日の実際の獲得数を予測した値ではない。

### 5.4 用途ごとに異なる評価式

1日の探索では、先の状態をどの程度重視するかを表す `w` を用いる。
各日の最適化の前に `[0.05, 0.2, 0.7, 1.5, 3.0]` から無作為に選ぶ。

| 用途 | 比較値 |
| --- | --- |
| 焼きなましの受理 | `S = 1000u + 100d + q + wP − λV` |
| 実行可能な最良解の保存 | `R = 10^8 u + 10^5 d + 100q + 100wP` |
| 仕上げ探索 | `Q = R − 0.0001 Σ 終了時刻` |

`Evaluation.reward` 自体には `0.12P` が入るが、受理差分で `(w − 0.12)ΔP` を足すため、最終的な状態価値の係数は `w` になる。
`Evaluation.rank()` の `P` も呼び出し側で補正され、上表の `100wP` になる。
局所探索では将来の燃料と当日の玉数を交換する余地を残し、複数日のシミュレーション結果で候補を選ぶ。

先読みが指定日数を完了した場合の比較値は、実際の累積スコア `U, D, Q_udon` を使う。

```text
Trial.value = 10^9 U + 10^6 D + 100 Q_udon + 最後の日のP
```

係数は対象問題の最大規模（10日・32店舗・8台）を踏まえ、種類数、日別種類数、玉数の優先順位を保つよう設定している。
先読みが最終日に届く場合は末尾の `P` が0になる。

## 6. 焼きなまし探索

### 6.1 初期状態と最良解

空の訪問列を実行可能な最良解の初期値にする。
渡された初期解があれば現在解に使い、合流順が解決不能なら空の訪問列へ戻す。
初期解に燃料・時間の違反があっても現在解として探索できるが、最良解へ保存するには違反0が必要になる。

現在解、変更候補、最良の実行可能解を別々に保持する。
受理されない変更でも、実行可能で保存評価 `R` が改善していれば最良解へ保存する。
候補配列には `clone_from` とバッファの交換を使い、反復ごとの確保を抑える。

### 6.2 近傍の選択

`op = rng.index(100)` によって次の操作を選ぶ。
表の割合は分岐に入る割合で、条件不成立による無変更や棄却も含む。

| `op` | 操作 | 補足 |
| --- | --- | --- |
| 0〜23 | 通常訪問を挿入 | 対象巡回車に同じ明示地点があれば無変更。半分は追加時間が最小の位置、半分はランダム位置 |
| 24〜35 | 訪問を削除 | 合流なら同IDの相手側も削除 |
| 36〜54 | 訪問の位置を移動 | 通常訪問は1/3の分岐で巡回車を再選択。合流は同じ車の中で移動 |
| 55〜63 | 2訪問を交換 | 同一巡回車なら任意の2訪問、異なる巡回車なら通常訪問同士のみ |
| 64〜70 | 区間反転 | 車と2つの位置を選び、区間の訪問順を反転 |
| 71〜78 | 経路モード変更 | 訪問に入る区間のモードを0〜3から再選択 |
| 79〜87 | 合流追加 | 補給車がある場合。未使用IDで巡回車と補給車へ対を挿入 |
| 88〜93 | 合流地点変更 | 補給車がある場合。同IDの双方の地点を変更 |
| 94〜97 | 通常訪問の地点変更 | 半分は同系列の店舗から選び、半分は全店舗から選ぶ |
| 98〜99 | 後半列の交換 | 異なる巡回車の切断位置以降を交換。合流も含む |

補給車がいない場合は79〜93も通常訪問の地点変更へ流れる。
合流追加時の地点は、対象巡回車に既存の訪問があれば半分の確率でその地点から、残りは全店舗から選ぶ。
新しい合流の経路モードは両車とも0にする。
操作後の合流整合性・燃料・時間は必ず評価し直す。

### 6.3 温度と罰則

`optimize` が開始してから残っている予算の88%を焼きなましに割り当て、残りを仕上げに使う。
焼きなまし時間に対する進捗を `p` とし、8周期の再加熱を行う。

```text
cycle = floor(8p)
phase = frac(8p)
T     = peak × 0.008^phase
λ     = 15 + 85 × phase
```

`peak` は通常25、その日の全系列を最良の実行可能解がカバーしていれば8に下げる。
周期が変わったときは現在解を最良の実行可能解へ戻す。
周期の後半ほど温度を下げ、違反に対する罰則を強くする。

受理差分を `Δ = S_next − S_current` とし、`Δ >= 0` なら受理する。
悪化する場合も確率 `exp(Δ / T)` で受理する。
時間、周期、温度、罰則は128反復ごとに更新する。

### 6.4 仕上げ探索

焼きなましで保存した最良の実行可能解を基準に、以下を順に列挙する。

1. 巡回車が未訪問の店舗を、各挿入位置・4モードで追加する。
2. 各訪問の削除、経路モード変更、各区間の反転を試す。合流削除は相手も消す。
3. 通常訪問を、同じ巡回車または別の巡回車の各位置へ移す。
4. 各合流の地点を別の店舗へ変更する。

1巡中の候補は、その巡の開始時に保存した同じ基準解から生成する。
違反0で `Q` が現在の最良値を `1e-7` より大きく上回る候補だけを保存する。
1巡で改善があれば新しい基準解で繰り返し、改善がなければ早期終了する。
期限は外側の反復と64候補ごとの確認で監視する。
仕上げが早く終わった場合は上位の先読み・候補探索へ戻り、残り時間を別候補に使う。

## 7. 独立シミュレーションによる先読み

### 7.1 1候補の作り方

`rollout` は元の `Game` を複製し、指定された日数だけ以下を繰り返す。

1. 回答全体の期限を確認する。
2. この候補の残り時間を、未探索の日へ配分する。
3. 初日は呼び出し元の `Context` を使い、翌日以降は直前のシミュレーション結果から再構築する。
4. 保存済み計画の再現、または `optimize` でその日の訪問列を決める。
5. `materialize` した計画を `Game::play_day` に渡す。
6. 収集イベントから獲得済み店舗集合を更新し、翌日へ進む。

燃料・終着位置・累積スコア・過去の移動による混雑は複製した `Game` が引き継ぐ。
全日数を完了して初めて `Trial.value` を計算する。
途中で回答期限に達した候補は値を負の無限大とし、完了済み候補を置き換えない。
1日も探索できなかった場合にも、空の訪問列を1日分保持して計画を返せるようにする。

### 7.2 日ごとの時間配分

各日の開始時点で、候補の期限までの残り時間を `L`、その後に残る日数を `r` とする。
その日の探索終了目標は `現在時刻 + L × w_day / (r + w_day)` である。

| 呼び出し | 初日の `w_day` | 翌日以降 |
| --- | ---: | ---: |
| 車種選択 | 1 | 1 |
| 日別回答 | 2 | 1 |

これは候補内の時間配分目標であり、回答全体の期限とは別に管理する。
候補の配分時間がなくなっても、回答期限内なら残りの日の計画・シミュレーションを進める場合がある。
回答期限後には新しい日の前計算を開始しない。

### 7.3 保存済みの計画を残す候補

日別回答では、最初の候補だけ `replay_prefix = true` にする。
各日に対応する保存済み訪問列が現在の状態で実行可能なら、そのまま評価・シミュレーションする。
保存がない日や実行不能な日は通常の探索を行う。
判定は日ごとに行うため、ある日を組み直しても、後続の日の保存済み計画は改めて実行可能性を調べる。

通常は前回の先読みから残る2日分を再現し、新しい3日目を追加探索する。
この候補も他の候補と比較することで、再探索によって以前の良い訪問列を失うことを防ぐ。
ただし、最大3日の範囲で比較する仕組みなので、試合全体の得点が毎回単調に改善する保証はない。

## 8. 車種選択と日別回答

### 8.1 車種選択 `select`

車両数を `n`、補給車数を `s` とする。
すべての車種ビットマスクから、`s <= 2`、`s < n`、`s = 0 または s <= floor(n / 2)` の候補を列挙する。
したがって、1台なら巡回車のみを選び、巡回車0台の構成は試さない。

初期試行には経路前計算前の残り時間の半分を配分基準として使う。
各候補の重みは、補給車0台が10、1台が100、2台が25である。
候補ごとの配分は、この重みを全候補の重みの和で割った比率になる。
これは補給車数ごとの総配分ではなく、**各構成1件あたり**の重みである。

各構成を全日程で先読みし、比較値の上位6候補を残す。
その後は最大4秒を目安とする追加試行を回答期限まで繰り返す。
0から数えた反復番号が4の倍数なら首位、それ以外なら保持候補からランダムに選ぶ。
改善した構成の計画を更新し、そのつど候補を並べ直す。

### 8.2 同じ補給車数の構成間での初期解共有

`transfer` は巡回車から補給車へ変わる番号と、逆に変わる番号を対にして訪問列を入れ替える。
各列の車種上の役割と合流IDを維持し、変更後の初期位置から再探索できるようにする。

初期試行は、それまでの同じ補給車数の最良候補を初期解に使う。
追加試行では、偶数回は同じ補給車数の最良候補、奇数回は選択した候補自身の計画を使う。
初期位置が異なるため、移した計画の実行可能性や得点がそのまま保存されるとは限らない。
共有するのは探索の出発点であり、構成の比較値は新しいシミュレーションで求める。

### 8.3 日別回答 `plan`

先読み日数は `min(残り日数, 3)` とする。
当日の `Context` を構築した後、残り時間の1/8を目標に保存済み計画を再現する初期候補を作る。
続いて最大1.8秒を目安とする候補探索を繰り返す。

通常は最良候補の訪問列から探索し、初期候補の後の5回目・10回目・…では保存列を使わずに探索する。
初期候補以外では保存済み計画の固定再現をせず、各日を最適化する。
完了した先読みの比較値が厳密に改善した場合だけ最良候補を置き換える。

回答には最良候補の初日の計画を使い、2日目以降の訪問列を `Memory.tours` に保存する。
車種選択時には選んだ全日程の計画を保存するが、日別回答後に保持するのはその回の先読みの残り部分になる。

## 9. 通信・検証・回答期限

受信した行を読み終えた直後の `Instant` を基準に、JSON解析前から時間を計測する。
制限時間 `timeLimitMs` に対する余裕と探索予算は次の通り。

```text
margin = clamp(timeLimitMs / 100, 10, 600) ms
budget = max(timeLimitMs − margin, 0)
deadline = 受信時刻 + budget
```

通常の日別60秒なら約59.4秒、車種選択90秒なら約89.4秒、120秒なら約119.4秒を探索に使える。
車種選択・日別回答の外側の反復は、期限まで20 ms未満になったら新しい候補を開始しない。
経路前計算やシミュレーションの内部を強制中断する仕組みではなく、探索の節目で期限を確認する。
余裕時間は最終検証・JSON生成・送信と、そのような処理の実行時間差を吸収するために使う。

送信前には `Game` を複製し、当日の計画を `play_day` で再検証する。
次の要求では、前回の計画を内部状態へ反映してから日番号・車両状態・交通量を観測と照合する。
前回の計画が却下された場合は全待機を反映する。
車種選択が却下された場合は、観測された車種で `Game` を作り直し、探索用の保存状態も初期化する。

乱数生成器は [mod.rs（単一ファイル内）](../solver04.rs) の64ビット状態のXorshiftを使う。
初期値は引数のseedに定数を加え、各乱数で左13・右7・左17ビットのXORシフトを行う。
探索を実時間で打ち切るため、同じseedでもCPU負荷によって試行回数と結果が変わる。

## 10. 実装上の高速化と検証範囲

評価関数を探索ループへインライン展開し、計画出力が不要な評価経路を最適化できるようにしている。
x86_64では `Context` 構築時にPOPCNT対応を検出し、`optimize` の入口で対応する探索関数へ一度だけ分岐する。
各候補の評価ごとに命令対応を判定せず、未対応CPU・他アーキテクチャでは同じ処理の汎用版を使う。

9つのテストで、独立シミュレータとの一致、時刻0の合流、循環依存、32店舗・8台の集計、
役割を入れ替えた計画、仕上げの合法性、期限切れ候補、POPCNT版との一致、保存計画の再現を確認する。
性能の優劣は短い単体テストから判断せず、同一問題・本番制限時間のフル60件で比較する。

制限時間・再現性の設定は[settings.md](settings.md)、実測値とテスト手順は[validation.md](validation.md)を参照。
