## 1. 処理の構成

ソルバは、車種選択と各日の計画を同じ日別探索器で解く。
日別探索では軽量な評価を多数回実行し、複数日を進めるときと回答を提出するときには `tester::engine::Game` を使う。

| 実装 | 処理 |
| --- | --- |
| [main.rs（単一ファイル内）](../solver03.rs) | JSON Lines通信、要求ごとの期限、前回回答の反映、観測との照合、最終検証 |
| [Context::new（単一ファイル内）](../solver03.rs) / [Paths::new（単一ファイル内）](../solver03.rs) | 現在状態に対応する端点間の経路を前計算 |
| [Context::evaluate（単一ファイル内）](../solver03.rs) | 訪問列と合流を解き、時間・燃料・得点の概算を計算 |
| [Context::mutate / search（単一ファイル内）](../solver03.rs) | 訪問列や合流を変更し、焼きなまし法で実行可能な良い候補を探す |
| [plan / lookahead（単一ファイル内）](../solver03.rs) | 当日の複数候補を最大2日先まで試し、採用する計画を選ぶ |
| [select / rollout（単一ファイル内）](../solver03.rs) | 車種の組合せごとに全日程を試行する |
| [Game::play_day](../../../../common/src/engine.rs) | ステップ単位の行動検証、獲得、補給、次の日の交通量の反映 |

`search` が返すのは1日分の計画である。先読みと車種選択は、この探索を状態を変えながら繰り返すことで構成している。

## 2. 通信、試合状態、回答期限

### 2.1 試合中に保持する状態

1試合を1プロセスで処理し、標準出力には要求IDを付けた回答だけを出す。
各回答はJSONを1行で書き、改行後に `flush` する。通信形式の詳細は[通信仕様](../../../../tester/solo/docs/protocol.md)を参照。

`main` は次の状態を日をまたいで保持する。

| 変数 | 内容 |
| --- | --- |
| `game` | 車の位置・燃料、完了済み日数、累計得点、獲得済み系列、交通量履歴を持つ `Game` |
| `collected` | 実際に獲得したことのある店舗の集合。店舗番号に対応する `u32` のビット集合 |
| `pending` | 直前に提出した日別計画。次の要求で採否を確認してから `game` に反映する |
| `memory.next` | 次の要求の初期候補として使える計画と、その計画の開始時点の観測 |
| `random` | 車種選択・日別探索・先読みで共有する乱数生成器 |

`select` 要求で車種を決め、その車種を使って `Game` を初期化する。
`plan` 要求では、前回の提出計画があれば先に反映する。`previousAccepted == false` の場合は、提出計画の代わりに当日の全ステップ待機を反映する。
反映後の `Collect` イベントから `collected` を更新する。

その後、予測した車の種別・位置・燃料と道路の混雑状態が、要求中の観測と一致することを `assert_eq!` で確認する。
不整合があれば異常として検出する。日別の探索時間とは別に、計画が使うステップ数には保持中の問題の `day_steps[game.day]` を使う。

### 2.2 要求ごとの探索期限

入力行を読み終えた直後の時刻を `received`、通知された制限時間をミリ秒単位で `L` とすると、期限は次のように決める。

```text
safety = clamp(floor(L / 40), 15, 1000)
usable = max(L - safety, 0)
configured = SOLVER_BUDGET_MS があればその値、なければ usable
budget = min(configured, usable)
deadline = received + budget ミリ秒
```

本番条件では余裕が1000ミリ秒となり、日別計画は約59秒、車種選択は形式に応じて約59・89・119秒を使う。
要求のJSON解析、前回状態の反映、経路の前計算も同じ期限までの時間に含まれる。
探索終了後の最終検証と出力は、通知された制限時間までに残した余裕で行う。

時間管理は実時間による。`search` は256反復ごとに期限を確認し、Dijkstra法やシミュレーションの内部には期限による割込みを設けていない。
したがって `deadline` は探索の停止目標であり、処理をその時刻で強制終了する仕組みではない。
環境変数と実行例は[実行設定](settings.md)を参照。

## 3. 計画と集合の表現

### 3.1 端点番号、店舗番号、系列番号

店舗数を `S`、車両数を `N` とする。`Paths::points` は最初の `S` 要素に問題の店舗位置をそのまま並べ、その後に、まだ含まれていない各車の現在地を追加する。
端点数 `P` は最大 `S + N`。同じ位置にいる車は同じ端点を使う。

- **店舗番号**：`problem.spots` の添字。`0 .. S`。
- **端点番号**：`Paths::points` の添字。店舗番号は同じ番号の端点も表す。
- **系列番号**：問題中の `brand` の値を、登場順に `0` から振り直した内部番号。

現在のテスタが扱う店舗数は最大32なので、店舗集合と系列集合はそれぞれ `u32` に収まる。
`brand_masks[s]` は店舗 `s` の系列に対応する1ビットであり、同じ系列の店舗は同じビットを持つ。
`collected` は店舗のビット集合、`Context::collected_brands` はそこから変換した系列のビット集合で、両者のビット番号は異なる。

### 3.2 訪問列と合流

| 型・フィールド | 意味 |
| --- | --- |
| `Stop.target` | 通常の訪問先の端点番号 |
| `Stop.meeting` | 合流なら `Some(合流ID)`、通常の訪問なら `None` |
| `Stop.mode` | この `Stop` に向かう区間の経路モード。0・1・2のいずれか |
| `Meeting.car / truck` | 合流する巡回車と補給車の番号 |
| `Meeting.point` | 合流地点の端点番号 |
| `Meeting.active` | その合流IDが現在使われているか |
| `Schedule.routes[a]` | 車 `a` の `Stop` の列 |
| `Schedule.meetings` | 最大32件の合流を保持する固定長配列 |

合流用の `Stop` では `Meeting.point` を目的地に使い、`Stop.target` は参照しない。
このため、合流地点の変更は `Meeting.point` の書換えで双方の経路に反映される。
経路モードは双方の `Stop` が独立に持つ。

1つの有効な合流IDは、担当巡回車と担当補給車の経路にそれぞれ1回現れる。
合流を削除するときは、双方の経路からそのIDを除き、配列の要素を非アクティブにする。
追加時は最初の空きIDを再利用する。

合流地点の候補は店舗と各車の現在地に限る。盤面の全セルや自由な時刻を直接列挙する表現ではなく、合流時刻は訪問順と移動時間から決まる。

## 4. 端点間の経路の前計算

### 4.1 移動コスト

六角形グリッドの隣接セルへ向かう有向辺を使う。盤外と池への移動は除外する。
辺の時間 `t(q)` と巡回車の燃料消費 `f(q)` は、移動先ではなく移動元 `q` の地形で決まる。

| 移動元 | `t(q)` | `f(q)` |
| --- | ---: | ---: |
| 平地 | 2 | 1 |
| 山地 | 3 | 2 |
| 道路・順調 | 1 | 2 |
| 道路・混雑 | 2 | 2 |
| 道路・渋滞 | 4 | 2 |

道路状態はその日の観測から読み、日中は固定する。逆向きの移動では移動元が変わるため、2端点間の時間・燃料が対称とは限らない。

### 4.2 3種類の経路モード

各端点を始点として、モードごとにDijkstra法を実行する。
辺の重みは次の整数値で、経路全体の重みの合計を最小化する。

| `mode` | 辺の重み | 狙い |
| --- | --- | --- |
| 0 | `1024 * t(q) + f(q)` | 時間を強く優先し、燃料も重みに含める |
| 1 | `16 * t(q) + 12 * f(q)` | 時間と燃料の折衷 |
| 2 | `1024 * f(q) + t(q)` | 燃料を強く優先し、時間も重みに含める |

これらは重み付き最短路であり、時間と燃料のすべての非劣解を列挙するものではない。
同じ始点・終点でも、モード間で同じ経路になることがある。

`Path` には、復元した経路の所要時間、燃料消費、通過する店舗のビット集合、移動方向の命令列を保存する。
店舗集合には始点と終点も含む。同じ端点間の経路は時間・燃料が0で、移動命令は空になる。

経路表は長さ `3 * P * P` の配列で、添字は `(from * P + to) * 3 + mode`。
探索中の区間評価はこの表を参照するだけで済む。
補給車にも同じ表を使うが、評価時に補給車の燃料は減らさない。通常の追加ではモード0を使い、近傍操作でモードを変えられる。

## 5. 1日分の計画の評価

### 5.1 合流の依存関係を解く

`Context::evaluate` は、車ごとの時刻、燃料、端点、次の訪問位置、合流待ちID、訪問済み店舗集合を持つ。
初期時刻は0、燃料と位置は現在の観測値であり、燃料を日ごとに満タンへ戻すことはしない。

1. 合流待ちでない車について、通常の訪問を順に処理し、合流用の `Stop` に着いたら止める。
2. 区間の時間を加算し、巡回車なら燃料を減らして通過店舗集合を加える。
3. 同じ合流IDで巡回車と補給車の両方が待っていれば、その合流を成立させる。
4. 合流待ちを解除し、後続の訪問を処理する。全訪問を処理するまで繰り返す。

合流する巡回車・補給車の到着時刻を `t_car`、`t_truck` とすると、合流時刻は `max(t_car, t_truck, 1)`。
早着した車は差分だけ待機し、巡回車の燃料を上限 `F` に戻す。

例えば巡回車が時刻8、補給車が時刻11に着く場合、巡回車に3ステップの待機を挿入し、双方が時刻11から後続の区間へ進む。
両者が日の開始時点で同じセルにいても、時刻0には補給が起きないため、双方を時刻1まで待機させる。
途中の同時刻到着では追加の1ステップを必ず課すわけではない。

未処理の訪問が残っているのに1巡で処理が進まない場合は、合流順の循環として実行不可にする。
例えば巡回車の合流順が `A → B`、同じ補給車の合流順が `B → A` なら、お互いの先の合流を待ち続ける。
この場合の評価値は `-1e12`。

### 5.2 時間超過と燃料不足

車 `a` の経路処理終了時刻を `t_a`、当日のステップ数を `T` とすると、時間超過量は全車についての `sum(max(t_a - T, 0))`。

燃料は探索途中に負の値を許す。各巡回車について、合流直前と経路終了時の `max(-fuel, 0)` を合計した値を燃料不足量とする。
合流直前に不足量を加えた後で燃料を `F` に戻すので、後の補給でそれ以前の燃料不足が帳消しになることはない。
明示した合流の間では燃料が減るだけなので、区間末尾の不足量で、その区間で必要だった追加燃料を表せる。

時間超過量と燃料不足量がともに0なら `feasible = true`。
この評価では明示した合流以外の補給を数えない。実際には移動中や末尾の待機中の同居でも補給が起きるため、評価上の残燃料は実際の残燃料以下になる場合がある。
実行可能な計画を保守的に探せる一方、偶然の補給を必要とする計画は探索中に不利に評価される。

### 5.3 種類数と玉数

巡回車 `a` が通る店舗集合を `V_a` とし、店舗 `s` を含む集合の数を `c_s` とする。
当日の玉数は `sum(min(c_s, stocks_s))`、当日の系列集合 `B` は `c_s > 0` の店舗の系列の和集合である。
同じ車が同じ店舗へ何度戻っても、集合には1回だけ数える。

店舗の在庫が正であり、各車が各店舗から受け取れるのは1日1回なので、全車合計の玉数と系列集合には到着順の逐次処理が不要となる。
どの車が在庫を受け取るかという個別のイベントは、シミュレータで確定する。

開始位置が店舗なら、初期の訪問集合にも含める。実際の獲得は時刻1以降に起きるが、店舗は平地で出発に2ステップ必要なので、そこから出発する場合も最初の獲得機会がある。
実行不可の候補も訪問列全体で得点を数えてから罰則を引くため、時間外の訪問も探索途中の概算値には含まれる。

### 5.4 評価式

`popcount` は集合のビット数、`C` は試合全体で獲得済みの系列集合とする。
記号を次のように定義する。

| 記号 | 意味 |
| --- | --- |
| `D = popcount(B)` | 当日の系列数 |
| `U = popcount(B & ~C)` | 当日新たに獲得できる系列数 |
| `Q` | 当日の玉数 |
| `O` | 全車の時間超過量の合計 |
| `H` | 巡回車の燃料不足量の合計 |
| `t_a`、`f_a` | 巡回車 `a` の経路終了時刻と残燃料。末尾を埋める待機は `t_a` に含めない |

基本評価値は次のとおり。

```text
value = 1000 * D + 2000 * U + 5 * Q
        - 110 * O - 120 * H
        - 0.025 * sum(t_a)        # 巡回車だけを合計
```

未獲得の系列は `D` と `U` の両方に寄与するため、新たな1系列の寄与は3000となる。
これは探索用の重み付き評価であり、公式の「種類数 → 日別種類数 → 玉数」の比較手順をそのまま実行する関数ではない。

最終日以外は、巡回車ごとに次の項を加える。

```text
reserve_a = min(max(f_a, 0), floor(F / 2))
nearest_a = 経路終端から最寄り補給車の終端までの mode 0 の所要時間
future_a  = 0.16 * reserve_a
            - 0.6 * max(nearest_a - max(f_a, 0), 0)
            + (終端が店舗なら 1.0、そうでなければ 0.0)
```

補給車がいない場合の `nearest_a` は200とする。
距離には当日の経路表を使う。時間と燃料を組み合わせた経験的な補正であり、翌日の到達可能性を厳密に判定する式ではない。
また、`reserve_a` を燃料上限の半分で打ち切り、満タンに近づけることだけで評価が増え続けるのを避けている。

### 5.5 回答命令への変換

多数回呼ぶ評価では `output = false` とし、移動・待機の命令列を組み立てない。
採用する実行可能な候補だけを `output = true` で再評価し、区間の命令と合流待機を出力する。
最後に各車の残り時間を `-(T - t_a)` の待機命令で埋め、全車がちょうど `T` ステップ使う計画にする。

## 6. 焼きなましによる日別探索

### 6.1 現在解と最良の実行可能解

`search` は探索中の `current` と、見つかった実行可能解のうち評価値が最大の `best` を別に保持する。
初期候補があれば `current` に使い、なければ全車の訪問列が空の計画から始める。
`best` はまず全待機とし、初期候補が実行可能でより良ければ置き換える。

```text
期限まで繰り返す:
    256回:
        next = current のコピー
        next に近傍操作を1回適用
        gain = evaluate(next).value - evaluate(current).value
        gain >= 0、または乱数 < exp(gain / temperature) なら採用
        採用解が実行可能で best より良ければ best を更新
    経過時間から温度を更新
    条件を満たせば current を best に戻す
best を命令列に変換して返す
```

実行可能解の更新では評価値の差が `1e-9` より大きいことを要求する。
探索途中には時間超過・燃料不足のある解を許し、回答には `best` だけを使う。
反復ごとに計画全体を複製して再評価し、差分評価は行っていない。

### 6.2 温度と再開

開始時の温度は400。探索開始からの経過時間を割り当て時間で割った値を `progress` として、256反復ごとに次の温度へ更新する。

```text
cycle = fract(8 * progress)
temperature = 0.5 * 800^(1 - cycle)
```

通常の割り当て時間内では約8回、400付近から0.5付近へ温度を下げて再び上げる。
割り当て時間の分母には最低0.001秒を使う。
また、累計反復数が16384の倍数のとき、約1/3の確率で `current` を `best` に戻す。
温度も乱数状態もその場で初期化し直すわけではない。

### 6.3 近傍操作

まず巡回車を1台選び、`random.index(20)` の値で操作を選ぶ。
表の比率は分岐を選ぶ段階のものであり、操作条件を満たさず何も変えない場合も反復数に含まれる。

| 分岐値 | 選択比率 | 操作 |
| --- | ---: | --- |
| 0〜3 | 20% | ランダムな店舗を訪問列の任意の位置へ追加 |
| 4〜5 | 10% | 選んだ訪問を削除。合流なら双方の列から合流を削除 |
| 6〜7 | 10% | 同じ列の2要素の交換、またはその間の区間反転を半々で選ぶ |
| 8 | 5% | 通常の訪問を取り出し、ランダムな巡回車の列へ挿入。同じ車も選ばれる |
| 9 | 5% | 全車から1台を選び、1区間の経路モードを0〜2のいずれかに変更 |
| 10〜11 | 10% | 巡回車と補給車の両方の列に新しい合流を挿入 |
| 12〜14 | 15% | 有効な合流を選び、地点変更・削除・順序変更のいずれかを行う |
| 15 | 5% | 通常の訪問先を別のランダムな店舗番号で置き換える |
| 16〜17 | 10% | 異なる巡回車の通常訪問を1つずつ交換 |
| 18 | 5% | 同じ列の1要素を抜き、別の位置へ挿入。合流も対象 |
| 19 | 5% | 異なる巡回車の列を途中で切り、後半を交換 |

通常訪問の追加は、選んだ車の列が55要素以上なら行わない。同じ店舗への通常訪問がすでに列にある場合も追加しない。
ただし、通過する店舗や合流地点までは重複判定しない。置換・移動・後半交換により同じ店舗が再び現れることはあり、得点計算時に集合として重複を除く。

合流の追加は、空きIDがあり、選んだ巡回車の列にある合流が5件未満の場合に行う。
合流地点は、列が空でなければ約2/3の確率で挿入位置付近の訪問・合流地点を使い、残りは全端点から選ぶ。
補給車と、その列への挿入位置はランダムに選ぶ。新しい `Stop` の経路モードは0。

分岐12〜14の内訳は、地点変更が1/4、削除が1/4、順序変更が1/2。
順序変更では巡回車側か補給車側のどちらかを選び、その列の中で合流を移す。
後半交換では、移動した合流の `Meeting.car` も更新する。

55要素・5合流という条件はそれぞれ追加操作時の制限であり、移動や後半交換の後にも各車で必ず守られる上限ではない。
全体の合流数32件は固定長配列による上限である。

## 7. 当日の候補生成と最大2日先の比較

### 7.1 先読みを行う条件

`plan` は当日の `Context` を作ってから、残りの時間を `A` とする。
最終日、`SOLVER_HORIZON=0`、または残り時間が100ミリ秒未満の場合は、先読みをせず期限まで1回の `search` を行う。
開始状態が一致する引継ぎ計画があれば、その探索の初期候補に使う。

### 7.2 当日候補と時間配分

先読みを行う場合は、引継ぎ計画が実行可能なら候補に加え、さらに6回の `search` を行う。
1回当たりの時間は `0.38 * A / 6`。偶数回目（0・2・4）はその時点の当日評価値が最大の候補を初期解にし、奇数回目は空の訪問列から始める。
候補の重複除去は行わないため、通常の候補数 `K` は6または7になる。

翌日以降の先読み日数を `h = min(残り日数, 2)` とすると、全候補を最初に試すときの1候補・1日当たりの探索時間は `b = 0.29 * A / (K * h)`。

| 段階 | 時間配分の目安 | 処理 |
| --- | --- | --- |
| 当日候補の生成 | `A` の38% | 6候補を探索 |
| 全候補の先読み | `A` の29% | 各候補を翌日・翌々日まで試行 |
| 上位候補の再評価 | 残り時間 | 上位3候補の先読みを繰り返す |

割合は `search` に渡す時間の配分である。途中の経路前計算やシミュレーションにも時間がかかるため、処理全体が厳密に38%・29%・33%へ分かれるわけではない。
個々の探索期限は要求全体の `deadline` を超えないように切り詰める。

### 7.3 先読み内の状態更新

`lookahead` は現在の `Game` を複製し、まず当日候補の命令列を `play_day` で実行する。
続けて最大2日先まで、次の順で処理する。

1. シミュレーション後の位置・燃料・交通量から、新しい `Context` と経路表を作る。
2. 日別探索を行い、その計画をシミュレータへ渡す。
3. 獲得イベントを店舗集合へ加え、次の日へ進む。

燃料と位置を引き継ぎ、在庫と各車の当日訪問履歴は日ごとにリセットする。
道路状態はシミュレータが保持する過去2日分の道路上の滞在ステップ数から再計算する。
同じ当日得点でも終端位置や補給状態が違えば、後続の日の得点が変わる。

試行が規定の先読み日数まで到達したときだけ、次の累計評価を比較する。

```text
future_score = 1_000_000 * Game.score.unique_brands
               + 1_000 * Game.score.daily_brands
               + Game.score.udon
```

この値には、候補に共通する過去の日の得点も含む。
同じ候補の再試行で得点が下がった場合は、過去に得られた良い評価と対応する翌日計画を保持する。
時間切れなどで先読みを完走できなければ評価を更新しない。当日計画そのものの検証に失敗した場合の評価値は `-1e12`。

### 7.4 上位候補の再試行と引継ぎ

全候補を `future_score` の降順、同点なら当日評価値の降順に並べ、上位3件に絞る。
その3件を順番に再試行する。各日の探索時間は `min(2 * b, 残り時間 / h)` で、残り時間が10ミリ秒未満なら終了する。
この段階では当日の訪問列を固定し、翌日以降の探索に時間を使う。

各候補は翌日の計画だけを `Cached` として保存する。
再試行でも、その候補の翌日計画を初期解として使えるが、翌々日は空の訪問列から探索する。
最後に再び同じ順序で並べ、最良候補の当日計画を返し、対応する翌日計画を `Memory.next` へ移す。

`Cached::matches` が比較するのは日番号、車の配列、道路状態の配列である。車の配列には車種・位置・燃料が含まれる。
一致しない引継ぎ計画は捨てる。端点表を観測から決定的に作るため、これらが一致すると、保存した計画の端点番号を次の `Context` でも使用できる。
締切時刻の `ends_at` は一致条件に含めない。

## 8. 車種選択

### 8.1 組合せの列挙

車ごとのビットを車種（0が巡回車、1が補給車）とし、ビットマスクを昇順に列挙する。
補給車数が1〜2台かつ `floor(N / 2)` 以下の組合せだけを候補にする。
例えば4台なら10通り、5台なら15通り、7台なら28通りとなる。
1台だけの問題では試行をせず巡回車を選ぶ。

### 8.2 全日程の試行と絞込み

車種選択開始時の残り時間を秒単位で `A_select`、組合せ数を `K_select`、試合の日数を `D_match` とする。
初回試行の1日当たりの探索時間は次のとおり。

```text
screening = max(0.48 * A_select / K_select / D_match, 0.001) 秒
```

各組合せについて新しい `Game` を作り、`rollout` で全日程を進める。
各日は空の訪問列から `search` を行い、得られた計画を `play_day` で反映する。
車種選択中の試行は単日探索を順に実行するもので、`plan` の複数候補・2日先読みを日ごとにさらに呼び出す構成ではない。

全日程終了後の評価は、先読みと同じ `1_000_000 * 種類数 + 1_000 * 日別種類数 + 玉数`。
計画が不正、または試合の途中で期限に達した場合は `-1e9` を返す。
各試行の初日計画を、その開始観測とともに保存する。

初回の評価上位3組を残し、順に再試行する。このときの1日当たりの時間は `min(4 * screening, 残り時間 / D_match)`。
2ミリ秒未満しか割り当てられない場合は終了する。
上位3組の顔ぶれは初回の順位で固定し、その中で得られた試行結果を、初回を含む最良結果と比較する。
最良評価が更新されたら車種と初日計画を保存し、決定した初日計画を実際の1日目の初期候補へ引き継ぐ。

## 9. 最終検証と実装上の範囲

提出前には現在の `Game` をもう一度複製し、出力予定の計画を `play_day` に渡す。
この検証は軽量評価とは別の、テスタのステップ単位の処理で行う。不正な計画は `expect` で検出する。
検証用の複製を使うため、本体の `game` はこの時点では進めず、次の要求で採否を確認して反映する。

[tests.rs（単一ファイル内）](../solver03.rs) では、合流待機と補給後の移動、燃料不足、循環する合流順、時刻0の同居、複数の生成盤面・日程を確認している。
軽量評価とシミュレータについて得点・終端位置を照合し、概算残燃料が実際の残燃料を超えていないことも確認する。
本番条件での得点・判定・回答時間は[検証記録](validation.md)を参照。

探索は単一スレッドで、初日から最終日まで同じ乱数生成器を使う。
乱数は64ビット整数に対する左13・右7・左17ビットのxor-shiftで更新し、初期状態は入力seedに `0x9e3779b97f4a7c15` を加えた値（64ビットで折り返す）である。
同じseedでもCPU負荷により期限内の反復回数が変わるため、結果の完全な一致を保証する実行方式ではない。

計算量の中心は、経路表の作成と多数回の計画評価になる。
セル数を `V`、通行可能な有向辺数を `E` とすると、経路表作成では `3P` 回のDijkstra法を実行し、探索部分の目安は `O(3P(V + E) log V)`。
さらに全端点対の経路復元を行い、時間・燃料・店舗集合に加えて `3P²` 本分の命令列を保持する。
計画評価は合流の依存関係が解けるまで列を走査し、全セル・全ステップのシミュレーションは反復ごとには行わない。

探索範囲は3種類の経路、店舗と現在地での合流、最大32合流、最大2日先の候補比較に限定される。
先読みは期間内で得られた試行結果を比較する方法であり、最終日までの大域的な最適解や、すべての実行可能経路を調べ切ったことを保証するものではない。
