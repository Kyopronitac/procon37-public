## 1. 探索全体の流れ

探索は、車種や複数日の計画を比較する外側の処理と、1日分の訪問・補給を改善する内側の処理からなる。
内側では経路を前計算した高速な評価器を使い、外側では `Game::play_day` で行動列を実行して得点と翌日の状態を求める。

```text
車種選択: 補給車の配置候補 → 全日程の計画を生成・実行 → 有望な配置を再探索
日別回答: 保存計画を再評価 → 最大3日分の計画を繰り返し生成・実行
                               ↓ 各日の計画生成
            当日の経路を前計算 → 焼きなまし → 近傍の列挙 → 行動列に変換
                               ↓
            複数日分の実得点で比較 → 当日分を最終検証して送信
```

`daySteps` はゲーム内の1日の長さ、`timeLimitMs` は回答までの実時間の制限を表す。
以下では「時刻」「移動時間」をゲーム内のステップ数、「探索時間」「期限」を実時間として扱う。

| 実装 | 主な入口・責務 |
| --- | --- |
| [main.rs（単一ファイル内）](../solver05.rs) | 要求の受信、前日の確定、観測との照合、最終検証、回答 |
| [network.rs（単一ファイル内）](../solver05.rs) | `Network::new`：端点と経路の前計算 |
| [routing.rs（単一ファイル内）](../solver05.rs) | `Router::evaluate`、`improve_inner`、`polish`、`plan`：1日の探索 |
| [strategy.rs（単一ファイル内）](../solver05.rs) | `select`、`plan`、`rollout`：車種選択と複数日の比較 |
| [random.rs（単一ファイル内）](../solver05.rs) | `Random`：探索用の乱数列 |

## 2. 移動経路の前計算

### 2.1 端点と格納形式

`Network::positions` は端点番号からセル番号への対応を保持する。セル番号は `y * width + x`。
先頭に入力順の全店舗、その後にまだ登録されていない車両の現在位置、最後に合流用の追加地点を並べる。
店舗番号と端点番号が一致するため、通常の訪問先は店舗番号をそのまま利用できる。

各端点間について4種類の経路を作り、次の情報を保存する。

| データ | 内容 |
| --- | --- |
| `Leg::time` | 経路の移動時間の合計 |
| `Leg::fuel` | 巡回車が消費する燃料の合計 |
| `Leg::visits` | 出発点・到着点・途中で通る店舗の集合（`u32`） |
| `directions` | 出力に使う移動方向 `0..5` の列 |
| `starts` | 各車の開始端点番号 |
| `spot_at` | マップの各セルに対応する店舗のビット |

経路表の添字は `(from * 端点数 + to) * 4 + mode`。
最大32店舗・8車両・16追加地点なら端点数は最大56で、経路表は最大 `56 * 56 * 4` 件になる。

### 2.2 時間と燃料を重み付けしたDijkstra法

移動コストは、移動先ではなく**移動元のセル**に応じて決まる。

| 地形番号 | 1回の移動時間 | 巡回車の消費燃料 |
| --- | --- | --- |
| 0 | 2 | 1 |
| 1 | 混雑状態0・1・2に応じて1・2・4 | 2 |
| 2 | 3 | 2 |
| 3 | 進入不可 | — |

各出発端点から、次の辺コストを用いてモードごとにDijkstra法を実行する。

```text
cost(u → v) = tw * time[u] + fw * fuel[u]
```

| モード | `tw` | `fw` | 狙い |
| --- | ---: | ---: | --- |
| 0 | 100 | 1 | 時間を重視する |
| 1 | 100 | 30 | 燃料も考慮して時間を抑える |
| 2 | 100 | 100 | 時間と燃料を同じ重みで扱う |
| 3 | 1 | 100 | 燃料を重視する |

同じ重み付き距離なら親を更新せず、各モードで1本の経路を保存する。
4モードは時間と燃料の異なる折り合いを試すための代表経路であり、あらゆる経路を列挙するものではない。
移動元のコストを使うため、逆方向の経路の時間や燃料が同じとは限らない。
交通量はシミュレーション中の日の状態から取得し、`Router` の生成時に経路表を作り直す。

### 2.3 店舗以外の合流候補

`add_meeting_positions` は店舗間でよく通るセルを候補に加える。

1. 各店舗から `100 * time + fuel` のコストで最短経路木を作る。
2. 他の各店舗までの経路をたどり、通過セルに票を加える。各店舗対について、選ばれた1本の経路を数える。
3. 店舗・車両位置と、その隣接セルを候補から除外する。
4. 残った正の得票があるセルのうち最多票の地点を追加し、その地点から2辺以内のセルを除外する。
5. 最大16地点まで繰り返す。候補が尽きたら終了する。

除外範囲は、通行可能な六角格子上のBFSで求める。時間・燃料の重みは使わない。
追加地点は道路の地形に限定せず、経路上の通行可能なセルから選ぶ。
これにより、店舗へ迂回せずに途中で補給する計画を表現できる。

## 3. 訪問列と合流の表現

`Itinerary` は各車の `Route` を持つ。`Route` は最大48件の `Stop` を固定長配列に格納し、有効な件数を別に保持する。
候補の複製や経路後半の交換で、車両ごとに一時的な可変長配列を確保する処理を避けている。

| `Stop` のフィールド | 意味 |
| --- | --- |
| `node: u8` | 到着する端点番号 |
| `mode: u8` | 直前の端点から、この端点へ入る経路のモード |
| `meeting: u8` | 合流ID。通常訪問は255、合流は0〜31 |

合流は、巡回車と補給車の双方に同じID・同じ端点の `Stop` を置くことで表す。
1日の合流IDは最大32個。経路モードは両車で異なってよい。
車種は巡回車が `kind == 0`、補給車が `kind == 1`。
通常訪問の追加先は店舗から、合流先は現在位置や追加地点を含む全端点から選ぶ。

## 4. 1日分の高速評価

### 4.1 合流時刻と燃料

`Router::evaluate` は各車について、現在の端点・時刻・燃料・訪問店舗集合・次の `Stop` の位置を管理する。
巡回車の訪問集合には開始位置の店舗も含める。補給車は燃料を消費せず、店舗の獲得にも参加しない。

車両を順に見て、合流待ちでなければ次の合流または経路末尾まで進める。
通常の移動では前計算済みの時間・燃料を加算し、巡回車の訪問集合へ `Leg::visits` をORする。
合流地点では次のように処理する。

1. 先に評価された車両を、その合流IDの待機車両として登録する。
2. 相手が到着したら、異なる車両・異なる車種・同じ端点で待っていることを確認する。
3. 両車の時刻を `max(巡回車の到着時刻, 補給車の到着時刻, 1)` にそろえる。
4. 巡回車の燃料を `fuelLimits` に戻し、双方の合流を完了させる。

たとえば巡回車が時刻7、補給車が時刻10に到着する合流では、巡回車に3ステップの待機を入れる。
双方が開始位置で合流する場合も時刻1まで待つ。これにより、ゲーム内の補給判定が行われるステップを確保する。

合流が未処理なのに、どの車も先へ進めなくなった候補は棄却する。
たとえば巡回車の合流順が `A → B`、補給車が `B → A` なら相互に待ち続ける。
相手の欠けた合流や不正な組み合わせも棄却し、評価値を `-1e15`、違反量を `100000` とする。

燃料不足と日内の時間超過は、構造が成立する候補では違反量 `V` として数える。

```text
燃料 f の巡回車が消費量 c の区間へ進むとき:
    V += max(0, c - f) - max(0, -f)
    f -= c
全経路を処理した後:
    V += Σ車両 max(0, 最終Stopの完了時刻 - 当日のdaySteps)
```

この差分式は、既に不足している燃料を重複して数えないためのもの。
たとえば残量5から8を消費すると違反量は3、続けて2を消費すると追加の違反量は2となる。
後で補給しても、それ以前に生じた違反量は消さない。

偶然のすれ違いや待機中に生じる予定外の補給は、この評価器では見込まない。
行動列を実行する `Game::play_day` はそれらも反映し、実際の残燃料を次の日へ渡す。
このため、探索中の燃料評価は予定した合流だけを使う保守的な評価になる。

### 4.2 店舗在庫とブランドの集計

巡回車 `a` の訪問店舗集合を `M[a]` とする。同じ車が同じ店舗を何回通っても1ビットとして扱う。
各店舗に何台の巡回車が来るかを、次の8個のビット集合へ変換する。

```text
L[0] = 1台以上が訪れる店舗
L[1] = 2台以上が訪れる店舗
...
L[7] = 8台以上が訪れる店舗

巡回車を i = 0, 1, ... の順に追加:
    j = i, i-1, ..., 1 の順に L[j] |= L[j-1] & M[a]
    L[0] |= M[a]
```

`stock_masks[k]` を在庫が `k + 1` 以上の店舗集合として前計算しておくと、玉数は次式で求められる。

```text
udon = Σ(k=0..7) popcount(L[k] & stock_masks[k])
```

たとえば在庫2の店舗へ3台が訪れても、加点されるのは `L[0]` と `L[1]` の2玉分だけになる。
訪問時刻の順序を再現せず、獲得玉数の合計を集計できる。

ブランドIDは入力の店舗で最初に現れる順に0から圧縮する。
店舗集合を8ビットずつ4区画に分け、各区画の256通りをブランド集合へ変換する表 `brands[4][256]` を作る。
4回の表引きとORで、全訪問店舗 `L[0]` から当日のブランド集合 `B` を求める。
既獲得のブランド集合を `known` とすると、当日の種類数は `popcount(B)`、初獲得の種類数は `popcount(B & !known)`。

### 4.3 探索中の評価式

構造が成立する候補の評価値 `E` は次の合計。制約違反 `V` の罰則は焼きなましの受理判定時に別途加える。

```text
E = 100 * 当日の種類数 + 1000 * 初獲得の種類数 + 玉数
    + 訪問先の一時的報酬 + 残燃料の報酬 - 補給車との距離罰則
    + 翌日の目的地への誘導
    - 0.005 * Σ車両 最終Stopの完了時刻 - 0.00001 * Stop総数
```

`最終Stopの完了時刻` は各車の最後の予定が終わる時刻で、合流待ちを含む。
出力時に付け足す終業までの待機は含めない。そのため、同程度の得点なら早く予定を終える候補を優先できる。

翌日がある場合、燃料重みを `w`、翌日の歩数を `N`、巡回車の終了燃料を `f` として次の項を加える。

| 状況 | 巡回車1台あたりの評価 |
| --- | --- |
| 補給車なし | `+ w * max(f, 0)` |
| 補給車あり | `+ w * clamp(f, 0, N)` |
| 補給車ありの距離罰則 | `- w * 0.4 * d * clamp(N - f, 0, N) / max(N, 1)` |

`d` は巡回車の終点から最寄りの補給車の終点までの、モード0の移動時間。
燃料が翌日の歩数以上なら距離罰則は0となる。
また、翌日の保存経路に最初の目的地があり、そのセルが当日の端点表にも存在すれば、各車の終点からのモード0の移動時間に `-guidance` を掛けて加える。
最終日は残燃料・補給車との距離・翌日目的地の3項をすべて省く。

訪問先の一時的報酬は、巡回車と店舗の組ごとに `(-perturbation, +perturbation)` から乱数で決める。
その車の訪問集合に含まれる店舗の報酬を加算し、同じ車の再訪は重複計上しない。
在庫の配分とは独立した探索用の誘導で、複数日の最終比較には使わない。

## 5. 焼きなましと仕上げの局所探索

### 5.1 初期解と保持する解

`improve_inner` は現在解 `current` と、実行可能な最良解 `best` を別に持つ。
初期解が実行可能なら `best` に採用し、そうでなければ全車の空経路を `best` にする。
`current` には制約違反がある初期解も使えるため、保存経路の移植で生じた燃料不足や時間超過を修復しながら探索できる。

最良解の更新条件は `V == 0` かつ `E > best.E + 1e-8`。
更新した最良解は `compact` で重複を取り除いて再評価する。

### 5.2 ランダム近傍

`mutate` は0〜99の乱数から操作を選ぶ。次の比率は操作を**試す確率**であり、経路が空、容量不足、補給車なしなどの場合は変更せずに終わる。

| 比率 | 操作 | 対象・内容 |
| ---: | --- | --- |
| 24% | 訪問追加 | 巡回車に店舗を挿入する |
| 11% | 訪問削除・合流解除 | 通常訪問を削除。合流なら半々でペア全体の削除か解除 |
| 14% | 訪問移動 | 巡回車内または巡回車間で `Stop` を移す |
| 9% | 訪問交換 | 巡回車の2個の `Stop` を交換する |
| 8% | 区間反転 | 巡回車の訪問列の連続区間を反転する |
| 5% | 後半交換 | 異なる巡回車の経路を途中で切り、後半を交換する |
| 5% | モード変更 | 全車から選び、その `Stop` へ入る経路モードを変える |
| 4% | 場所変更 | 通常訪問なら店舗へ、合流ならペア双方を同じ端点へ変える |
| 13% | 合流追加 | 巡回車と補給車に未使用IDの合流を挿入する |
| 4% | 車内での順序変更 | 全車から選び、1個の `Stop` を同じ車の別位置へ移す |
| 3% | 合流削除 | 全車から選んだ `Stop` が合流ならペア全体を削除する |

訪問追加では3/4の確率でその巡回車が未訪問の店舗、残りで全店舗から選ぶ。
経路モードは4種類から選び、挿入位置は1/3でランダム、2/3で移動時間の増加が最小の場所とする。
この挿入位置の評価では合流待ちの変化を省略し、挿入後の全体評価で確認する。

合流追加では、巡回車側の挿入位置をランダムに選ぶ。
合流地点は2/3で直前の端点（先頭なら開始位置）、1/3で全端点から選ぶ。
補給車側の挿入位置は1/3でランダム、2/3でモード0の迂回時間が最小の場所とする。
巡回車の流れに補給車を合わせる候補を多く試す構成になっている。

`unpair_meeting` による合流解除では、巡回車側を通常訪問に変え、補給車側だけを削除する。
店舗への訪問やそこへ至る経路を残しつつ、補給への依存を外せる。
移動・交換・反転は合流順も変え得るため、操作後に循環などを全体評価で検出する。

### 5.3 温度と制約違反の受理

初期解の評価後から期限までの探索時間の90%を焼きなましに割り当てる。
その区間の経過割合を `p`、8周期のうち現在の周期内の経過割合を `c = fract(8p)` とする。

```text
温度 T       = 4 * 0.008^c * (1 - 0.65p)
違反の重み λ = 4 + 24c
Δ            = E(candidate) - E(current) - λ * (V(candidate) - V(current))

Δ >= 0 なら受理
それ以外は確率 exp(Δ / T) で受理
```

周期が切り替わるたびに `current` を実行可能な `best` へ戻す。
周期の始めは違反の罰則を弱めて温度を上げ、周期の終わりにかけて実行可能な改善へ絞る。
全体の後半ほど温度の上限も低くする。時計・温度・周期の更新は512試行ごとに行う。

```text
best = 実行可能な初期解、なければ空経路
current = 初期解、なければbest
焼きなまし期限まで:
    周期が変わったら current = best
    candidate = currentを複製してランダム近傍を適用
    candidateを評価し、実行可能な最良解を更新
    Δと温度に従ってcurrentを更新
best = 残り時間で近傍を列挙して改善
bestを圧縮して返す
```

### 5.4 残り時間での近傍列挙

`polish` は焼きなまし後の残り時間を使う。1巡の開始時の解を固定し、次の単一操作から改善量が最大の実行可能な候補を残す。

- 通常訪問・合流ペアの削除、巡回車の訪問を残す合流解除。
- 各 `Stop` の経路モード変更、訪問先または合流地点の変更。
- 通常訪問の巡回車内・巡回車間の移動。
- 未訪問店舗の全挿入位置・全モードでの追加、および巡回車の区間反転。

改善があれば、その解を基準に次の1巡を行う。改善がないか、期限に達したら終了する。
列挙中の期限確認は128候補ごとに行う。合流追加や後半交換など、ランダム探索の全操作を列挙するわけではない。

`compact` は移動を伴わない通常訪問を削除する。
同じ端点の通常訪問の直後に合流がある場合は、通常訪問の進入モードを合流へ移して1件にまとめる。
合流そのものを失わず、出力する行動列を保ったまま経路の枠を空ける。

## 6. 複数日の生成・再利用・比較

### 6.1 保存する情報と経路の移植

`SavedDay` は探索上の訪問列 `route`、当時の端点表 `positions`、実行用の行動列 `plan` を保存する。
`Memory` は先読みした日程の `days` と、実際に獲得したブランド集合 `known` を持つ。

日付や開始位置が変わると端点番号も変わるため、`transplant` は保存時の端点をセル番号に戻してから新しい端点表で探す。
同じセルが端点にない場合は、座標上の `|Δx| + |Δy|` が最小の店舗で代用する。
この代用距離は六角格子の最短移動時間ではない。移植では経路モードと合流IDを保ち、実行可能性は再評価する。

当日の保存経路がない場合は、今回の先読みで直前に生成した日の経路を移植し、各車の訪問順を逆にして初期解に使う。
それもなければ空経路から始める。

### 6.2 `rollout` による先読み

`rollout` は現在の `Game` を複製し、指定した日数 `H` だけ次を繰り返す。

1. 保存計画をそのまま再生する範囲 `replay_prefix` 内なら、保存済みの行動列を変更せずに実行する。
2. それ以外では、その日の状態で `Router` を生成し、訪問報酬と翌日目的地への誘導を設定する。
3. 保存経路または前日の逆順経路を初期解として、その日を探索する。
4. 訪問列を行動列に変換し、`Game::play_day` で実行する。
5. `Collect` イベントから獲得ブランドを更新し、実際の位置・燃料・交通量で次の日へ進む。

先読み内の日番号を `j = 0..H-1`、指定された基準探索時間を `τ` とすると、日ごとの要求時間は先頭日が `τ`、それ以降が `0.6τ`。
実際の割当は `min(要求時間, 期限までの残時間 / (H - j))` とする。
経路の前計算後に残時間を測るため、前計算の費用も要求全体の期限に含まれる。
各日の開始時に残り2 ms以下、または前計算後に残り1 ms未満なら、その先読みを中止する。
行動列が不正な場合も中止し、指定日数を完了しない候補は比較に入れない。

### 6.3 保存計画をそのまま残す候補

日別回答の先読み日数は `H = min(3, 残り日数)`。
最初に `preserved` で保存済みの `H` 日分をそのまま実行し、比較の基準として残す。
保存日数が不足する場合は、保存部分だけを変更せず再生し、不足分を `rollout` で追加する。
たとえば残っている保存計画が2日分なら、まずその2日を再生してから3日目を探索する。

以後の改善試行では保存経路を初期解にし、`replay_prefix = 0` として先読み全体を再探索する。
良い候補が得られたら、その全日程を次の試行の初期解に使う。
回答するのは最良候補の先頭1日分で、残りも `Memory` に保持する。
完成した候補が一つもなければ保存計画を消し、全車待機の合法な計画を返す。

### 6.4 実得点による最終比較

先読みの比較には、独立シミュレーション後の累積得点を使う。

```text
Q = 10,000,000 * 種類数 + 10,000 * 日別種類数 + 玉数
```

種類数・日別種類数を優先する大きな重みを付け、探索中の訪問報酬・終点への誘導・時間罰則は含めない。
先読み終了後にも日程が残る場合だけ、各巡回車について次の燃料評価を加える。

```text
Q += 0.06 * min(実際の残燃料, 上限)
上限 = 次の未実行日のdaySteps * (補給車がいるなら1、いないなら2)
```

この係数は、内側の探索で使った燃料重みにかかわらず常に0.06。
残燃料の項によって、先読みの玉数と以後の余力の間には小さな交換を許す。
全日程を実行した候補には燃料評価を付けない。

## 7. 車種選択と探索時間の配分

### 7.1 車種候補の生成と絞り込み

`select` は全車巡回を最初の候補とし、車両数が2台以上なら補給車1台の全配置、4台以上なら補給車2台の全配置を加える。
車両数 `n >= 4` なら候補数は `K = 1 + n + n(n-1)/2`。
各配置を問題の全日程 `D` 日にわたって先読みする。

選択処理の開始時点の残り探索時間を `B` 秒とすると、初期比較の基準時間は次式。

```text
τ₀ = max(0.001, 0.23 * B / (K * D)) 秒
```

`0.23` は1日あたりの要求時間を決める配分係数で、前計算やシミュレーションを含む総所要時間を23%に固定するものではない。
初期比較の燃料重みは0.06で、目的地への誘導と訪問報酬は使わない。
候補を一つも完了できなければ全車巡回を返す。

`retain_candidates` は、まず補給車0・1・2台の各区分から存在する最良候補を1件ずつ残す。
残りの枠を評価順に埋め、最大5件とする。これにより補給車台数の異なる構成も継続して改良する。

改良試行を `a = 0, 1, ...` とすると、毎3回のうち最初は最良候補を選び、残りは候補群から分散して選ぶ。
具体的には、最良候補の添字を0とし、残り2回の添字は `(floor(a / 3) + a % 3) % 候補数`。
基準時間は `τ = τ₀ * (2 + 0.5 * floor(a / 5))` とし、後の試行ほど長く探索する。
毎3回のうち最後には、可能なら巡回車と補給車を1台ずつ選んで役割を交換し、保存経路と行動列の車両対応も交換する。
移植した経路を全日程で再探索し、同じ車種配置なら改善時だけ更新、新しい配置なら候補に加えて再び5件に絞る。

### 7.2 日別回答と探索の多様化

日別回答の基準探索時間は、処理開始時点の残時間 `B` と先読み日数 `H` から `τ = max(0.001, B / (12H))` 秒とする。
この基準値を使って期限まで短い先読みを繰り返し、各日への実際の割当は `rollout` が残時間から制限する。
新しい試行は、車種選択では期限の10 ms前、日別回答では5 ms前まで開始できる。

燃料重み `w`、翌日目的地への誘導係数 `g`、訪問報酬の幅 `s` は、試行番号を5で割った余りに応じて切り替える。

| 試行番号 `% 5` | 車種選択の `(w, g, s)` | 日別回答の `(w, g, s)` |
| ---: | --- | --- |
| 0 | `(0.025, 0.04, 0.12)` | `(0.06, 0, 0)` |
| 1 | `(0.06, 0, 0)` | `(0.02, 0.04, 0.12)` |
| 2 | `(0.12, 0.08, 0.25)` | `(0.12, 0.08, 0.25)` |
| 3 | `(0, 0.12, 0.5)` | `(0, 0.12, 0.5)` |
| 4 | `(0.2, 0, 0)` | `(0.2, 0, 0)` |

燃料を使い切る候補、翌日に余力を残す候補、車両ごとの店舗分担を変える候補を探索し、最後は共通の `Q` で比較する。

## 8. 行動列への変換と状態の確定

`Router::plan` は合流ごとの完了時刻を記録しながら再評価し、違反量が0の場合だけ行動列を作る。
各区間の `directions` を連結し、予定の完了時刻が到着時刻より遅ければ差分を負の整数の待機命令として挿入する。
最後に、当日の `daySteps` までの残時間も待機命令で埋める。
命令形式の詳細は[通信仕様](../../../../tester/solo/docs/protocol.md)を参照する。

`main` は送信前に `Game` の複製で当日計画を実行し、最終検証する。
本体の `Game` はその場では進めず、回答した計画を `pending` に保存する。
次の要求を受け取った時点で、前日の計画が受理されたならその計画、拒否されたなら待機計画を実行して本体の状態を進める。
実際の獲得ブランドを `Memory::known` に反映し、保存日程の先頭を取り除く。拒否時は残りの保存日程も消す。

車種選択が拒否された場合は、観測された車種で `Game` を作り直して `Memory` を初期化する。
次の日の探索に入る前に、内部状態の日付・車両状態・交通量を観測と `assert_eq!` で照合する。
不一致を観測で上書きする処理ではなく、シミュレーションとのずれを検出する処理である。

## 9. 実時間の管理・再現性・検証

要求行を読み終えた直後から実時間を測り、次の期限を使う。JSONの解析、経路の前計算、先読みのシミュレーションもこの時間に含む。

```text
reserve_ms = clamp(timeLimitMs / 100, 15, 700)  // 整数除算
探索期限   = 開始時刻 + max(0, timeLimitMs - reserve_ms)
```

予約時間は最終検証とJSON出力のために残す。
期限確認は探索の節目に行うため、反復1回ごとに厳密に停止する仕組みではない。
実行設定や短縮確認の方法は[設定](settings.md)にまとめている。

探索は単一スレッドで、`Random` の同じseedからは同じ乱数列を生成する。
ただし終了条件は実時間なので、同じseedでもマシンの負荷などで反復回数や最終計画が変わる場合がある。
入力の地形・店舗・状態から計画を作り、ケース番号や事前に保存したケース別解答は利用しない。

高速評価では、経路情報の表引き、32ビットの店舗・ブランド集合、固定長の訪問列を使う。
x86_64では実行時にPOPCNT対応を確認し、対応CPUでは同命令を有効にした探索関数を使う。非対応環境では通常の関数を使う。

検証は [tests.rs（単一ファイル内）](../solver05.rs) と [routing.rs（単一ファイル内）](../solver05.rs)・[strategy.rs（単一ファイル内）](../solver05.rs) 内のテストで行う。
主な確認対象は、合流依存の循環、開始位置での補給、店舗在庫とブランド集計、ランダムな実行可能計画の実得点・終了状態、行動列を保つ圧縮、保存2日分を再生して先読みを延長する処理、車種交換、乱数列と評価の一致。
テスト実行コマンドは[比較対象のアルゴリズム](../algorithms.md#solver05)、本番条件での比較結果は[検証記録](validation.md)を参照する。
