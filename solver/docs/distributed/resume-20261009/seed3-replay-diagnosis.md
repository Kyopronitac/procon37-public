# seed 3：C008 短縮1の日別種類数低下

2026-10-09。D0短縮1、C007短縮1、C008短縮1の保存済み公開リプレイだけを比較した診断。対戦やソルバを再実行していない。小さいJSON集計と最短距離計算はローカルCPU 3に固定した。固定相手の内部実装は閲覧していない。

## 結論と適用範囲

C008の日別種類数の不足3は、すべて **5日目（56 steps）** で生じた。4日目終了時の配置と5日目の実際の交通を固定すると、C008は翌日の13種類取得がすでに不可能で、日別種類数の楽観的上界は11だった。実績は10種類である。この上界は移動時間だけの必要条件であり、11種類を同時達成できることの証明ではない。

これは終了位置と次日の短い行動時間を評価する候補を調べる根拠になる。一方、共有キャッシュの計算が誤った、車種選択だけが原因、あるいはこの対策が全体成績を改善する、という結論は出せない。版ごとに車種選択・他チームの行動・日々の交通も異なる。1ケースの観測から採用判断は行わない。

## 4日目終了と5日目の到達上界

| 版 | 5日目開始の収集車セル（車番号:セル） | 補給車セル |
| --- | --- | ---: |
| D0 | 0:64、2:29、3:33 | 28 |
| C007 | 0:83、1:33、2:63 | 57 |
| C008 | 0:33、1:33、3:83 | 244 |

C008の未取得ブランドは0（セル29）、5（セル63）、11（セル11）。この3ブランドはそれぞれ該当店舗が1つだけで、5日目終了時にも初期在庫2・2・4玉がすべて残っている。

実際の5日目交通からDijkstraで得た最短**移動時間**は次のとおり。

| 出発セル | ブランド11 / セル11 | ブランド0 / セル29 | ブランド5 / セル63 |
| --- | ---: | ---: | ---: |
| 33（収集車0・1） | 58 | 59 | 61 |
| 83（収集車3） | 55 | 56 | 58 |

計算は出発セルの費用を使う。地形0は2、地形2は3、道路は記録されたstatus 0/1/2に対して1/2/4 steps。池は通れず、交通はその日中固定。全リプレイの予約移動時間がこの費用と一致することも照合した。

公開engineは各stepで移動を反映した後に収集するので、**最終step 56への到着も取得可能**として含めた。初期位置の店舗はstep 1に収集できる。補給車2は店舗へ到達しても収集しないため、上界計算から除外した。燃料制約と他店舗回収に必要な時間は無視しており、これは有利な仮定である。

車0・1は3つの欠落店舗のいずれにも届かない。車3もセル63には届かず、11→29と29→11はそれぞれ6 stepsなので、セル83から両方を回るには最短でも `min(55+6,56+6)=61` steps必要。したがって欠落3ブランドのうち取得できるのは最大1つ。他の10種類をすべて取れると仮定しても上界11となる。**不足3のうち少なくとも2は5日目の開始状態ですでに不可避**だった。

この証明はC008で観測した配置と交通の組に対するもの。配置だけ、交通だけの原因帰属ではない。同じ33/83から別runの5日目交通を仮に用いると、D0交通ではさらに遅い一方、C007交通では33→11/29/63が54/54/56となる。交通差は無視できない。この仮想置換は実対戦の再現や改善実験ではない。

## 自作D0 plannerの読取と最小候補案

保護対象外の `solver/distributed/solver/planner.rs`、`pool.rs` を確認した。次はコード上で確認できる事実である。

- `terminal_value`（planner.rs:416）は補給車までの燃料距離、残燃料、最寄り店舗へ動ける燃料を評価する。次日のstepsや、チーム全体で届くブランド集合は引数に持たない。
- `evaluate`（planner.rs:563）には既存の `coverage_weight` 項があり、終了位置から各ブランドまでの最小推定費用と次日の `steps/4` を比較する。しかし分散SearchPoolの生成（pool.rs:212付近）では `coverage_weight=0.0` を渡している。
- `plan_with_rollout`（planner.rs:1432）は局所予算3500ms以上で当日探索に67%を使い、余裕があれば実際の次日stepsを使って1〜2交通シナリオを探索する。**当日planを作り直さず**、未来を含む `choice_value` を計算し、77探索間の候補選択へ渡す。
- `forecast_traffic`（planner.rs:424）は自身の滞在、観測カテゴリ、相手位置からの推定を使う。2つ目のrolloutも観測混雑を最低status 1へ残す処理であり、次日の実交通と一致する保証はない。
- 終端配置が異なる複数の当日planを再比較する `coverage_guard` は、`allow_archive=true`、16店舗以下、局所limit 20000ms以上が条件（planner.rs:1003）。通常の `plan` は `allow_archive=false` を渡す（planner.rs:959）ため、今回の10秒短縮だけでなく、通常の分散日探索で時間を延ばしてもこの経路は有効にならない。

推論として、当日37玉の候補内で終端が分散しない、あるいはrolloutが将来交通を楽観視すると、後段の77候補比較だけでは北東側へ車を残せない可能性がある。ただしseed 3で採用されたworkerの全内部予測はこの診断資料に残っておらず、「rolloutが13種類を予測した」「予測誤差だけが原因」とは確認できない。

**最小の候補案**は、既存 `g.potential` と `Outcome.endnodes/endfuel` を使うチーム単位の終了位置評価を独立の小さな項として追加し、次日の短いstepsで各ブランドへ届く余裕が少ない配置を、当日得点が近い候補の中で避けるもの。補給車を除き、同一ブランドの複数店舗は最小値にまとめ、最終日には無効化する。毎回の経路再探索を行わず、車数×店舗数程度に抑え、当日の種類・玉数を不用意に犠牲にしないよう寄与を制限する。特定seed・ブランド・セル番号の条件は入れない。

単に既存 `coverage_weight` を正にするだけでは `beam_car` がlegacy経路へ切り替わる（planner.rs:643）ため、探索速度も同時に変わる。最初の比較ではこの副作用を避けて終端評価だけを分離するのが小さく評価しやすい。`g.potential` は現日の経路表に基づく推定値であり、厳密な翌日到達上界とは呼ばない。またブランドごとの最短値だけでは、1台が複数ブランドを同時に回れない制約を捉えきれない。この制約の厳密化や交通シナリオ追加は初案へ詰め込まず、全12件の同条件反復で品質と探索回数の変化を見てから判断する。

一般化した初案、計算費、既存beam／rolloutとの整合性、全形式の検証案は [C011設計](c011-terminal-reachability-design.md) に記した。この資料は診断と案の保存のみ。D0/C007/C008のソース・設定・バイナリは変更していない。
