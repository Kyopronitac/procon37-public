# C007：compact経路表の有限microbench

**C007は未採用・対戦未評価です。** 同一のrelease test binary内で、D0のeager `Graph::new` とC007のcompact `Graph::new` を比較しました。構築とqueryの合計は速くなりましたが、初回の訪問列queryには遅延復元の費用があります。

## 測定結果

ローカルCPU **1だけ** に固定し、他のCPUで探索・並列ビルドは行っていません。seed 0/1/2の3形式を各3反復、eager→compactとcompact→eagerを交互に測定しました。値は各項目の中央値、倍率は対応する反復ごとの合計速度比の中央値です。

| seed | 構築ms（D0→C007） | cold訪問列4096件ms | hot訪問列4096件ms | 構築＋全query ms | 合計速度比 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 0 | 84.780 → 54.837 | 0.321 → 0.468 | 0.131 → 0.146 | 85.285 → 55.523 | 1.54倍 |
| 1 | 194.258 → 104.832 | 0.697 → 0.721 | 0.601 → 0.145 | 195.664 → 106.041 | 1.92倍 |
| 2 | 457.998 → 230.873 | 0.864 → 1.232 | 0.771 → 0.210 | 459.716 → 232.593 | 1.98倍 |

別途4096件のtime/fuelメタデータqueryも測定し、合計時間に含めています。全9比較でtime/fuelと訪問列のchecksumは一致しました。cold queryはC007で遅くなり、総時間の削減は主に未使用経路列の構築を省いた効果です。測定した訪問列queryを繰り返すhot段階では、seed 1/2でC007が速くなりました。

経路表と経路列のみの格納量見積りは、大盤seed 2でD0が約232.6MiB、C007が構築直後約46.1MiB、query後約46.8MiBでした。これは構造体・配列容量から算出した見積りで、プロセスRSS、allocator管理情報、共通のその他Graph領域を含みません。全経路が使われればlazy cacheは増えます。

## 方法と限界

- 問題は公開 `generate_for_players(seed, None, 4)`、形式自動・練習場有効。観測は初日で全車の初期位置・燃料を使用。
- eager側は測定専用moduleにD0の `Graph::new` を保存したもの。経路だけを簡略化した参照器ではなく、座標生成、6modeのDijkstra、time/fuel、重複mode判定、燃料距離、potential、mobilityまで同じ範囲を構築します。
- queryは4096件。75%をmode 0、残りをmode 1〜5とし、sourceの75%をtarget/anchor部分集合、残りを全sourceから選ぶ固定乱数列です。各queryでtime/fuelを参照した後、同じ列で全訪問セルを走査するcold段階、その反復であるhot段階を測定します。
- この分布は合成したものです。実探索でのアクセス頻度をトレースして得た分布ではありません。各形式につきquery範囲取得用のcompact Graphを1回構築・破棄してから、3反復を開始します。
- 合計は構築＋metadata query＋cold route query＋hot route query。Graph破棄時間、同時15/31探索による負荷、通信、GPU、対戦成績を含みません。
- メモリ見積りの全表走査はtiming後に行い、構築とcold queryの間でcacheを暖めないようにしました。
- 全source/target/modeの意味同一性は、別の通常単体テストで1,608,270経路を比較済みです。checksumだけで同一性を判断していません。

この結果から、実対戦で同じ倍率になる、得点が改善する、正式採用できる、とは判断しません。採用には指定4チーム・短縮12件の反復と、その後の正式12件が必要です。
