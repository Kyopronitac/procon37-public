# C011 設計案：翌日 steps を使う終端配置評価

2026-10-09。設計のみ。D0 の自作 planner を読み、公開リプレイの [seed 3 診断](seed3-replay-diagnosis.md) から一般化した案を記す。候補ソース作成・ビルド・対戦・遠隔操作は行っていない。固定相手の内部実装は参照していない。

## 提案

D0 を直接の土台とし、当日探索の全車評価に、**翌日の短い steps で各ブランドへ向かう余裕が乏しい終了配置への小さな減点**を加える。既存 `coverage_weight` は 0 のまま、現在の高速 beam と rollout を維持する。C007/C008/C010/GPU との同時変更は初案に含めない。

毎回の評価で車数×店舗数を走査する代わりに、既存経路表から各ノードのブランド到達 mask を一度作る。候補評価は収集車の mask の OR と popcount だけにする。初案は燃料項、厳密な複数ブランド巡回判定、新しい交通シナリオを追加しない。

これは探索を誘導する代理指標であり、翌日の取得種類数の保証でも厳密な上界でもない。採用判断には全12件の反復比較と正式フルテストが必要である。

## 観測とコード上の根拠

公開リプレイでは、seed 3 の C008 は4日目に D0 と同じ37玉を取得した一方、翌日56 stepsの開始配置と実交通を固定すると、種類数の楽観的上界が11、実績が10だった。燃料切れは観測されていない。ただし配置・交通・車種選択が版間で異なり、終端評価不足だけが原因とは断定できない。1台で複数店舗へ届くかという上界証明は診断資料に分離した。

読取対象は `solver/distributed/solver/planner.rs` と `solver/distributed/pool.rs`。SHA-256 はそれぞれ `11e043e33018dee34f41f295d6ae1500497b0bfc7c8c33d5b253a5621587461a`、`74a981b5f1423b16e07b8f0e888e00c797b41b670140921112b874b4a6b27214`。

| 箇所 | 確認できた動作 | 設計への意味 |
| --- | --- | --- |
| `terminal_value` :416 | 補給車への燃料距離・残燃料・最寄り店舗へ動ける燃料を評価 | 翌日 steps と全車のブランド分担を直接扱わない |
| `evaluate` :563、`pool.rs` :212 | 既存 coverage 項はあるが、分散側は weight 0 | 別の独立項を追加する |
| `beam_car` :643 | coverage または future weight が正だと legacy へ切替 | weight を流用せず、現行の高速経路を保つ |
| `plan` :948、`plan_inner` :1001 | 通常の `plan` は `allow_archive=false`。coverage_guard には同フラグと limit 20000ms以上が必要 | 通常の分散日探索では、時間を延ばすだけでも guard は有効にならない |
| `plan_with_rollout` :1432 | 予算3500ms以上では当日探索に67%を割当て、後から翌日を1〜2シナリオ探索 | 元の当日 plan は変更せず、77探索の候補比較に使う |

考えられる不足は、当日得点が同等の候補を生成する段階で、翌日の短い時間に備えた終了配置が残りにくいことである。rollout は最終的な候補選択を改善できても、生成されなかった当日配置を作り直せない。一方、seed 3 の採用 worker の予測値は保存資料から確認できず、「rollout が13種類を予測した」といった説明は推測になる。

## 初案の評価式

翌日の制限 steps を `T = day_steps[obs.day + 1]` とする。対象ブランド集合 `B` は、在庫が正の店舗に存在するブランド。既取得ブランドも翌日の日別種類数に意味があるため除外しない。同一ブランドの複数店舗は同じビットにまとめる。

各グラフノード `u` に、`g.potential[u][shop].time` を使って次の2つの `u64` mask を作る。

- `near[u]`：対応する店舗へ `floor(T/2)` steps以内の経路を持つブランド。
- `full[u]`：対応する店舗へ `T` steps以内の経路を持つブランド。

比較は `<=` とする。出発セルの移動費用と途中移動による終了セルは既存 Graph／evaluate に従い、`Outcome.endnodes` を使う。目的としていた店舗や最後の route token へ置き換えない。開始位置が店舗なら距離0として含む。T が正なら初期位置の取得も可能だが、T=0、翌日なし、通常の収集車・補給車構成でない場合は新項を無効にする。

補給車を除く全収集車について終了ノードの mask を OR し、`N` と `F` を得る。`N` は `F` の部分集合になる。初期の固定係数案は次のとおり。

```text
far  = popcount(B & ~F)
thin = popcount(B & F & ~N)
terminal_penalty = -min(12, 4 * far + thin)
search_value = D0_evaluate_value + terminal_penalty
```

1ブランドがどの車からも T に収まらない場合を4点、Tの後半まで掛かる場合を1点とし、全体で12点まで減点する。全形式に同じ式・係数を使う。店舗番号・seed・地図座標・特定の日数の条件を入れない。係数は未測定の初期仮説で、初回実装前に固定して記録する。

12点は D0 の1玉20点より小さいが、既存の時間・燃料項もあるため、**当日得点を絶対に犠牲にしない保証ではない**。日別種類数・玉数の全ケース集計で副作用を確認する。上限に達した配置同士の差や帯の中の微小な距離差は見えなくなるが、初案では速度と小さい変更範囲を優先する。

## 最小の接続範囲と整合性

実装箇所は候補コピーの planner と小さい専用 unit test を基本とする。通信、Snapshot、worker数、Graphの経路生成、RNG、探索予算の配分を変更しない。feature off では mask の作成も行わない。

| 接続点 | 必要な処理 |
| --- | --- |
| 当日 `plan_inner` の入口 | 当日実要求か forecast/selection かを明示し、前要求の補助表を消す。実要求だけで Graph 確定後に表を構築する |
| 全車 `evaluate` | 各車の route memo／`route_values` を確定した後、チーム単位で1回だけ新項を加える |
| 高速 `beam_car` | `zero.value` に含まれる新項を `fixed` から外す。他車の終端 OR を先に作り、prefix候補の `next.node` の mask を加えて新項を計算し直す |
| `fleet_pool` | 個別 route 値には新項を入れず、既存の最終 full evaluate で確認する。分枝上界は新項が非正なので楽観側のまま保てる |
| canonical 再評価 | 新項を明示的に外して従来どおり reserve 15 で評価する。raw_value、choice_valueの式は D0 のまま |
| 終了・restore・早期 return | 補助表が次要求や別 Graph へ残らないよう消す。Snapshot や wire へ追加しない |

適用範囲には暗黙の `!selecting` だけを使わない。`select_role` は通常の `plan_inner` を `selecting=false` のまま呼ぶためである。例えば当日実要求かどうかの明示引数を追加し、全呼出し箇所の selection／rollout を false、通常 `plan` の本探索だけ true とする。補助表は day と Graph に対応する1要求限りの所有データとする。

最終日、110ms以下の待機 fallback、役割不整合時の collector fallback では作成しない。C011初案では既存 coverage/future/archive weight を0に固定し、別の未来探索モードへ混ぜない。worker間で係数を変えず、同じ reserve group 内の elite が同じ評価式を使う状態を保つ。既存の receiver 側再評価も維持する。

高速 beam の補正は省かない。単に `evaluate` に項を足すだけだと、空 route の全車減点が `fixed` に残り、候補の終了位置に追随しない。補正後もラベル `(mask,node)` と時刻・燃料による枝刈りは維持できる。新項は、他車を固定すると同じ node で同じ値だからである。最終 full evaluate の受理確認も残す。

fleet の候補生成と上位候補切捨ては従来の個別 route 値を使うため、有益な終了位置がその段階で落ちる可能性は残る。これを同時に作り替えると変更が大きくなるので初案には含めない。新項が非正であることは既存上界を壊さないが、既存の上位幅による近似探索を完全探索へ変えるものではない。

## 二重計上と不確実性

- **燃料**：新項は時間だけを使う。既存 terminal_value に加えて残燃料不足を再減点しない。その分、燃料や補給制約で実際には届かないブランドを到達側に数えることはある。
- **rollout**：新項は当日の探索誘導だけに使い、forecast探索・canonical・候補比較の式には入れない。`first_raw + 0.75 * worst + 0.05 * (first_canonical - first_raw)` は D0 のまま。rolloutで十分に予測できる場合にも小さい代理減点を二重加算しない。
- **交通**：現在の観測交通の既存経路を使う。翌日は他チームの経路も関係し、今より速くも遅くもなり得る。現在の full mask に入ることも入らないことも、翌日の取得可否の証明にならない。
- **経路表**：時間と燃料の重み付き経路なので、同じ交通でさえ純粋な最短時間より遅いことがある。Tを超えても別経路では届く可能性がある。厳密な上界は診断で使った時間のみの最短経路計算と区別する。
- **複数ブランド**：同じ車の full mask に2ブランドが入っても両方を同日に回れるとは限らない。seed 3 の「車3は北の2店舗を同時には取れない」という制約を、この初案は完全には検出しない。
- **既存の終端項との関係**：燃料を保つ配置とブランドへ分散する配置が競合する場合がある。小さい減点と全12件の得点確認で評価し、燃料項や補給戦略も同時に調整しない。

## 計算費とログ

Graphのノード数を S、店舗数を M、収集車数を A とすると、表作成は O(SM)、表本体は `16S` byte。現行経路表を読むだけで、新しい Dijkstra、Graph、スレッド、ネットワーク要求は不要。例えば S=1032 なら表本体は16,512 byte/workerだが、これは説明用のサイズ計算で実測ではない。

full evaluate の追加量は O(A) の2本のORと2回のpopcount。高速 beam では他車分の OR を1回計算し、各prefixの追加量を定数にする。hot loop内の確保・辞書・排他・ログは追加しない。表作成も既存要求締切の内側に含め、探索時間を延長して補償しない。

計測時は1要求終了につき、表作成時間、当日採用planの far/thin/減点、適用有無を1行にまとめる。既存 graph_ms/iterations と区別して保存する。速度の評価は同じ入力・同じCPU配置の feature off/on を反復し、全形式で表作成時間、探索回数、締切超過、RSS/HWMを比較する。未計測の現段階では「追加費用が無視できる」とは主張しない。

## 検証案

実装後は、次の境界と統合を小さく確認する。

1. T/2・Tの直前／一致／直後、T=1、T=0、最終日を確認する。到着がTと一致する場合はfullに含める。補給車の位置だけ改善しても値は変わらず、収集車がブランドへ近づくと減点は増えない。
2. 同一ブランドの複数店舗、在庫0店舗、既取得ブランド、店舗上の開始、経路途中の実終端を確認する。独立した単純な車×店舗走査と mask 版の値を照合する。
3. 新項が常に [-12,0] で、route memoの再利用順序・同じ車routeと異なる他車routeに依存する誤キャッシュがないことを確認する。高速beamの局所式と full evaluate の同じ候補での値を照合する。
4. 車種選択・forecast・canonical・fallbackに項が漏れず、restore後に古いGraphのnode番号を参照しないことを確認する。offでは固定の評価入力・RNG状態・計数予算で D0 の値と出力を照合する。時間制探索の完全一致を決定的テストとして要求しない。
5. 1回戦・準決勝・決勝の公開問題を使い、全agent数・店舗数と node配置で合法提出、engine得点と内部予測を確認する。seed 3は境界理解の1ケースとして使い、係数選定を同ケースだけで行わない。

対戦は今回指定の固定4チーム、12件 seed 0〜11、形式auto各4件、arena取り込み有効、選択・各日10秒で行い、全48ACと前後hash一致を必須とする。D0短縮1/2のばらつきも基準にし、C011を複数回評価して平均順位、種類・日別種類・玉の合計、対D0の勝・同点・敗を保存する。終了位置の指標改善だけで採用しない。

条件や係数を変更した場合は新しい候補識別として保存する。時間・配置を変えた場合はD0も同条件で再評価する。明確な反復改善があってから、探索予算短縮なしの公式時間による正式12件へ進む。各runは内容が分かる `--label` を付け、`--output-dir` を指定せず `.server/runs/` に保存する。正式評価済みの実装・設定とcommitする版を一致させる。
