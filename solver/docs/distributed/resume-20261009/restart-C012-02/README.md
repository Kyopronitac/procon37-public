同じ窓口を待っていた別配置D0のVOID1運用プロセスを、その管理ツールの_node stopで停止した。運用親プロセスのcleanupでVOID2も終了し、ポートを解放した。その配置ファイルは変更していない。

最初にH2-D0-short-01を12件・seed0〜11・形式自動・練習場有効・全員10秒で実行する。配置と実行ファイルを凍結する。その後同じ環境でC012を比較し、有望なら反復と正式評価を優先する。以前のC012初回（平均1.1667）は参考情報として保持する。

`inventory.json`、`performance-restored.json`、`clock-restored.json`、`clock-process.json`、`.server/distributed/lab-config.json`を参照。観測は`solver/distributed-lab/observe.py`で開始前mark・実行中の1窓・終了後だけ行う。ログは既定.server/runsへ保存し、実行中の重いビルドや性能測定は行わない。

## 反復中の考察

ユーザーの指示により、監視と並行して保存済み記録を分析した。必要なsubagentの起動も明示許可されたため、リプレイ・通信・GPUの3範囲を分担した。CPU3の軽い読取のみとし、評価PCでの追加計測・ビルド・実装/配置変更は行っていない。

- [順位と大盤seed11のリプレイ分析](analysis-replay-first-pair.md): 初回の順位改善は主に16盤面。自己得点は+19玉と−15玉が相殺して+4。seed11では最終日の追加玉配分が差の中心であり、観測された補給待ちを直接原因と断定できない。
- [通信と受信担当の分析](analysis-communication-first-pair.md): 受信が成立していてもchecks=0の日がある。LAN周期の短縮より初期bindの理由計測/回復と、最終提出への寄与計測を優先する仮説。VOID2/3の代表選出とVOID1の最終提出を混同しない。
- [GPUの次段階](analysis-gpu-next-step.md): OpenCL前の起動失敗では性能棄却できない。C009bの最小修正検証と有限6pairには価値が残るが、共有後の対象量・初期化・CPU競合を含めて足切りし、C012の正式判断を先に進める。

これらの考察は現行C012に混ぜない。H2の2組の成績を確認し、有望なら凍結版の正式評価へ進む。次候補へ進む場合も、単純な通信頻度増と受信有効化修正とGPUを同時に変更しない。
