# 16×16共有周期の選定方法

この資料は候補の評価中に作成した判断手順です。実装・配置・評価ハーネスを変更せず、保存された JSON 成績と今回のログ範囲だけを読みます。最終判断と本番配置は別に記録します。

## 比較の範囲

新規評価は C014（100 ms）と C015（2000 ms）を各 seed 0・3・6・9、同じ4チーム、公式60秒で比較します。C013（500 ms）の再評価はユーザー指定により省略します。

`baseline.json` の4件は均一な C013 評価ではありません。seed 0 は提出時刻変更前の C012、seed 3・6・9 は55秒提出・同内容再提出省略後の C013 です。したがって次を分けて表示します。

| 集計 | 使う seed | 解釈 |
|---|---|---|
| 保存済み4件参照 | 0・3・6・9 | C012/C013 混在。全4件の参考位置を示す |
| 同じ提出方針の C013 部分 | 3・6・9 | C013 との比較はこちらも必ず確認する |
| 新規候補間 | 0・3・6・9 | C014/C015 を同じ現在の条件で比較する |

保存済み4件の分散平均順位は1.50、種類数48、日別種類数334、玉数637。同じ提出方針の3件は平均順位1.3333、種類数36、日別種類数278、玉数571です。参照値の新規実行は行いません。

## 表示する指標

- 各 seed の公式順位、種類数、日別種類数、玉数を、分散・固定並列・第6世代・第8世代の全員について並べる。
- 集計では平均順位を主にし、種類数・日別種類数・玉数はそれぞれ独立に記載する。独自の重み付き点数や得点辞書順の勝敗指標を作らない。
- 完了した seed のみ暫定集計する。途中の平均と参照4件全体を直接比較せず、同じ seed の参照値も併記する。
- 最終の平均順位と各合計に加え、seed 3・6・9 だけの集計を載せる。seed 0 だけの変化を C013 の改善根拠にしない。

固定相手も時間制探索を行い、分散側の経路変更は他チームの混雑にも影響します。相手の実行ファイルが同じでも、同じ seed の成績は変動します。分散側の順位上昇が相手の低下によるものか、分散自身の指標にも変化があるかを確認します。固定並列・第6・第8世代の各指標の差を併記し、相手の変動を独立した環境補正値として差し引きません。

## 信頼できる実行かの確認

選定対象とするには全16AC、候補ごとの前後識別一致、4件の問題一致、固定相手・提出条件・CPU配置不変を確認します。探索は4回の車種選択と28日分の計画、計32要求です。VOID1の31探索とリモート2件、VOID2の15探索、VOID3の31探索の完了と入力ハッシュを照合します。

通信は各ノードの取り込み数・受信側改善数・入力不一致・不正パケット・サイズ超過・確認回数0の日を確認します。最終候補が受信専用探索スレッドから選ばれた回数も参考にできますが、取り込んだ解が最終提出に残ったことの証明にはなりません。取り込み回数の多さだけで採用しません。`ELITE_INTERVAL` はネット送信だけでなくローカル公開と残時間条件にも効くため、差をネット通信だけに帰属させません。

## 判断と記載

4件だけの小差、特に1玉差から順位が動いた場合は強さを断定しません。新規候補の差と、同じ提出方針の C013 3件に対する差を合わせ、悪化する seed と固定相手の変動を確認します。同等または結論が不安定なら既存 C013 を優先します。期限までに選んだとしても、16×16の指定4件に基づく試合向け選択であり、全形式の正式12件評価による一般採用とは区別します。

最終記録には、選んだ版、平均順位と3指標、全員ACと識別検証、C012混在の制約、通信の健全性、選択に残る不確実性を記載します。06:15までの配布・起動検査・commit・pushを妨げる追加評価は、この判断資料からは開始しません。
