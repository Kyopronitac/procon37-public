# 成績と通信についての観測

## 評価途中の注意点

公開された問題から、seed 0・3・6・9 の種類数と日数はそれぞれ 12×5、13×10、11×8、12×5 です。種類を毎日すべて得たときの日別種類数上限は 60・130・88・60 になります。参照 C013 の seed 3・6・9 はすべてこの上限に到達しています。この3件では玉数の小差で公式順位が大きく動きやすいため、順位だけで探索の改善を断定しません。

C014 の seed 0 は全4ACで、分散1位・12種類・日別57・玉63でした。混在参照の同じ seed は C012 の2位・12種類・日別56・玉66です。日別種類が増え、玉数は減っています。また NOM は日別56→55・玉66→70、第6世代は日別56→55・玉67→65、第8世代は日別54→54・玉65→66と変動しました。この1件は C013 と同じ提出条件の比較ではなく、ここから C013 に対する強化を確定しません。

暫定・最終の機械集計は `selection-analysis.json` に保存します。元の run.json は `evidence/raw-runs/`、元ファイルと問題・設定・リプレイの識別は `evidence-index.json` に保存します。リプレイ本体はコピーしません。

## 通信の解釈

既存 C013 の通信監査は seed 3・6・7・9 を対象にしており、新規評価の seed 0・3・6・9 とは対象が異なります。過去の取り込み総数を、新しい4件の取り込み総数とそのまま比較しません。通信頻度による差は、まず同じ4件の C014 と C015 を見ます。

各候補の `ELITE_INTERVAL` は通信間隔とローカル公開間隔、共有に必要な残り時間の条件を同時に変更しています。送信数が増えても、新しい解の更新頻度・受信者の停滞条件・共有の終了時刻などが影響します。受信側の改善回数や受信専用 worker が最終候補に選ばれた回数は、取り込んだ外来解が提出まで残ったことの直接証明ではありません。

## 通信カウンターの解釈

C014/C015 の変更定数はネットワーク送出間隔だけでなく、ローカル優良解の公開間隔と残り時間の公開・送出ガードにも使われる。したがって、この試験は単一の定数変更ではあるが「送出頻度だけ」を独立操作した試験ではない。C014 は 100 ms、C013 は 500 ms、C015 は 2,000 ms。受信候補を調べる間隔は全案 250 ms、停滞判定と取り込み後クールダウンは各 1 秒、取り込み余裕は 750 ms のままである。

実装では各グループの解が改善した場合だけ新しい公開版が生成され、同じ内容は再送されない。従って、100 ms 設定が 1 日に一定個数の送信を保証するわけではない。100 ms への短縮には新しい解が早く届く可能性がある一方、受信者の 250 ms 確認・1 秒クールダウンで取り込み頻度が制約される。2,000 ms は送出回数を減らすが、その分だけ 77 探索すべての探索量が増えるとまでは言えない。通信は制御スレッドが担当し、探索側の公開は try_lock で競合時に見送る。

集計する sent はパケット数、received は新しく格納した offer 数であり、単位が異なる。imports/improved は受信者内の取り込み・局所改善イベントで、最終提出内容への寄与や対戦得点の改善そのものではない。probe_ns/repair_ns は受信者内の評価・修復に要した時間で、通信・直列化費用を含まない。max_receiver_mailbox_age_ms は候補を検討した時点の保管経過時間であり、LAN の片道遅延として解釈しない。最終採用はこれらの内部件数よりも、全員 AC、固定条件の一致、順位と実際の得点指標を優先する。
