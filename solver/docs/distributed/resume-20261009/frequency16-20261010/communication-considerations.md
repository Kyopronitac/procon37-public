# 共有周期比較で見る点

この比較は、C013のPC間共有周期500msを100ms（C014）と2000ms（C015）へ変更したもの。各日の途中で共有する仕組みは3案とも有効である。

## 短い周期でも効果が比例しない理由

送信に先立ち、探索側から共有バスへ更新された候補を公開する。ネットワーク送信側にも周期があるため、公開と送信の両方で待ちが生じる。周期を短くすると新しい候補を相手へ届けるまでの待ちを減らせる。一方、受信側の探索は250msごとの確認、1秒の停滞条件と取り込み後1秒の間隔を維持する。100msへ変更しても、受信探索の取り込み回数が500msの5倍になる設定ではない。

同一候補や改善していない候補は公開せず、送信済みrevisionも再送しない。このため100ms周期は毎秒10個の解を必ず送る意味ではない。通信カウンタは実際の更新量にも依存する。読み取りに使う共有ロックはtry_lockで、競合時には探索を待たせず機会を見送る。

2000ms案では公開・送信の待ちが増える一方、通信処理と共有ロックの試行を減らせる。ただし同じ定数は共有開始・公開・送信時の残時間判定にも使うため、最後の2秒は送出機会が制約される。この比較から「ネットワーク帯域だけが律速だった」とは判断できない。

## 今回の選定

16×16の公式60秒を使うので、10秒短縮試験よりも共有後に探索を続けられる期間が長い。もっとも盤面によっては早期に同じ解へ収束し、共有頻度の違いが得点に出ない。固定相手も時間制探索で変動し、1玉などの差で順位が変わる場合がある。

通信数や受信側改善回数は仕組みが動いた証拠として扱い、最終提出への寄与回数とは扱わない。保存された順位、種類数・日別種類数・玉数、同試合の固定相手の値と合わせて選ぶ。ユーザー指定どおり追加2案各4seedの限定比較であり、統計的な優越や正式12件での一般採用を主張しない。
