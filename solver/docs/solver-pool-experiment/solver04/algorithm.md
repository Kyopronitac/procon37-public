# 第4世代の探索アルゴリズム

[一覧](../algorithms.md#solver04) / [単一ファイル](../solver04.rs) / [設定](settings.md) / [検証](validation.md)

第4世代は補給車の行動を時間付きの占有表へ変換し、その上で巡回車の経路を構築・改善する。
巡回車だけを先に作って補給を修復する候補も試し、問題条件によって翌日まで比較する。
昇格までの候補と正式結果は[世代記録](../records/generation-004.md)にある。

## 1. 処理の構成

入口の `Solver` は問題、乱数、選んだ車種、内部 `Game`、前回の回答と候補を保持する。
車種選択要求では補給車1台の位置を比較する。
日別要求では前回回答の採否を内部ゲームへ反映し、観測された車両・道路状態を設定する。
探索後は共通エンジンで回答の合法性を検査し、予測した終点・得点とも照合する。

| モジュール | 主な役割 |
| --- | --- |
| `itinerary` | 経路表、補給時刻表、候補生成、日別探索、車種選択 |
| `escort` | 補給車の移動・待機経路の改善 |
| `tour`・`window` | 訪問順や経路の一部の改善 |
| `joint`・`route_set` | 補給と巡回の共同改善、複数巡回経路の組合せ |
| `patrol_first`・`circuit` | 巡回側を先に組む候補、経路構築の補助 |
| `tomorrow` | 当日候補の翌日試走と選択 |

## 2. 端点間経路の前計算

`Network` は店舗と車両位置を端点にし、同じ位置を持つ端点は経路を共用する。
移動元セルの時間を `t`、燃料を `f` として、Dijkstra法の辺重み `4t`、`4t+2f`、`4t+9f` の3モードを用意する。
`Path` には移動方向列、実時間、実燃料を保存する。
訪問に必要な近接情報や終点の到達性も前計算し、探索中の繰り返しの経路計算を減らす。

道路状態は日ごとの観測を反映する。
翌日を試す際にはその試走に応じた状態で経路を作り直すため、当日の経路表をそのまま翌日に使い回さない。

## 3. 補給車の時刻表

`SupportRoute` は補給車の停車端点と待機時間、または直接の行動列を保持する。
`Supply::build` は各補給車の行動を1ステップずつ展開し、セルと時刻の占有表 `at` を作る。
移動時間中の位置、到着時刻、待機時間、日末までの待機も処理する。

占有表から「この時刻にこのセルで補給可能か」と「次に補給車がそのセルに現れる時刻」を取得できる。
`windows` は補給可能な連続区間で、巡回車の合流候補として使う。
補給車の終点から各セルへの時間・燃料距離も保持し、日末の巡回車が翌日に合流できるかを評価する。
補給と移動が同時刻に起きる境界は、行動列の時刻順で扱う。

## 4. 巡回候補と1日の評価

`Candidate` は補給経路、全車の行動列、訪問店舗のビット集合、日末車両状態、探索値をまとめる。
巡回経路は `car_route` と `cell_route` などがビーム探索で構築する。
巡回車が複数あるときは既に選んだ車の通過店舗と在庫消費を考慮し、同じ店舗へ過剰に集中しない候補を作る。

`local_value` は当日系列の種類数、未取得系列、在庫上限を適用した玉数を評価する。
日末の位置と燃料は `terminal_pos` で加点・減点し、翌日の店舗へ届きやすい位置と補給車への到達可能性も見る。
位置価値は最終日には弱まり、翌日がある場合に残り燃料と到達性の効果が大きくなる。
これは高速な探索用の値であり、正式得点は共通エンジンで求める。

## 5. 日別探索と改善処理

まず補給車の初期経路を作り、各巡回車の候補を組み合わせる。
その後、補給経路の変異と巡回経路の再構築を繰り返す。
前回の有効な計画があれば、反転や再時刻合わせで新しい観測へ移し、探索の初期候補に含める。

探索の反復では次のような改善を交互に適用する。

- `rebuild_subset` は一部の巡回車を、他車が選んだ訪問を考慮して作り直す。
- `escort` は補給車の経路を変更し、巡回車の合流可能性を広げる。
- `tour` と `window` は訪問順と経路の区間を局所的に置き換える。
- `joint` は巡回と補給を同時に調整し、`route_set` は車両別に保存した経路候補の組合せを比較する。
- `patrol_first` は燃料制約を緩めた巡回案を作り、実際の補給条件へ修復する候補を追加する。

候補の点数を比較して最良を保存し、温度に従って悪化候補も現在解へ受け入れる。
燃料不足や時間超過の候補を正式な回答へ直接採用しない。
最後に選んだ行動列を `Game::play_day` で検査する。

## 6. 車種選択と翌日比較

車種選択では各車を補給車1台にした配置を巡る。
初日は経路探索で得点を見積もり、同じ配置の候補を複数回改善する。
候補には巡回と補給の組合せが含まれ、最良の初日候補を日別要求へ持ち越す。
探索上限は要求時間の80%から100 msを引いた時間である。

日別探索では、車両4台以下、翌日があり、要求時間5秒以上などの条件を満たすと `tomorrow` で当日の候補を保持し、翌日の状態まで試走して比較する。
翌日比較を行う場合、当日の候補生成には日別予算の約4分の3を使い、残りを先読みへ回す。
日別予算は要求時間の86%から60 msを引いた値を基本とする。
詳細は[実行設定](settings.md)を参照。

## 在庫と通過の集計

`Solver::new` は店舗の在庫数に応じて `stock_layers` の各ビット層を用意する。
候補の巡回車別訪問集合を層へ重ねることで、同じ店舗を何台の巡回車が通ったかを高速に数える。
玉数は訪問台数と在庫の小さい方となる。
系列集合も訪問した店舗から生成するため、明示的な停車先だけでなく経路上の通過店舗を評価できる。

日別評価の中心は当日系列 `1000`、新規系列は残り日数に応じた `fresh_bonus`、玉数 `10` である。
`fresh_bonus` は残り1日で100000、2日で2000、それ以前で300。
試合終盤ではまだ取得していない系列の価値を上げる。
日末の燃料・位置・補給車への到達性は `terminal_pos` と `local_value` によって補正する。

## 巡回ビームの状態と構築

`Beam` は端点、経過時刻、残燃料、通過店舗集合、系列集合、探索値、そこまでの経路を保持する。
補給車の時刻表を参照し、あるセル・時刻で燃料が回復できるときは状態へ反映する。
店舗を追加するときは、その店舗へ着ける時刻、燃料、経路上の通過店舗、他車の消費済み在庫を考慮する。
候補が日末まで収まらない場合は回答として残さない。

`rebuild_subset` は全巡回車を毎回作り直さず、一部の車だけを別の順序・ビーム幅で再探索する。
これにより補給車の停車地点だけを変えた候補や、他車の訪問が変わった候補を比較しやすい。
巡回車の候補集合は `route_set` でも再組合せされる。

## 補給経路を変更したときの整合

補給車の停車先や待機時間を変えると、巡回車が補給を受けた時刻と残燃料が変わる。
そのため `Supply::build` で占有表を再計算し、巡回車の経路を再時刻合わせする。
`preserve_patrols` は元の巡回行動を可能な限り残した候補を作り、完全再構築より良い場合はそちらを採る。

`escort` と `joint` は補給車の経路や合流点を変える。
`tour` と `window` は巡回順・経路区間を直す。
`patrol_first` は燃料を緩めて有望な巡回案を得てから、補給可能時刻と実燃料へ戻す。
どの経路も最後は共通エンジンで実行できる行動列へ変換する。

## 予測値と実行結果の照合

日別回答を選んだ後、内部の `Game` の複製で行動列を実行する。
エンジンが不正と判定した場合は待機計画へ切り替える。
受理された場合も、候補が予測した終点位置・燃料、日別系列数、玉数と実結果を比較し、差があれば標準エラーへ記録する。
これは高速な候補評価が公開ルールの実行とずれないかを見るための確認である。

## 機能ごとの候補作成

`initial_support` は補給車の初期停車・待機候補を用意する。
`mutate_support` は停車点や待機を変更し、`hub_support` は補給拠点を中心に新しい候補を作る。
`rendezvous_support` は巡回車の経路を見て合流しやすい補給候補を作る。
補給車の行動を変えた後は `Supply::build` をやり直し、各時刻の占有表と補給窓を作り直す。

`build_candidate` はその補給表を使い、巡回車の経路を作る。
`rebuild_subset` は既存候補の一部だけを変え、他車の訪問集合を保持する。
`preserve_patrols` は補給計画を変えた後も巡回行動を維持できる候補を探す。
候補に含む `masks` と `end` は最終得点と翌日価値の計算に用いる。

## 9モジュールの関係

`itinerary` が日別探索の時間と候補更新を管理する。
`escort` は補給車の直接行動、`tour` は巡回順や合流を含む行程、`window` は行動列の一部区間の差し替えを扱う。
`joint` は補給と巡回を合わせて調整し、`route_set` は複数巡回車が別々に持つ候補を組み合わせる。
`patrol_first` は補給をいったん緩めて巡回案を作り、実燃料へ戻す入口である。
`circuit` は巡回候補の構築を補助し、`tomorrow` は当日案の翌日試走を担う。

これらは独立した最終回答ではない。
同じ `Candidate` と `Supply` を受け渡しながら、より良い当日案を探す段階として機能する。
異なる操作を組み合わせることで、巡回順だけの改善や補給経路だけの改善で止まることを避ける。

## 得点と翌日位置の考え方

玉数の計数では、ある店舗が複数車に通過された回数をビット層へ積む。
店舗の在庫が3であれば3層までが得点に入り、4台目以降の通過は同じ店舗の玉数を増やさない。
系列は少なくとも1台が通過した店舗のブランド集合から数える。
未取得系列の重みは残り1日のときに大きくし、最終日に取り逃した系列を優先する。

翌日が残る場合、終点から各店舗までの時間距離と燃料距離を見る。
燃料不足なら補給車の終点からの距離も加味し、翌日を始めたときの救援が難しい配置を低く評価する。
車両4台以下では翌日のステップ数に対して遠すぎる系列へ追加の罰則を与える。
こうした終点評価は当日の系列・玉数が近い候補を区別する補正である。

## 先読みの成立条件と限界

`tomorrow` の先読みは、車両が4台以下、翌日が存在、要求時間が5秒以上のときに候補になる。
既にすべての系列を取得した状態などでは先読みを打ち切る。
残り時間の範囲で当日候補を保持して翌日を試し、より良い今日の行動を選ぶ。
翌日の交通は予測であり、次の実要求では観測交通を使って再計画する。

車種選択も日別探索も要求時間で打ち切る。
同じ乱数seedでも計算機負荷が違えば反復数と結果は変わり得る。
正式な昇格判定はこの保存用ソースの再測定ではなく、当時の30件の[対戦結果](validation.md)に基づく。

## `tomorrow` の候補選別

先読み候補は単純な `score` 上位6件ではない。
`retain` はまず当日に取れる系列数が最大の候補だけを残す。
同じ終点位置と燃料帯（燃料を8単位で区切る）を持つ候補があれば、その中では高得点のものに置き換える。
6件を超えたときは得点と終点の位置・燃料の違いを使い、翌日開始状態の多様性を残す。

`choose` は各候補の終点車両状態から別の `Solver` を作り、翌日の補給・巡回を探索する。
初日の翌日交通は道路状態1を仮定し、それ以降は当日観測を引き継ぐ。
候補ごとの残り時間を均等に配分し、補給車経路の更新、巡回の部分再構築、`tour` と `route_set` の改善を試す。

比較値は `当日の候補値 + 0.65×翌日の候補値` で、これがもっとも高い当日候補を返す。
この翌日探索は候補の終点から始める内部予測であり、当日を共通エンジンで全車再生してから評価する手順とは異なる。
実際の翌日要求では新しい観測に基づいて再計画する。

## 実装の高速化と対象範囲

経路探索や状態集合のキーには小さな整数が多いため、`SearchHasher` を使用する。
通過店舗と在庫の集計はビット集合と `stock_layers` で行う。
`Supply` は全時刻×全セルの補給可否を保持し、探索中に何度も合流判定を行うときの計算を抑える。

保存版の既定テストは18件成功し、2件は明示的なリプレイを使う任意の診断として `#[ignore]` のまま保存した。
これらを実行していないことは[検証記録](validation.md)にも記録した。
正式runで確認したのは30件・5体全員ACと順位合計による単独首位であり、全ての地図や計算機負荷での優位を保証するものではない。

## 8. モジュールを読む順番

第4世代は処理を複数モジュールへ分けている。
全体の入口は `entry.rs`、主要な状態と候補比較は `itinerary.rs` にある。
経路の前計算を理解してから、補給車の可用時刻を読む。
その後に巡回車の訪問構築と全車の組合せを読むと流れを追いやすい。

1. `Network` が店舗と車両位置を端点にする。
2. 複数の重みで端点間経路を前計算する。
3. `SupportRoute` が補給車の停車や直接行動を表す。
4. `Supply::build` が時刻ごとの補給可能セルを作る。
5. 巡回側の探索がその表を参照して行動を作る。
6. `Candidate` が全車の行動と終点をまとめる。
7. `local_value` が系列、玉数、日末の位置を比較する。
8. 必要なら `tomorrow` が翌日の候補を探索する。
9. 最終案を共通エンジンで検査する。

補給と巡回を一度に総当たりすると候補が大きくなる。
この構造では補給可能な時刻とセルを先に表へする。
巡回側は表を参照するだけで合流判定できる。
補給車の行動を変更したら、表と巡回側の評価を更新する。

## 9. 端点と移動コスト

端点は店舗と車両の現在位置を中心に作る。
同じセルが重なる場合は番号を正規化する。
こうして「店舗でもあり車両位置でもある」セルを一つの場所として扱う。
経路は `4t`、`4t+2f`、`4t+9f` の3モードを持つ。
`t` は移動元セルで支払う時間である。
`f` はそのセルの燃料消費である。

時間優先モードで届く店舗でも、燃料が足りない場合がある。
燃料を重く見るモードなら遠回りでも届く可能性がある。
一方、燃料節約の道が長すぎると日末時刻を超える。
候補評価では前計算の重み付き距離ではなく実時間と実燃料を用いる。
経路上にある店舗を通った場合は、その店舗の取得も数える。

端点を正規化しないと、同じセルに二つの番号が付き得る。
そのままでは「位置が同じなのに異なる終点」と判定するおそれがある。
正規化は経路表の大きさと候補の重複を抑える。
道路状態が変わる日には経路表を作り直す。

## 10. 補給時刻表の意味

`SupportRoute` は補給車の移動と停車を表す。
`Supply::build` はそれを時刻×セルの占有情報へ変える。
巡回車がある時刻にそのセルへ着いたとき、補給可能か調べられる。
この表には補給可能区間、次の補給可能時刻、補給車の終点情報もある。

例えば補給車がPへ時刻6に着き、時刻10まで待つとする。
巡回車が時刻8にPへ着けば補給できる。
時刻5に着いた場合は待機で時刻6に合わせる余地がある。
時刻11に着いた場合はその停車では補給できない。
実際には移動命令とセルの占有規則も関わるので、
表はゲームの時刻規則に合わせて構築する。

合流可否は位置だけでは決まらない。
補給地点へ着くまでの燃料が必要である。
補給を待つ時間は日末までの残り時間を減らす。
補給後の残燃料で次の店舗や終点へ届く必要がある。
巡回車の探索はこれらをまとめて判定する。

補給車の計画が変わった場合、前の巡回経路が同じ時刻に補給できるとは限らない。
そこで補給時刻表を再構築し、必要なら巡回の一部を作り直す。
補給計画と巡回計画が相互に依存する点が、この世代の探索の中心である。

## 11. 在庫を含む評価例

店舗aの在庫を2、系列をXとする。
巡回車AとBが同じ日にaを通れば、玉数は2増える。
3台目も通ってもaの玉数は増えない。
しかし3台目の経路が系列Yの店舗も通るなら、その価値は残る。
`stock_layers` は在庫ごとのビット集合を使ってこの集計を速くする。

`mask_statistics` は候補全体の通過店舗を読む。
全期間で新しく得た系列を数える。
当日の系列を数える。
店舗ごとの訪問台数を在庫で切って玉数を数える。
局所的に良さそうな単車経路でも、他車と重なれば全体価値は下がる。
候補の更新では全車のマスクを合わせて見る。

`local_value` は当日系列へ1000を掛ける。
新規系列の重みは残り日数で変える。
残り1日なら100000、2日なら2000、それ以外は300である。
玉数には10を掛ける。
さらに日末の機動性と翌日の系列への近さを評価する。
最終日には新規系列を特に重視する設計である。

この係数は共通エンジンの正式順位そのものではない。
探索中に候補を素早く比べるための値である。
正式な車種配置や世代比較は実行結果を使う。
同じ当日系列数でも、未取得系列の有無と日末位置で候補の順位は変わる。

## 12. 巡回計画を組み立てる

巡回側には異なる規模の変更を行う探索がある。
個別の巡回を組む処理は、補給表を参照しながら店舗へ伸ばす。
複数車の計画を組み合わせる処理は、系列と在庫の重複を調整する。
既存候補の一部を壊して再構築する処理は、局所解から抜ける。
補給側の停車や経路を変える処理は、合流可能な領域そのものを変える。

`escort` は補給車と巡回車の同行に関わる候補を作る。
`tour` は訪問順を探る。
`joint` は複数車の組合せを扱う。
`window` は補給の時刻窓を扱う。
`route_set` は経路候補の集合を組み合わせる。
`patrol_first` は巡回側から先に候補を作る。
`circuit` は巡回経路の構築・改善を行う。
`tomorrow` は翌日の候補比較を担当する。
名前は処理の入口を見つける手掛かりであり、最終評価は `Candidate` にまとまる。

## 13. `Candidate` が表すもの

`Candidate.plan` は回答可能な全車の行動列である。
`Candidate.score` は探索用の評価値である。
`Candidate.masks` は取得店舗などの集合を保持する。
`Candidate.end` は候補の実行後に想定する車両状態である。
`Candidate.support` は補給車計画を保持する。

今日の候補を比べるときは `score` を使う。
翌日の見込みを比べるときは `end` から次のソルバを作る。
補給経路を直すときは `support` を変更し、
その影響が `plan` と `end` に反映された候補を評価する。
このまとまりがないと、得点と終点だけ異なる版を誤って組み合わせてしまう。

## 14. 翌日比較の実際

`tomorrow::retain` は当日候補を全て残すわけではない。
現在日で得た系列数が最大の候補を中心にする。
終点の異なる案を残し、最大6件程度に絞る。
明日へ進む前に当日の重要な取得を落とさないためである。

`tomorrow::choose` は各候補の `end` から翌日用 `Solver` を作る。
そこで補給と巡回を短時間探索する。
初日の次の交通は道路状態1を仮定する。
それより後は当日観測を予測に使う。
これは予測であり、次の実要求の交通ではない。

今日と明日の比較値は `current.score + 0.65 × future.score` である。
例えば今日の差が小さくても、終点が明日の未取得系列に近い案が選ばれ得る。
反対に、明日の予測が良くても今日の重要な系列を失う案は `retain` で残りにくい。
ここでの今日の終点は候補内部の状態である。
今日の全行動を共通エンジンで再生してから明日のソルバを作る手順ではない。
最終的に返す今日の計画は共通エンジンで合法性を確かめる。

## 15. 車種選択から日別回答まで

車種選択は主補給車を各車で試す。
各配置で初日の候補を作り、その評価値で補給車を選ぶ。
比較した配置を回答し、初期案を日別探索の種にする。
日別回答では観測位置・燃料・交通を取り込む。
残り時間の条件に合わせて補給と巡回を改善する。
4台以下で時間が十分なら翌日比較を加える。
選択した当日案を共通エンジンで検査する。

候補の評価と実際の行動列の判定は別段階である。
探索で高評価でも時刻規則に違反する案は回答できない。
エンジン検査が失敗したら待機計画へ戻す。
次の要求では前回採否を反映して観測へ同期する。
予測した翌日の案は固定せず、その日の実交通で作り直す。

## 16. 読み違えやすい点

補給車が近いだけでは補給できない。
時刻窓と補給前燃料が必要である。
経路表の重み付き距離は実時間ではない。
店舗への明示訪問がなくても、経路途中の通過で取得し得る。
在庫を超える重複訪問は玉数に寄与しない。
`tomorrow` の翌日得点は内部予測である。
`Candidate.end` は先読み用の候補終点である。
正式な次の日の状態は次要求の観測に合わせる。

保存版のテストは補給の時刻、経路費用、在庫計算などを確認する。
任意診断2件は既定では実行されない。
時間制限と予測交通のため、同じseedでも実行環境が変われば探索結果が変わり得る。
正式な強さは[検証記録](validation.md)にある実行結果で確認する。

## 17. 候補更新の小さな例

巡回車Aは店舗aを通り、巡回車Bは店舗bを通るとする。
両店舗が同じ系列なら、当日系列は1種類である。
aの在庫が1、bの在庫が2なら、玉数は最大3になる。
Bの経路を変えてaへも寄っても、aの在庫は既に使い切っている。
その変更だけでは玉数は増えない。
ただしBが途中で別系列の店舗cを通れば当日系列は増える。

単車の走行時間だけを見ると、Bの変更は遠回りかもしれない。
全車のマスクを合わせると、cの系列価値が分かる。
`mask_statistics` はこの全体集計に使う。
`stock_layers` は在庫上限を速く数える。
`local_value` は全体の系列、玉数、終点を比較する。
したがって局所的な最短経路が全体最良とは限らない。

## 18. 補給変更の波及

補給車がPで待つ時刻を短くすると、別の地点Qへ早く行ける。
Qで待つ巡回車には有利になる。
一方、Pへ遅れて着く巡回車は補給を受けられなくなるかもしれない。
その車は後半の燃料が不足する。
補給車の停車を一箇所だけ変えても、全車の合法性を見直す必要がある。

`Supply::build` は新しい時刻表を作る。
巡回の修復処理は新しい表で行動を作り直す。
`Candidate` には行動列と終点を一緒に保存する。
古い `end` と新しい `support` を混ぜない。
最終案は共通エンジンの実行規則に通す。

## 19. 今日と明日の点差

仮に当日A案の評価値が10000、B案が9900とする。
翌日の内部予測でA案が4000、B案が4300とする。
`tomorrow` の比較ではA案が `10000 + 0.65×4000 = 12600`。
B案は `9900 + 0.65×4300 = 12695` である。
この場合はB案が選ばれる。
これは計算方法を示す例であり、実際の得点や係数内訳ではない。

今日の重要な系列を落とした案は `retain` の段階で残りにくい。
残した候補の間で、明日の予測を65%の重みで使う。
翌日の予測交通は実観測とは限らない。
次要求では新しい観測で計画し直す。
この先読みは候補の `end` から始まる。
共通エンジンによる今日の再生を先に行う仕組みではない。

## 20. 状態と期限

車種選択と日別回答は時間予算が違う。
日別回答では要求時間の86%から60 msを引き、最低20 msを使う。
車種選択では要求時間の80%から100 msを引く。
翌日比較は車両数と残り時間の条件を満たす場合に限る。
どの処理も時間内で探索を打ち切る。
同じseedでも実行環境の負荷で候補数が変わる。

探索が早く止まっても、保存済みの合法な候補は使える。
最終の行動列は共通エンジンで検査する。
検査に失敗すれば待機計画へ切り替える。
次の要求では前回の採否と新しい観測に同期する。
先読みの結果を絶対的な未来状態として保持しない。

## 21. 数字と上限のまとめ

| 項目 | 値 | 意味 |
| --- | ---: | --- |
| 経路モード | 3 | 時間と燃料の折合い |
| 当日系列係数 | 1000 | `local_value` |
| 新規系列係数、残り1日 | 100000 | 最終日に強く重視 |
| 新規系列係数、残り2日 | 2000 | 終盤で重視 |
| 新規系列係数、それ以外 | 300 | 通常日の評価 |
| 玉数係数 | 10 | 在庫上限後の個数 |
| 翌日予測の重み | 0.65 | 今日と翌日の比較 |
| 翌日比較の当日候補 | 最大6件 | 探索量の制御 |
| 既定テスト | 18件成功 | 保存版で確認済み |
| 任意診断 | 2件無効化 | 通常テストには含めない |

上の係数は探索用の値である。
実際の順位は共通エンジンとテスタの成績で決まる。
上限値は候補を打ち切るための設定で、最適性の保証ではない。

## 22. 読むときの確認順

まず現在の交通で作った経路表を確認する。
次に補給車の時刻×セルの表を確認する。
巡回車が補給前燃料でそこへ行けるかを確かめる。
通過店舗と明示訪問の双方を取得へ反映する。
他車の訪問と店舗在庫を合わせて玉数を数える。
日末位置と燃料を `Candidate.end` で確かめる。
翌日比較が動いた場合は内部予測交通を確認する。
最終回答は共通エンジンの合法性結果で確かめる。

## 23. 用語の短い対照表

| 用語 | この実装で指すもの |
| --- | --- |
| `Network` | 端点と複数経路の前計算 |
| `SupportRoute` | 補給車の停車または直接行動 |
| `Supply` | 時刻とセルごとの補給可能性 |
| `stock_layers` | 店舗在庫を段階別に数える集合 |
| `masks` | 各車が通った店舗の集合 |
| `Candidate.plan` | 当日の全車の回答行動 |
| `Candidate.end` | 候補が想定する日末の車両状態 |
| `local_value` | 当日候補を比較する探索値 |
| `retain` | 翌日比較へ残す当日候補の選別 |
| `choose` | 内部の翌日予測を使った当日案の選択 |

補給車が近いことと補給可能であることは違う。
候補の終点は翌日予測へ渡す内部状態である。
翌日予測を行っても、返す行動列は当日分だけである。
実際の翌日には新しい観測から経路表を作り直す。
