# 第7世代ソルバの探索方法

[一覧](../algorithms.md#solver07) / [単一ファイル](../solver07.rs) / [設定](settings.md) / [検証](validation.md)

本実装は公開通信仕様と共通判定エンジンから作成した単一スレッドの第7世代正式昇格版v37です。相手ソルバの実装、過去世代の実装・設計資料は利用していません。正式昇格の結果は[検証記録](validation.md)に記載しています。

## 計画の表現

補給車を1台選び、当日の計画を探索します。開発比較用の第4引数を正に指定し、翌日があり回答時間が5秒以上なら、当日の有力案から翌日の計画も作って最終案を選びます。第4引数が0の既定動作では、店舗16以下・回答時間20秒以上・翌日がある場合に、後述の翌日の種類数を確認する比較を使います。それ以外は当日の探索へ時間を使います。開発比較用の環境変数で翌日重みを正に指定した場合は、別方式として翌日の計画も同時に変更する探索を使います。補給車には4箇所の立ち寄り先と出発時刻を与えます。候補位置には店舗・車両位置に加え、地図を5×5の領域へ分けて選んだ通行可能セルを用い、店舗間での待ち合わせも探索します。店舗数16以下かつ地図全体が256セル以下の場合は、全ての通行可能セルを補給地点候補とします。巡回経路上で提案した待ち合わせ位置を近くの格子点へ置き換えず、その位置を直接選択できます。それを超える盤面は従来の候補範囲を使います。巡回車には店舗と補給地点の訪問順を与えます。補給地点では、到着を待つか、補給車の出発まで待つかを選択できます。

当日は受信した交通状態を使用します。通常の翌日比較では当日計画を公開エンジンのコピーで実行し、自チームの当日と前日の道路滞在数を合計します。その半分を混雑・渋滞の閾値へ当てはめ、現在混雑・渋滞している道路は少なくとも混雑として予測します。全チームが同じ道路を使うとは限らないため、滞在数を縮小して過大な予測を抑えます。当日の複数候補を比較する予測には、当日探索の最良案を基準として共通の交通を使います。地点間には時間優先、時間と燃料の両立、燃料優先、途中店舗の経由を優先する4種類の経路を用意し、各移動の経路を選択します。店舗経由の経路は時間優先の辺コストから店舗通過分を小さく差し引き、同じ時間で回収箇所を増やせる道を選びやすくします。辺コストは正に保ちます。逆向きの最短路計算により、日の終了時に店舗間の任意のセルへ到達した場合も、翌日の計画を継続できます。

## 得点と補給

種類の重複と在庫上限を考慮し、日別種類を玉数より強く評価します。当日の終端で補給車に届く燃料が残るかを評価し、翌日の行動余地を確保します。翌日がある場合、終了位置から別の店舗へ移動するための最少燃料を残せない車に減点を加え、少量の燃料を残したまま数日間動けなくなる計画を避けます。必要量は地形の燃料消費から正確に求め、現在いる店舗を除いて比較します。前日までの採用計画から取得済み種類を記録し、2日目以降に未取得の種類が残っていれば強く優先します。試験用の到達性重みが正の場合は、各ブランドについて終了位置から最も早く到達できる巡回車を求めます。最短移動時間に必要燃料の不足分を加えた見積もりが翌日のステップ数の4分の1を超える場合、その超過を軽く減点します。ただし、この見積もりを加えた短縮試験は悪化したため、既定では無効にしています。同じ回収数・到達性なら移動・待機が短い計画を優先します。

補給車の位置を各ステップで再現し、巡回車の移動中・待機中の補給も計算します。燃料消費は移動が反映される直前、補給は移動後という公開規則の順序を守ります。途中までしか進めない移動は、巡回車・補給車とも実行できる命令までに切り詰めます。補給車は次の目的地へ到着できない日も途中まで進めます。巡回車の燃料が不足し、補給車が後で現在位置を通る場合は、補給を待って同じ経路の走行を再開する計画も評価します。

## 探索

初期解では、各店舗を訪問列へ挿入する位置を比較します。その後、焼きなましで挿入、削除、交換、区間反転、担当変更、日を跨ぐ訪問移動、補給地点・出発時刻の変更を行います。2台の訪問列の後半を交換する操作と、連続する複数の訪問を別の車へ移す操作も使い、関連する店舗の担当をまとめて変更します。巡回車が3台以上なら、3台の訪問列の後半、または各車1箇所の訪問を循環交換する操作も使います。3台すべての変更後に採否を決め、途中の担当変更で回収種類が一時的に減る組み替えも探索します。補給地点の変更と巡回車の待ち合わせを同時に提案する操作も用います。当日探索では車1～2台の訪問列を空から組み直すビーム探索も行い、逐次の交換では抜けにくい配置から改善します。ビーム内の状態には、訪問列の終了時刻と、その時点の燃料を保持します。日末まで待機すると後で補給される場合も、経路を延ばす時点の燃料として区別します。同じ訪問済み店舗・終了位置について、評価値・時刻・燃料のいずれも改善できない候補を除き、探索枠を別の経路に使います。ビームへ残す途中候補の順位には、店舗数が少ないほど弱めた終了時刻の減点を加え、少数の回収のために長い時間を使う経路への偏りを抑えます。完成候補の採用は元の得点・燃料評価で判断します。

実行できない訪問列の後半は定期的に除き、探索が未実行部分の変更に偏ることを避けます。2台分の訪問を部分的に取り除き、挿入探索で修復する操作を併用します。補給日程・開始状態・訪問列が一致する車両の評価は再利用します。途中で日を終えた補給車までの最少燃料距離は、必要になった地点について計算して保持します。翌日用計画の補給地点は実座標を保持して次の要求へ渡します。

公開モデルの上限である8台・256ステップに合わせ、評価時の車両状態と補給車の時刻別位置は固定長配列に保持します。焼きなましの次候補は確保済みの訪問列へ内容を書き戻し、採用時に現在案と作業領域を交換します。ビームの経路延長も同じ訪問列の容量を再利用し、評価式と近傍の種類を維持したまま、反復ごとのメモリ確保を減らします。

回答時間が2秒以上ある当日探索では、開始燃料が容量の3分の1未満で、補給車の開始位置まで自力で届かない車がいる場合、その車を最初に補給する日程を試します。補給車が日のステップ数の4分の3未満で到着できる車を対象にし、全巡回車の訪問列をまとめて空にしてビーム探索で再構築します。先に補給する車の経路を最初に組み、残りの車で未回収の種類・店舗を補います。全体を組み終えた値で採否を決めるため、補給日程だけを変えると一時的に得点を失う変更も試せます。通常の焼きなましと同じ温度で新しい配置へ移る一方、最良案は別に保持します。該当する低燃料車がいない場合は、既存の1～2台の探索を続けます。

焼きなましの冷却は探索時間を12区間に分けた経過率で進め、最良案への復帰もこの区間の境界に合わせます。途中で65536反復ごとに戻す方式から変更し、一度の冷却中は現在案を継続して変更します。常に別途保持する最良案を提出し、最後の20%は低温で改善します。経路再構築は通常の幅32を使います。

第4引数を正にした通常の計画要求では、探索時間の約75%を当日に使います。探索中の有力案を終了位置・燃料・新規取得種類で区別し、当日評価の高い最大24案を保持します。当日最良評価から120以内の候補から、終了状態の違いも考慮して最大8案を選びます。それぞれの終了位置と燃料から翌日の初期計画を作り、残り時間を等分して各巡回車のビーム探索で改善します。当日評価から終端燃料の近似評価を取り除いた値＋翌日評価×第4引数で比較し、採用した翌日計画を次の要求の初期候補へ渡します。翌日の交通は予測値なので、次の実要求では実際の交通を使って評価し直します。最終日、回答時間が短い場合、車種選択中には、この候補保存と再評価を行いません。


既定動作の小盤面では、翌日の種類数を確認するため、探索時間の80%を当日の探索へ使います。当日評価が最良から120以内で、当日最良案より種類数が少なくない候補から、終了位置と燃料の違いも考慮して最大4案を選びます。それぞれを公開エンジンのコピーで実行し、翌日の位置・燃料と候補ごとの交通予測を作ります。交通予測は車種選択や第4引数が正の比較と同じ係数0.5を使い、自チームの直近2日の道路滞在合計と混雑・渋滞閾値の2倍を比較します。現在の混雑・渋滞は少なくとも混雑として予測します。残り時間を等分し、補給日程も変更する通常の焼きなましとビーム探索で翌日を計画します。当日評価＋翌日に取れる種類数×1000で比べ、翌日の種類数が同じなら当日評価の高い案を選びます。翌日の玉数をこの比較値へ加えないため、翌日の玉数予測だけを理由に当日の案を替えることはありません。選んだ翌日計画の補給地点を座標で引き継ぎ、次の実要求では実際の交通と燃料から再評価して初期案にします。試算は同じスレッドで順次行い、その中でさらに翌日比較を呼び出すことはありません。

車種選択では全ての補給車候補を初期計画で比較します。各候補に700ms以上を配分できる場合は、補給車を固定して候補ごとに初日を独立して探索します。通常の当日探索を使い、候補あたり4000ms以上を確保できて3日以上ある場合は、時間の半分を初日へ割り当て、残りを2日目と3日目へ配分します。各日の採用計画を共通エンジンのコピーで実行し、終了位置と燃料、直近2日分の道路滞在を引き継ぎます。初日評価＋2日目評価×0.5＋3日目評価×0.25で補給役を選びます。候補あたり1000ms以上4000ms未満、または全体が2日なら、時間の約60%を初日へ割り当て、初日評価＋翌日評価×0.5で比較します。この試算では未取得種類への追加加点を無効にして、初日に取得しなかった種類が多い候補を誤って優先しないようにします。余裕が残れば選んだ候補の初日を追加探索します。時間が短い場合は初期比較の最良候補から先行探索し、補給車の担当も訪問列と一緒に交換します。開発比較用の翌日重みが正なら、従来の全道路を少なくとも混雑とする近似で翌日も同時に探索します。探索は内部単一スレッドです。

## 提出前の検証

提出計画を共通エンジンの状態コピーで実行します。各車の終了位置・燃料と、日別種類・玉数の増分を独自モデルと照合します。翌日比較で採用した計画も、当日を実行した後のコピーと同じ予測交通で照合します。共通エンジンが当日の計画を不正と判定した場合は待機計画へ置き換え、翌日の計画が不正なら翌日キャッシュを破棄し、診断を標準エラーに残します。前の回答が却下された場合は、待機計画を適用して内部履歴を同期します。

## 保存形式と出典

昇格時の設計資料を基に、保存先の案内と評価状況を更新しています。元の分割ソースは [main.rs](main.rs) と [solver/planner.rs](solver/planner.rs) に保持し、外部モジュールをインライン化した [単一ファイル版](../solver07.rs) を保存用Cargoのビルド対象にしています。出典と変換内容は [ソース対応表](../source-manifest.json)、昇格判断は [世代記録](../records/generation-007.md) を参照してください。
