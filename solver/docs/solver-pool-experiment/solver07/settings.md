# 第7世代ソルバの設定

[一覧](../algorithms.md#solver07) / [単一ファイル](../solver07.rs) / [設定](settings.md) / [検証](validation.md)

`cargo build --release --offline --manifest-path solver/docs/solver-pool-experiment/Cargo.toml --target-dir target --bin pool-solver-07` でルートの `main.rs` と `solver/planner.rs` をビルドします。実行ファイルは JSON Lines v1 の select / plan に対応します。

探索seedは第1引数に非負整数で指定します。省略時は0です。盤面の初期配置と組み合わせて乱数を初期化します。第2引数は翌日の到達性を評価する重みです。既定は0、許容範囲は0～20で、0ならこの評価を無効にします。第3引数は32店舗の場合のビーム途中候補の終了時刻への減点係数です。既定は2、許容範囲は0～20で、0なら追加の時間減点を無効にします。実際の係数は指定値×(店舗数/32)²で、既定値なら16店舗0.5、24店舗1.125、32店舗2です。

第4引数は当日候補の再評価に使う翌日評価の重みです。既定は0、許容範囲は0～1.5です。0なら玉数を含む旧方式の翌日比較を行わず、小盤面・長い回答時間では後述の種類数による比較を使います。`0 0 2 0.65` ならv25と同じ重みで候補再評価を有効にします。車種選択時の将来試算は第4引数に依存せず、候補ごとの予算と残り日数に応じて2日または3日を比較します。

```sh
target/release/pool-solver-07 0
```

各日の探索は要求の `timeLimitMs` の91%と、110msを残す時間の短い方を上限にします。通常の計画要求で第4引数が正、翌日があり、要求時間が5000ms以上なら、約75%を当日の探索へ使い、残りで候補ごとの翌日計画を比較します。車種選択でも残り時間を先行探索へ使います。候補1台あたり700ms以上を確保できれば全候補へ等分し、補給車を固定した独立探索で選択します。通常の当日探索で候補あたり4000ms以上かつ3日以上ある場合は、初日に50%を配分し、残り時間を2日目・3日目へ分けます。比較値は初日評価＋2日目評価×0.5＋3日目評価×0.25です。1000ms以上でこの条件を満たさない場合は初日に60%を配分し、初日評価＋翌日評価×0.5で比較します。各将来日の予算は残り時間から50msを引いて未実行の試算日数で割り、300ms未満ならそこで打ち切ります。標準出力は回答専用で、探索回数、モデル不一致、検証失敗は標準エラーへ出します。

主な現行定数は、補給車1台、立ち寄り先4箇所、当日探索と小盤面での翌日の種類数確認です。候補再評価を有効にした場合は当日候補を24案保存し、最大8案を翌日比較します。同時に2日を変更する旧比較方式と通常の候補再評価は、ともに翌日係数0を既定にしています。時間・燃料・途中店舗の経由を考慮した4経路を各区間で選択します。内部並列や分散処理は行いません。

評価用配列の上限は、公開共通モデルの検証条件と同じ車両8台・日内256ステップです。未使用の車両スロットは0で初期化し、提出計画の車両数は実際の台数に合わせます。候補生成とビーム拡張の訪問列は確保した容量を繰り返し使います。

当時の開発ビルド・試験はVOIDLINUX-3で実施し、正式昇格評価はVOIDLINUX-1で行いました。実行条件と結果は [検証記録](validation.md) に保持しています。

開発比較用に `PROCON37_G007_FUTURE_WEIGHT`（既定0、正の値で翌日の計画も評価）と `PROCON37_G007_RESERVE_WEIGHT`（既定15、終了時の燃料不足への重み）を指定できます。比較では値をラベルと実行記録に残します。正式評価は上書きせず既定値で行います。

当日だけを探索する場合は、既存の訪問列の局所変更に加え、幅32・最大20段のビーム探索で車1～2台の訪問列を再構築します。1回の再構築は1台で最大200ms、2台で合計最大400msとし、回答期限を優先します。

全巡回車の再構築は、要求時間2000ms以上、残り探索時間200ms超で、反復数を131072で割った余りが32768の時に候補条件を調べます。開始燃料が容量1/3未満、自力では補給車の開始位置へ届かず、補給車が日のステップ数の3/4未満で到着できる車がある場合だけ実行します。該当する1台を先に補給する日程にし、その車を最初に、残りの車を無作為の順で再構築します。1回最大400msを残り台数に等分します。その後の通常近傍でも改善を続けます。該当車がなければ既存の1～2台の探索を行います。試行・採用・最良更新・先行補給の回数は `fleet_calls` / `fleet_accepted` / `fleet_improved` / `fleet_rescues` に記録します。現行の全車再構築は全て先行補給を伴うため、`fleet_calls` と `fleet_rescues` は一致します。

game起動時に試験用環境変数を与えると、相手の保存識別情報も変わり、公式比較CUIは異なる実行条件として除外します。この方法の比較は設計の切り分け参考に留め、既定値を変更した候補は上書きなしで改めて評価します。

補給車の最終移動は日の残り時間で到達できる位置まで実行します。巡回車は燃料が不足していても、同じ日に補給車が現在位置を通過し、補給後に次の移動を終えられる場合には待機して再開します。

到達性の切り分けでは `target/release/pool-solver-07 0 0` や `target/release/pool-solver-07 0 6` のように対象だけの引数を使います。gameでは末尾を `-- 0 0` / `-- 0 6` とします。相手側の実行環境を変更しない方法ですが、比較時は公式CUIの同条件判定も確認します。正式評価では `-- 0` とし、第2～第4引数を上書きせず既定値を使います。

翌日がある場合の燃料評価は、補給車までの不足燃料×15と容量25%未満の不足燃料×2を減点します。別の店舗へ最少燃料経路でも到達できない場合は、さらに1600＋必要燃料の不足分×20を減点します。容量半分までの残燃料には1単位あたり0.2を加点します。最終日はこれらの終端燃料評価を使いません。

ビーム探索については、各回答の呼び出し回数と完了した探索段数の合計を標準エラーへ記録します。広い盤面で再構築が浅い段階で打ち切られていないかを診断するための値です。

焼きなましでは、従来の100種類分の選択割合に加え、16種類分を2台の訪問列の操作へ割り当てます。この操作は後半の相互交換と連続区間の移動を半々で選び、各車の訪問列は最大24要素に制限します。巡回車が3台以上なら、さらに8種類分を3台の循環交換へ割り当てます。全124種類分のうち8種類分、約6.45%です。3台の異なる巡回車を選び、各列を切った後半の循環交換と、各列1要素の循環交換を半々で提案します。後半交換は変更後の全列が24要素以下の場合だけ行い、1要素交換は3列とも空でない場合だけ行います。巡回車が3台未満なら従来の116種類分です。

`triple_calls` は3台操作を選んだ回数、`triple_accepted` はその提案を焼きなましで採用した回数、`triple_improved` はその直後に最良案を更新した回数です。長さ・空列の条件で変更できない場合も提案回数に含め、同点採用も数えます。同じ反復で待ち合わせ等の追加変更を伴う場合があるため、3台操作単独の効果を表す数値ではありません。

ビーム探索の状態整理では、日末の待機で補給される前の到着時燃料を使います。同じ訪問済み店舗と終了位置で、評価値が同等以上・到着が同時刻以前・燃料が同量以上の候補があれば、その状態を優先します。

ビーム内の候補順位は元の評価値−終了時刻×第3引数×(店舗数/32)²で求めます。提出する経路の選択と焼きなましの目的関数は、追加の時間減点を含まない元の評価値を使います。切り分けでは対象引数 `0 0 0` / `0 0 2` などをrun条件へ記録します。

第4の経路は、移動元セルの所要時間×100＋燃料消費×3から、移動元が店舗なら20を差し引く辺コストで計算します。店舗を経由しても回収できない場合や、遠回りの不利が大きい場合は、評価関数が他の経路を選べます。

車種選択と通常の候補再評価の翌日試算では、公開エンジンで当日を実行し、自チームの当日と前日の道路滞在数を合計します。合計を混雑・渋滞閾値の2倍と比較して状態を決め、受信した現在状態を最大1へ切り詰めた値を下限にします。通常の候補再評価では当日最良案を基準に共通の予測交通を作り、翌日グラフはその後で構築します。予測交通は実際の翌日交通との一致を保証するものではありません。車種候補ごとの初日・2日目・3日目・合成評価、試算した将来の日数と所要時間を標準エラーへ記録します。`forecast` は2日目、`forecast2` は3日目、`forecast_days` は試算を完了した将来の日数です。開発用の正の `PROCON37_G007_FUTURE_WEIGHT` では、従来の全道路を少なくとも混雑とする近似を維持します。

第4引数が正の場合の候補保存は4096反復ごとに行い、同じ新規取得種類・補給車終了位置・巡回車終了状態なら高評価の1案を残します。巡回車は区別せず終了位置と残燃料を並べ、燃料は4単位刻みで整理します。終了時には当日最良から120以内の候補を残し、残り時間220msにつき1案、最大8案を翌日比較へ回します。選出では当日評価差＋既に選んだ案との最短状態距離×2を使い、距離は車両ごとの座標差と燃料差/8の合計です。翌日探索は候補ごとの残り時間を等分し、1案1000ms超なら各巡回車のビーム探索を2巡、それ以下なら1巡行います。比較は当日評価−当日の終端燃料評価＋翌日評価×第4引数です。診断の `future_candidates` と `future_value` に比較件数と採用値を出し、当日・翌日のモデル照合には `current` / `forecast` を付記します。

焼きなましの温度は従来どおり、最初の80%では時間経過率を12倍した小数部を使って280から0.8へ冷却し、最後の20%では約2.48から0.08へ下げます。最良案への復帰は、その時間経過率を12倍した整数部が増えた時に行います。65536反復ごとの復帰は行いません。通常のビームは32768反復ごと、車1～2台の切り替えは65536反復ごとで維持します。`restart_calls` は各回答で最良案へ復帰した回数です。v30の幅128による追加探索は使いません。

既定の第4引数0・`PROCON37_G007_FUTURE_WEIGHT=0` では、通常の計画要求で店舗数16以下・要求時間20000ms以上・翌日ありの場合に、翌日に取れる種類数を確認します。探索予算の80%を当日へ使い、当日最良評価から120以内で当日の種類数を減らさない候補を最大4案比較します。候補の保持上限24案と4096反復ごとの保存、終了状態による多様性の選択は既存の処理を使います。残り700msにつき1案、最大4案に絞って残り時間を等分し、各案を実行した状態から翌日の通常探索を行います。試算の予算が200ms未満なら打ち切ります。

この比較値は当日評価＋翌日の種類数×1000です。翌日の未取得種類への追加加点は無効にして試算しますが、翌日探索自体は種類・玉数・燃料・終了時刻を通常どおり評価します。試算で採用した翌日計画を次の実要求へ渡し、実際の交通で再評価します。車種選択中・試算の内部・最終日にはこの比較を呼び出しません。第4引数が正なら従来の玉数を含む比較を使用します。

診断の `coverage_guard=1` はこの比較が有効な回答、`guard_base_brands` は当日最良案から試算した翌日の種類数、`guard_brands` は採用案から試算した種類数、`guard_changed=1` は当日最良案以外を選んだことを示します。`future_candidates` は比較を完了した案数です。試算用ソルバも同じスレッドで順次実行し、提出前の位置・燃料・得点照合を行います。


小盤面の翌日種類数確認も交通予測係数0.5を使い、整数で道路滞在合計と閾値×2を比較します。観測済みの現在状態を最大1へ切り詰めた値を予測の下限とします。v35で試した係数0.7はseed24で日別種類数が減ったため戻しました。追加の引数・環境変数はありません。


店舗数16以下かつ地図全体が256セル以下の場合、補給地点の候補を全通行可能セルへ広げます。この場合は全ての通行可能セルを出発点・目的地とする4種類の経路を事前計算します。それを超える盤面では、全通行可能セルを出発点とし、目的地は店舗・車両位置・引き継いだ補給地点・5×5領域の代表セルに制限します。いずれも立ち寄り先は4箇所です。診断の `graph_targets` / `graph_sources` はその回答で構築した当日グラフの目的地数／出発点数、`graph_ms` は当日グラフの構築時間です。翌日用グラフの構築時間はこの値に含めません。追加の引数・環境変数はありません。

## 保存版の起動と対戦設定

保存用のビルド対象は `pool-solver-07`、入口は [単一ファイル版](../solver07.rs) です。通信・引数・探索設定は元の分割ソースと同じです。[当時の正式評価設定](../records/generation-007-config.json)には実行時のパスと対戦相手を保存しています。現在の起動手順は [再現手順](../reproduction.md) を参照してください。保存形式の整理では追加ビルド・追加テストを行っていません。
