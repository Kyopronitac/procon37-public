# 第2世代の探索アルゴリズム

[一覧](../algorithms.md#solver02) / [単一ファイル](../solver02.rs) / [設定](settings.md) / [検証](validation.md)

第2世代は、巡回車の訪問順と移動する補給車との合流順を同時に変える。
各車の区間経路を時間・燃料の3モードから選び、複数日を試走して車種を決める。
設計と正式な結果は[世代記録](../records/generation-002.md)に対応する。

## 1. 通信と試合状態

入口は1プロセスで車種選択と各日の要求を受ける。
`Optimizer` は乱数、複数日探索の深さ、前回探索した候補を保持する。
入口側は `Game` と前回の回答を保存し、次の要求では採否を反映して内部ゲームを1日進める。
その後に観測された車両状態と交通へ合わせる。
採用した計画を回答する前に、複製した `Game` で合法性を検査する。

## 2. 経路の表現

`Network` は店舗、車両の初期位置、地図上に間引いて選ぶ合流候補セルを端点にする。
幅16以下では細かく、それより大きい地図では4セル間隔を目安に候補を採る。
各端点から3モードのDijkstra法を実行する。
移動元セルの時間を `t`、燃料を `f` とした辺重みは `12t+f`、`8t+5f`、`3t+9f`。
通過店舗の集合、時間、燃料、方向列を経路へ保存する。

巡回車の `Route` は店舗の端点列、区間ごとのモード、補給を挟む位置、任意の合流端点と合流へ向かうモードを持つ。
`Solution` は全巡回車の `Route` と、補給車ごとに担当する巡回車の順序 `orders` を持つ。
補給車の経路は、この順序と各巡回車の合流地点から決まる。

## 3. 合流を含む候補の評価

`Context::stats` は各巡回車を補給前と補給後に分け、区間時間、区間燃料、通過店舗、合流地点、終点を計算する。
`Context::evaluate` は補給車の担当順に合流地点を巡り、補給車到着と巡回車到着の遅い方を合流時刻とする。
到着後の待機を巡回車側へ加え、補給後の燃料を容量まで戻す。
開始時刻0の即時補給は許さず、時刻1以降にそろえる。

時間超過、補給前の燃料不足、補給後の燃料不足を `excess` に合算する。
訪問集合から当日の系列と店舗別の玉数を数え、在庫数で上限を掛ける。
探索用評価は未取得系列 `6000`、日別系列 `1000`、玉数 `10` を軸に、超過への罰則 `1200×excess` を引く。
翌日が残るときは日末燃料を少し加点し、補給車の終点へ届きにくい巡回車を減点する。
実行可能な候補は `excess == 0` で判定する。

候補評価は端点間の集計であり、全行動を毎回エンジン実行する処理ではない。
選択した候補だけを `Context::compile` が方向と待機の命令列へ変換する。

## 4. 複数日の焼きなまし

`Optimizer::solve` は空の訪問列から始め、前回の `carry` や車種選択時の `initial` があれば種として使う。
探索深さは残り日数と `planning_depth` の短い方。
候補を各日順に評価し、位置・燃料・取得系列を翌日へ引き継ぐ。
新規系列を重視し、翌日の得点には小さな割引を掛け、時間・燃料違反へ罰則を付ける。

`mutate` は訪問の挿入・削除・置換・順序変更、経路モード、補給位置と合流端点、補給車の担当順を変更する。
温度を下げながら悪化候補も確率的に受け入れ、一定周期で空候補または最良候補から再開する。
探索中には違反を含む候補を経由できるが、回答用の `best` は実行可能なものだけで更新する。
最後に初日の計画を出し、複数日の候補を次要求へ保持する。

## 5. 車種選択

各車を補給車1台とする配置を列挙する。
4台以下では2日探索も比較する。
6台以上で初日の燃料が少ない場合は補給車2台、1台だけの問題や十分な燃料の問題では補給車なしも候補に含む。
各配置を全日程試走し、`Game` の種類数・日別種類数・玉数を辞書順で比較する。
初日の候補と採用した探索深さを日別要求へ引き継ぐ。

日別探索の上限は要求時間の90%か52秒の短い方。
車種選択には要求時間の80%を候補数と日数に配分する。
詳細は[実行設定](settings.md)。

## 合流と違反量の計算例

巡回車の経路は補給記号の前後で区切る。
例えば巡回車が「店舗A → 合流P → 店舗B」、補給車が別の合流を経由してPへ来る場合、巡回車の `prefix_time` と補給車のP到着時刻の遅い方で合流する。
巡回車の遅延 `delay` はこの差である。
合流前に必要な燃料はその時点の残燃料から差し引き、満タン化は合流が成立した後に行う。

```text
合流時刻 = max(巡回車の合流前到着, 補給車の到着, 1)
巡回車の遅延 = 合流時刻 − 巡回車の合流前到着
補給前の残燃料 = 開始燃料 − prefix_fuel
補給後の残燃料 = 燃料上限 − suffix_fuel
```

時間超過と燃料不足は `excess` に足す。
補給車の最終合流が日末を超えた分、巡回車の最終時刻が日末を超えた分、補給前または後で燃料が負になった分が対象。
`valid` は合計が0である場合に限る。
実際の命令列では `compile` が補給車と巡回車の両方に移動方向と待機を出力し、日末まで待機する。

## 近傍操作の内訳

`mutate` は1回に1つの構造変更を行う。
訪問の挿入・削除・置換、同じ車の2店舗の交換と反転、別車への移動と交換、2台の後半列の入れ替えがある。
補給については巡回車の補給位置、合流端点、合流へ向かう経路モード、補給車が担当する巡回車の順序を変える。
近くの端点を選び直す操作もある。

訪問を別車へ移す場合、両車の列に同じ店舗を重複させない条件を確認する。
補給位置は訪問列の挿入・削除によってずれるため、同じ意味を保つようインデックスを調整する。
こうした変更で巡回車と補給車の計画を同時に動かす点が、この世代の中心となる。

## 複数日探索の評価順

`solve` は各日の `Solution` をまとめて候補とする。
ある日の終点位置と燃料は次の日の `Context::evaluate` に渡し、新しく取得した系列は次の日の `seen` に加える。
日別系列と玉数の近似値には翌日0.97の割引を掛ける。
最終日末には燃料と位置の価値も加える。

探索中の現在解には違反候補が残り得るが、返す `best` は全日が実行可能で、評価値が改善した場合だけ更新する。
一定周期で空の候補と保存した最良候補から交互に再出発する。
探索を跨いで保持する `carry` は次の要求時に先頭日を落として使うため、前回の長期予測を固定するのではなく新しい観測で再評価する。

## 実際の得点との関係

車種選択の配置比較は、各配置を共通エンジンで全日程実行した `Game.score` の辞書順で行う。
一方、日別焼きなましの受理判定は近似評価値を使う。
したがって、近似評価の小さな差が常に正式得点や対戦順位を改善するとは限らない。
正式な昇格判定は[検証記録](validation.md)の30件による。

## 経路表の作り方と使用範囲

経路表の端点には全店舗を先に置き、初期位置がまだ含まれていない車両を追加する。
さらに地図上の格子点を合流候補として足す。
格子点が水域の場合は隣接する通行可能セルを使う。
`spacing` は地図幅16以下なら1、それ以外なら4であり、全マスを常に端点にする構成ではない。
巡回車の店舗訪問先は店舗端点で、補給地点には追加端点も選べる。

各端点を始点に3通りのDijkstra法を行い、終点までの親辺を逆にたどって経路を復元する。
経路に含む時間と燃料は重み付き距離そのものではなく、元の地形と道路状態から足した実量である。
移動元セルでコストを払うので、同じ2地点の往復で時間や燃料が同じとは限らない。
海・水域のセルへ入る辺は除外する。

端点ごとの近傍12点も時間優先経路で並べて保持する。
合流地点を少し動かす近傍では、この表から近い候補を選び、完全な無作為変更だけに頼らない。

## `RouteStats` と補給時刻

1巡回車の訪問列に含まれる合流は高々1箇所として、`stats` は補給前の時間・燃料、補給後の時間・燃料を分けて数える。
通過店舗のビット集合も同じ走査で集める。
補給地点が訪問列の途中で明示的に指定される場合、そこへ向かう経路の時間と燃料も補給前へ含める。
合流の後は燃料容量から後半の必要燃料を引く。

補給車ごとの `orders` は担当巡回車の順番を表す。
例えば同じ補給車にAとBを割り当て、Aの合流が先なら、補給車はまずAの合流地点に到着し、Aを待ち、次にBへ向かう。
`delays[a]` はAが補給車を待った分で、巡回車の最終時刻に加える。
補給車の最終時刻も当日の制限を超えれば `excess` に加える。

時刻0に同じセルで両車が始まる場合でも、合流時刻は最低1とする。
燃料がない巡回車について、合流地点へ移動するための燃料を合流後の燃料で前借りしてはならない。
保存版のテストはこの境界を直接確認している。

## 目的値の各項

探索用の `objective` は新規系列 `6000`、当日系列 `1000`、玉数 `10` を合計する。
`score` には別の整数係数 `100000`、`1000`、`10` を使い、車種選択や複数日試走の比較で種類数を強く優先する。
`value` からは `1200×excess` を引くため、時間や燃料を少し超える候補も順位付けできる。
実行可能候補の保存条件は点数と独立し、`excess == 0` を必須にする。

翌日があるときの `fuelbonus` は残燃料を少し加点し、日末位置から最寄りの補給車終点へ戻る燃料が足りない場合に強く減点する。
終点が店舗なら翌日にその系列を取りやすい小さな加点もある。
余った時間は同点に近い候補の弱い優先条件としてのみ使う。
これらの補正は当日の玉数を置き換えるものではなく、将来の行動余地を区別するためにある。

## 探索の初期化と再利用

`solve` は補給車の担当順を巡回車に均等に割り当て、各巡回車を空訪問列にした初期候補を作る。
保存済みの複数日候補 `carry` があれば先頭日を取り除き、残りを新しい日の種にする。
前回の候補が1日しかなければ巡回順を逆にして種にする経路もある。
車種選択が保存した `initial` は初日から使う。

この再利用は回答を丸ごと固定する処理ではない。
新しい日の道路状態、燃料、取得済み系列で改めて評価し、焼きなましに投入する。
候補の中には不正なものや前日と条件が異なるものも生じ得るため、最良候補の条件は全日程で実行可能であることとする。

## 車種選択の候補数と時間配分

車種選択では、補給車の位置ごとに1日探索を基本候補とする。
4台以下の各配置では2日探索も試す。
6台以上で初日の燃料上限が短い日程に対して厳しければ、向かい合う2台を補給車とする候補を追加する。
1台問題や全日程に十分な燃料上限を持つ問題では、補給車なしも候補とする。
候補数が増えた場合は一候補・一日あたりの探索時間が短くなる。

各候補は全日程の共通エンジン試走で比較される。
途中で不正な日別行動が出た場合は待機でその日を進める。
最終的に `unique_brands`、`daily_brands`、`udon` を辞書順で比べ、最良配置を返す。
日別探索では実時間の上限が別にあるため、車種選択での予測得点と本番日別回答の得点が同じとは限らない。

## 要求ごとのデータの流れ

```text
車種選択
  候補の車種配置を列挙
  → 配置ごとに Game を初期化
  → 各日で solve、回答を Game へ適用
  → 全日程の実得点を比較
  → 採用配置と初日の探索種を保存

日別回答
  前回回答の採否を内部 Game へ反映
  → 観測車両・交通を設定
  → 現在日と必要なら次の日の Solution を探索
  → 初日の Solution を命令列へ変換
  → Game の複製で合法性を検査して回答
```

この流れで車種選択時の `Game` は未来予測用、日別回答時の `Game` は観測と同期する内部状態という役割を持つ。
選択時の試走で得た補給車配置は変えないが、訪問列は毎日の観測に合わせて探索し直す。

## 実装上の境界

端点間の経路は3つの重みから選ぶため、地図の全ての経路を網羅するわけではない。
補給は巡回車ごとに高々1回の分割として `RouteStats` を集計する。
合流場所は端点表の範囲であり、実行時には端点間の方向列へ展開する。
探索中に計算した燃料・時刻は近似集計なので、回答を返す前の `Game::play_day` が最終的な合法性検査となる。

テスト3件は、時刻1の補給、補給地点へ行く燃料の前借りをしないこと、観測変更後の中間セルIDを扱うことを対象にしている。
全問題での性能や最適性を保証するテストではない。
正式な30件の結果は[検証記録](validation.md)にある。

## 7. まず二種類の順番を区別する

この世代には「巡回車が店舗を回る順番」と「補給車が巡回車に会う順番」がある。
巡回車Aが店舗1、合流P、店舗2を通る順番は `Route` が持つ。
補給車がAに会ってからBに会う順番は `orders` が持つ。
片方だけを変えても、もう片方との時刻が合わなくなることがある。
そのため `Solution` は両方をまとめて評価する。

補給車を固定拠点とみなす場合と違い、合流場所ごとの移動時間が必要になる。
補給車が先に着けば、巡回車を待てる。
巡回車が先に着けば、巡回車が待つ。
待機時間は後続の店舗訪問を減らす可能性がある。
合流を増やすだけで必ず得点が上がるわけではない。

### 訪問列と経路の違い

`Route.nodes` は通りたい店舗端点の列である。
隣り合う端点間をどの道で走るかは `modes` が選ぶ。
道中に別の店舗を通る場合、その店舗も取得の候補になる。
訪問列にない店舗を通過するため、端点列だけでは得点が決まらない。
経路表には方向列と通過店舗集合を一緒に保存する。

`refill_index` は訪問列のどの位置で補給を挟むかを表す。
`refill_node` は合流セルを表す。
`refill_mode` はそのセルへ向かう区間の経路モードである。
補給がない経路では前後分割を使わない。
補給のある経路では `stats` が燃料を前半と後半へ分ける。

## 8. 合流時刻を手計算する

仮に巡回車Aが時刻8にPへ着き、補給車が時刻11にPへ着く。
合流は時刻11であり、Aは3時刻待つ。
Aの後半区間が5時刻なら、少なくとも時刻16まで行動する。
日末が時刻15なら1時刻の超過を計上する。
この例では、Pを変えるか補給車の順序を変える必要がある。

別の巡回車Bが補給車の次の訪問先なら、Bの合流時刻も変わる。
Aへの到着が遅いほどBへの出発が遅くなる。
したがってAの経路変更がBの可否に波及する。
全車をまとめた `Context::evaluate` が必要な理由である。

燃料については前半と後半で基準が違う。
前半は開始燃料から消費する。
後半は合流が成立した後の燃料容量から消費する。
例えば開始燃料5でPまで6必要なら、Pで補給する予定でも前半が不可能である。
この不足1は `excess` に加える。
後半で容量を1超える場合も同じく不足1を加える。

時刻0の同位置合流には特別な境界がある。
`evaluate` は合流時刻を最低1にする。
時刻0の即時回復を見込んで前半の燃料不足を隠さない。
この境界は保存版テストで検査されている。

## 9. 違反を許す探索と、返せる候補

探索中の `value` は、時間超過や燃料不足を `excess` として罰する。
小さな違反案にも数値を与えられるので、その周辺を探索できる。
例えば合流場所を一度遠くへずらし、次に補給車の担当順を変えると改善する場合がある。
最初の変更だけでは違反が出ても、二つ目の変更で解消する余地がある。

ただし回答候補の `valid` は `excess == 0` を必要とする。
焼きなましの現在案と保存する最良案を分けている。
現在案が高い `value` でも違反があれば回答に使わない。
最良案が更新されるのは、全日程で実行可能かつ評価値が改善した場合である。
さらに回答直前に共通エンジンで命令列を検査する。

ここには三段階の判断がある。
第一に `stats` による端点間の時刻・燃料集計。
第二に `evaluate` による全車と全日程の候補比較。
第三に `Game::play_day` による実際の行動列の合法性確認。
探索の高速化のため、全候補を第三段階まで実行するわけではない。

## 10. 近傍で何を直すか

店舗挿入は、余った時間と燃料を得点へ変える操作である。
店舗削除は、遅い車や燃料不足の車を実行可能へ戻す操作である。
同じ車の交換は、移動距離と通過店舗を変える。
列の反転は、複数店舗の順番をまとめて変える。
別車への移動は、時間の余る車へ仕事を渡す。
別車との交換は、両車の終点と燃料を同時に変える。

合流地点の変更は、巡回車と補給車の移動時間を同時に変える。
補給位置の変更は、満タン化の前後に属する店舗を変える。
経路モードの変更は、訪問順を保ちながら時間と燃料を調整する。
`orders` の変更は、補給車の移動順と巡回車の待ち時間を変える。
このうちどれか一種類だけでは全ての制約を直せない。

訪問列へ店舗を入れると、補給位置の添字がずれる。
削除でも同じ問題が起こる。
近傍操作は補給位置を補正し、意図しない前後分割を避ける。
候補の意味を保ったうえで `evaluate` に渡す。

## 11. 複数日を読む順序

`planning_depth` は今から何日分の `Solution` を一度に考えるかを決める。
残り日数より深くはしない。
1日目の終点位置は2日目の出発位置になる。
1日目の残燃料は2日目の開始燃料になる。
1日目に新たに取得した系列は、2日目には「既取得」として扱う。

例えば同じ系列の店舗が二日とも近くにある場合を考える。
初日に取れば全期間系列が増える。
翌日に再取得すると、翌日系列と玉数の価値はある。
しかし全期間系列を二度増やすことはできない。
複数日評価ではこの違いを `seen` の引継ぎで表す。

日別値の先の日には0.97の割引を掛ける。
遠い日の交通や行動の予測を今日と同じ確かさで扱わないためである。
それでも将来の燃料と位置を見れば、今日の高得点だけを追う案を避けられる。
翌日の実要求では交通が更新されるので、保存した候補を再評価する。
`carry` は再利用する初期案であり、確定した翌日回答ではない。

## 12. 車種選択と日別回答の評価を分ける

車種選択では補給車にする車を固定する必要がある。
単独補給車候補を列挙し、条件により2台または0台も試す。
各候補は全日程を共通エンジンで試走する。
最後に全期間系列、日別系列、玉数を辞書順で比較する。
初日の計画がよくても、残り日程の成績が悪ければ選ばれない。

一方の日別探索は、限られた時間で `value` を改善する。
日別 `value` の係数は正式得点の辞書順比較とは違う。
超過への罰則、残燃料の補正も含む。
同じ「得点」という言葉でも、比較対象と目的が異なる。
結果を読むときは `score`、`value`、共通エンジンの実得点を区別する。

補給車なしの案では、補給へ回す車を巡回に使える。
十分な燃料がある問題なら有利な場合がある。
燃料が足りない問題では、店舗の近くまで走っても帰路で止まる可能性がある。
2台補給では巡回車が減る代わりに合流機会が増える。
条件付き列挙は、この損得を実際の全日程試走で比べるためのものだ。

## 13. 実装を追うためのチェック表

まず `Network` の端点を調べる。
地図幅で合流地点の密度が変わる。
次に3モードの経路で時間・燃料がどう違うかを見る。
`Route` の店舗順と補給位置を確認する。
補給車の `orders` と各合流セルを確認する。
巡回車の前半燃料を開始燃料と比べる。
補給車到着と巡回車到着の遅い方を合流時刻にする。
後半燃料を容量と比べる。
両車の日末時刻を確認する。
最後に店舗在庫上限を適用して系列と玉数を数える。

時刻や燃料が近似評価では足りているのに回答が待機になる場合、
`compile` の行動列と `Game::play_day` の結果を調べる。
複数日案と翌日の実回答が違う場合、
観測交通の更新と `carry` の再評価を確認する。
探索seedが同じでも実時間予算のため反復数は変わり得る。
ここに書いた評価の流れはアルゴリズムの説明であり、
正式な順位や全問題での最適性の保証ではない。

## 14. 候補一件の計算を追う

`Context::stats` は巡回車ごとに経路を展開する。
補給前の区間時間を足す。
補給前の区間燃料を足す。
補給後の区間時間と燃料を別に足す。
経路の途中で通った店舗を集合へ入れる。
合流セルと最後のセルを記録する。

`evaluate` は補給車ごとに `orders` を左から読む。
次の合流セルまで補給車を進める。
巡回車の前半到着と補給車の到着を比べる。
遅い方を合流時刻にする。
巡回車が待った分を後半の完了時刻へ足す。
補給後の燃料を容量から数える。
補給車の次の担当へ進む。

全担当が終わったら、各車の日末時刻を調べる。
補給前後の燃料不足を調べる。
これらを `excess` にまとめる。
各店舗の訪問台数を在庫で切る。
通過した系列の和集合を数える。
既取得系列を除いて新規系列を数える。
日末燃料と補給車終点への近さを弱く補正する。

### 小さな二車例

巡回車Aは補給前に燃料4を使い、開始燃料5である。
補給後に燃料3を使い、容量6である。
この部分は燃料不足を起こさない。
巡回車Bは補給前に燃料7を使い、開始燃料5である。
Bの不足2は、合流予定があっても違反量へ入る。
Bの合流地点を近くするか、補給前の経路モードを変える必要がある。

補給車がAへ時刻6に着き、Bへ時刻12に着くとする。
Aが時刻4に着いたなら2待つ。
Bが時刻14に着いたなら補給車が2待つ。
その後の完了時刻が日末を超えれば、さらに違反量へ入る。
この例でBをAより先に担当すると、両車の待ち時間が変わる。
`orders` の変更が得点と可否へ影響する理由である。

## 15. 探索値と実得点の対応

| 値 | 計算対象 | 主な用途 |
| --- | --- | --- |
| `value` | 端点集計、違反罰則、日末補正 | 焼きなましの候補比較 |
| `valid` | 超過と不足がゼロか | 回答候補の保存条件 |
| `score` | 系列と玉数の整数重み | 候補の順位付け |
| `Game.score` | 実行後の全日程 | 車種配置の最終比較 |

これらを一つの数値として扱わない。
`value` が高くても `valid` が偽なら回答候補ではない。
`valid` が真でも、全日程の実得点では別候補に負け得る。
翌日の観測交通が違えば、今日の予測値も変わる。
正式な成績は実行したゲームの結果である。

## 16. 時間予算の効果

車種選択は複数の補給車配置を比べる。
配置ごとに全日程を試すため、候補数が増えるほど一候補の時間は短い。
4台以下なら2日深さの候補も加わる。
6台以上で燃料が厳しいと2台補給も加わる。
補給車なしの候補も条件により加わる。

日別回答では要求時間の90%と52秒の短い方が上限になる。
時間内で焼きなましの反復を続ける。
同じseedでもCPU負荷で反復数は異なる。
そのため回答の完全な再現にはseedだけでなく実行条件も関わる。
保存版の設定値は[設定](settings.md)にまとめてある。

## 17. 調査時に見る境界

合流を時刻0に置いていないか。
合流前に燃料が負になっていないか。
合流後の区間燃料が容量を超えていないか。
補給車の担当順が行動列と一致するか。
巡回車の待機が日末時刻へ入っているか。
補給車自身の日末時刻も制限内か。
経路途中の店舗取得を数えたか。
同一店舗の玉数を在庫で切ったか。
翌日へ位置、燃料、既取得系列を渡したか。
観測変更後のセルIDを新しい経路表へ対応させたか。

近似評価だけで判断に迷う場合は、
`compile` した行動列を共通エンジンで実行する。
回答直前の検査と、正式runの採点はその実行規則に基づく。

## 18. 用語の短い対照表

| 用語 | この実装で指すもの |
| --- | --- |
| 端点 | 店舗、車両位置、間引いた合流候補 |
| `Route.nodes` | 巡回車が狙う店舗端点の列 |
| `modes` | 端点間の経路の選び方 |
| `refill_index` | 巡回列のどこで補給するか |
| `refill_node` | 補給車と会う端点 |
| `orders` | 補給車が担当車に会う順序 |
| `RouteStats` | 巡回車の補給前後の集計 |
| `excess` | 時刻超過と燃料不足の合計 |
| `carry` | 次の要求へ持ち越す探索の種 |
| `compile` | 端点計画から方向・待機への変換 |

「合流位置」と「合流順」は別の変数である。
「補給前燃料」と「補給後燃料」も別に数える。
探索用の違反量を持つ候補は、そのまま実行しない。
共通エンジンで検査した行動列が最終回答になる。
