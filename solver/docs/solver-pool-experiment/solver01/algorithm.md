# 第1世代の探索アルゴリズム

[一覧](../algorithms.md#solver01) / [単一ファイル](../solver01.rs) / [設定](settings.md) / [検証](validation.md)

第1世代は、車種と巡回・補給を一つの `Genome` として持つ。
補給車の拠点を時間帯ごとに動かし、巡回車の訪問列と経路を探索する。
保存版の `context` が用意する経路表は当日分だけなので、実際の入口では当日計画を最適化し、日末の状態から翌日以降の動きやすさを概算する。
ここでいう「予測」は保存時の実装に含まれる将来日の概算であり、正式成績は[世代記録](../records/generation-001.md)の実行結果を参照する。

## 1. 要求と内部状態

入口はJSON Linesの `select` と日別計画要求を処理する。
`Solver` は問題、乱数、共通エンジンの `Game`、前回の `Genome`、保留中の回答、取得済み店舗のビット集合を保持する。
日別要求では前回回答の採否に従って内部ゲームを進め、観測された車両位置・燃料・道路状態で上書きしてから再探索する。

`select` は補給車の種類を返し、`plan` は移動方向と負の待機時間からなる各車の行動列を返す。
探索が作った行動列は出力前に `Game::play_day` で検査し、不正なら全車待機の計画に切り替える。

## 2. 計画の表現

| 要素 | `Genome` 内での意味 |
| --- | --- |
| `supplier`・`secondary` | 主補給車と、条件により使う2台目。車両数と同じ値は2台目なしを表す |
| `hubs`・`late_hubs`・`last_hubs` | 各日の主補給車の拠点 |
| `switches`・`last_switches` | 時間帯を切り替える時刻 |
| `secondary_hubs`・`secondary_switches` | 2台目の補給車の拠点と切替時刻 |
| `routes[d][i]` | 日 `d` の巡回車 `i` の訪問先列。店舗と補給地点を同じ列に表す |
| `variant[d][i]`・`reserve[d][i]` | 区間経路の既定モードと翌日へ残す燃料の強さ |

`Context` は現在の車両状態、日ごとの経路表、取得済み系列、補給地点、燃料余力の評価表を用意する。
訪問列は実際の移動方向列ではなく、評価時に端点間経路へ展開する。
補給地点は時刻付きの滞在区間となり、巡回車はその区間に到着できるときだけ補給を受ける。

通常は補給車1台。
7台以上、短い日程、初日の燃料条件などを満たす一部の問題では2台目も候補にする。
5台以下では店舗に隣接する通行可能セルを補給拠点候補へ追加する。

## 3. 経路の前計算と将来の交通

`roads` は店舗、車両位置、補給拠点を端点としてDijkstra法で3種類の区間経路を前計算する。
移動元セルの時間を `t`、燃料を `f`、地図セル数を `V` とすると、辺重みは次のとおり。

| モード | 辺重み | 主な用途 |
| --- | --- | --- |
| 0 | `10000t + 1` | 時間優先 |
| 1 | `10000t + 10000f + 1` | 時間と燃料の両立 |
| 2 | `10000t + (4V+1)×10000f + 1` | 燃料を強く優先 |

経路表には時間・燃料・通過店舗と系列の集合・移動方向列を保存する。
日別要求の当日は観測交通を使用する。
`roads` には将来日向けの `forecast` 分岐もあるが、保存版の `context` は `forecast=false` の当日表だけを作る。
実観測が届く次の要求では経路表を作り直す。
重み付き距離と実際の移動時間を混同せず、行動の時間と燃料は経路に保存した値で評価する。

## 4. 補給と複数日の評価

`support_intervals` と `refill_intervals` は補給車が拠点を移動・待機する時間帯を計算する。
`evaluate` は `Context.roads` にある日を順に進めるが、現在の入口でその長さは1である。
巡回車は訪問列に従い、到着時刻・区間燃料・通過店舗を更新する。
指定した補給地点へ燃料内で到達し、補給区間内に時刻を合わせられる場合は燃料を満タンに戻す。
到達できない訪問は採用しない。

翌日が残る場合、店舗から次の補給拠点までの必要燃料を訪問の余力として見込む。
最終日でなければ終点の燃料と補給車までの距離を評価し、未取得系列へ近づける位置も好む。
各日の店舗ごとの訪問台数は在庫数で頭打ちにして玉数を数える。

評価値は「未取得を含む全期間の種類数」「日別種類数」「玉数」「終点の機動性」からなる。
日別種類数と玉数には先の日ほど小さくなる `0.8^d` の重みを掛ける構造だが、保存版の通常経路では当日分のみなので指数は0である。
最後の日は種類数の重みを高くする。
この値は探索用の近似指標であり、正式な順位合計そのものではない。

## 5. 車種選択と日別の探索

車種選択は主補給車の位置、必要なら2台目の位置を候補にし、各候補へ貪欲な初期訪問列を作る。
`optimize` は現在の `Context` が持つ当日分の `Genome` を評価し、最良の車種配置を返す。
その初期計画は日別要求の種にもなる。

`optimize` の前半は焼きなましで、訪問の挿入・削除・交換・反転・車両間移動、補給拠点と切替時刻、経路モード、燃料余力を変える。
160反復ごとに修復候補を試し、温度を下げながら最良解を保持する。
探索時間の約78%をこの段階に使い、残りは `beam_rebuild` で巡回車の訪問列を再構築する。
前回 `Genome` がある日は先頭日を除く処理を持つが、通常は要素が1日だけなので、その形を種として再評価する。

探索上限は `HORIZON_SEARCH_MS` と要求時間の78%で決まる。
既定上限は車種選択100秒、日別48秒。
詳しくは[実行設定](settings.md)を参照。

## 補給区間の時刻計算

各補給車は1日に最大3つの拠点を巡る。
`support_intervals` は前の拠点から経路モード0で移動した到着時刻を求め、切替割合をその日のステップ数へ掛けた時刻まで待機する。
次の拠点へ出発できない場合は、最後に到達した拠点で日末まで留まる。
巡回車が実際に補給を受けられる時間帯は `refill_intervals` で得る。

補給車は移動命令を出した直後に次のセルへ現れるわけではない。
移動元セルに残る時刻を `departure` から計算し、出発拠点の補給可能区間を延長する。
これにより「補給車が予約した移動の途中で、元セルにいる巡回車が補給を受ける」という境界を表現する。

巡回車の訪問列で補給記号に達すると、現在地から拠点までの時間と燃料を見積もる。
到着時刻と区間開始の遅い方、かつ時刻1以上を合流時刻にする。
合流時刻が区間終了、日末、移動可能燃料のいずれかを超える場合はその補給を採用しない。
補給した場合はそこまでの通過店舗を記録し、燃料を容量へ戻す。
単に補給拠点を通過した場合も、時刻が区間内なら回復する。

## 状態と得点

候補評価のループは日ごとに位置・燃料・取得済み店舗を更新する形だが、現在の入口では当日1回だけ回る。
店舗が経路の途中にある場合も取得集合へ加える。
店舗の玉数はその日に訪れた巡回車数と在庫数の小さい方を数える。

```text
日別系列 = その日に通過した店舗の系列の種類数
全期間系列 = これまで取得済みの系列と候補期間で取得する系列の和集合
玉数 = Σ日 Σ店舗 min(その日の訪問巡回車数, 店舗在庫)
```

`Evaluation.value` の中心は `全期間系列 × 5000 + Σ日 0.8^日差 × 日別系列 × 30000 + Σ日 0.8^日差 × 玉数 × 10`。
試合の最終日だけ全期間系列の係数を100万に上げる。
翌日以降の日程が残る場合は、終点の燃料余力と補給車への必要燃料、まだ取得していない系列への距離から機動性を補正する。
探索の重みは実際の対戦順位とは別である。

## ビーム再構築の枝刈り

`beam_rebuild` は1台の巡回車と1日を選び、他車の訪問集合と在庫消費を固定して、その車だけを作り直す。
状態は端点、時刻、燃料、訪問店舗集合、訪問列と優先値を持つ。
次の店舗か補給区間へ3モードで進め、時間・燃料・補給可能時刻を満たす子だけを作る。

優先値は他車がまだ取っていない系列、まだ在庫が残る店舗、残り時間、残燃料を使う。
同じ訪問集合と終点で、より早く到着し燃料も多い状態があれば劣る状態を捨てる。
各層で最大192状態を残し、上位40状態は全体の `evaluate` でも比較する。
局所的な高得点が全体の燃料や翌日を悪化させる可能性があるため、最終採用は全体評価値で決める。

## 設計上の制約

経路は3つの事前計算モードから選ぶ。
補給地点は `fixed_hubs` が列挙した端点に限り、全ての通行可能セルを自由な合流地点として探索するわけではない。
評価は実時間で打ち切るため、同じ探索seedでもCPU負荷により焼きなまし回数が変わる。
回答の合法性は最後に共通エンジンで確認する。

保存した入口 [entry.rs](entry.rs) と [horizon.rs](horizon.rs) をインライン化した [solver01.rs](../solver01.rs) がビルド対象。

## 7. 一度の要求を追う

以下は、日別回答でどのデータがどこへ渡るかを読むための順序である。
具体的な店舗名や座標は問題ごとに異なる。

1. 入口が観測と前回回答の採否を読む。
2. 前回の保留回答があれば、採用時はその回答を内部 `Game` に適用する。
3. 不採用なら全車待機を内部 `Game` に適用する。
4. その実行で発生した店舗取得イベントを `seen` に反映する。
5. 観測に含まれる車両位置・燃料・道路状態で内部状態を更新する。
6. `context` が現在位置を端点に加え、当日の経路表を作る。
7. 端点と燃料から翌日の機動性表を作る。
8. 以前の `Genome` を探索の初期候補にする。
9. `optimize` が初期候補を評価し、改善する。
10. 最良候補から当日の各車の行動を得る。
11. 複製した `Game` で行動を実行して合法性を確かめる。
12. 不正なら待機計画を回答する。
13. 採用した回答を `pending` に保持する。

手順2〜4は、前回回答が本当に採用されたかに内部記憶を合わせるために必要である。
手順5は、内部の試走結果より観測を優先する。
したがって前日の予測交通が今日の経路表に残り続けることはない。

### 当日だけを最適化する意味

`Genome` の配列には日を表す添字がある。
しかし配列の長さを決める `days` は `c.roads.len()` である。
`context` は `rs = vec![today]` としている。
そのため通常の車種選択も日別回答も、明日の経路を明示的には探索しない。
過去に検討した複数日用の型や関数が残っていても、入口からの実際の探索範囲を広げるわけではない。

明日の価値は `mobility_table` の終点評価で表す。
これは明日の予定行動列ではない。
次の要求が来たら、今日の終点と観測交通から新しい当日計画を作る。
「翌日まで見ている」と読むときは、この概算と明示的な翌日試走を区別する必要がある。

## 8. 端点と経路表を読む

経路探索は地図上の全セルから毎回始めるわけではない。
まず店舗セルと補給候補セルを `fixed_hubs` にまとめる。
現在の車両位置がまだ含まれていなければ、そこも端点に追加する。
補給拠点を表せる範囲は `hub_count` より前の端点である。
車両位置として追加した端点が、そのまま新しい拠点候補になるわけではない。

店舗は訪問先と通過時の取得対象を兼ねる。
補給候補は巡回車と補給車の合流場所になる。
車両位置は経路探索の出発点になる。
同じセルが複数の役割を持つ場合は端点を重複させない。

各端点対について3種類の経路を保存する。
重みの違いは、時間を多少使って燃料を節約する道を候補に残すためである。
モード0は時間を強く見る。
モード1は時間と燃料を合わせて見る。
モード2は燃料を非常に強く見る。

例えば、短いが燃料を多く使う道と遠回りでも燃料を節約する道があるとする。
出発時の燃料が十分なら短い道が有利になりやすい。
補給地点の手前で燃料が足りない場合は、遠回りの経路で訪問を成立させられる。
どのモードを選んでも、実行可能性の判定には保存した実時間と実燃料を用いる。
重み付き距離を燃料や時刻として解釈してはいけない。

経路は移動元セルのコストを積む。
道路状態が方向で同じでも、往路と復路の移動元セルが違えば費用は異なり得る。
店舗を経由した場合は、訪問列にその店舗を明記していなくても取得候補になる。
このため、訪問列だけを読んで得点を数えることはできない。

## 9. `Genome` を具体的に読む

`supplier` は主補給車の車両番号である。
`secondary` が車両数と等しければ2台目は使わない。
`is_supplier` は両方を検査し、該当車には巡回列の変更を適用しない。
`hubs`、`late_hubs`、`last_hubs` は主補給車の前半・中盤・後半の拠点を表す。
`switches` と `last_switches` はその境目を表す。
2台目には別の拠点列と切替時刻がある。

巡回車の `routes[d][i]` は整数の列である。
店舗番号の範囲に入る値はその店舗への訪問を表す。
補給記号は補給車との合流を表す。
経路表の端点番号そのものを方向として出力することはない。
評価・出力時に各訪問間の `Roads` の経路へ展開する。

`variant` は端点間移動の既定モードを変える。
`reserve` は翌日に残したい燃料の強さを変える。
この2項目は店舗の順番を変えずに走り方や終点の評価を変える。
同じ訪問列でも補給地点や経路モードが変われば、実行できるかどうかが変わる。

補給車を2台使う条件は限定されている。
単純に車両数が多いだけでは2台にならない。
残り日数、燃料容量、日別ステップ数の条件も `use_two_supplies` で判定する。
補給車を増やすと巡回車が1台減るので、得点上の利点がある場合だけ候補にする設計である。

## 10. 補給を時刻で追う例

例として巡回車が時刻4に合流地点へ着き、補給車の補給可能区間が時刻6〜10だとする。
巡回車は時刻6まで待つ。
合流後に燃料を容量まで戻し、次の店舗への移動を始める。
区間外の時刻11に着いたなら、その合流は成立しない。
地点へ着くための燃料がない場合も成立しない。

逆に、補給車が時刻4まで元の拠点で待ち、移動命令を出したとしても、
移動の処理中に元セルへ残る時刻があり得る。
`refill_intervals` はその時刻まで出発地での補給を許す。
これは「停車区間の終端」と「ゲーム内で車両がセルを離れる時刻」の差を埋める。

評価では補給を成功した後に次の区間の燃料を計算する。
補給地点までの燃料を、未来の満タン状態から先取りしない。
移動途中に補給地点を通過しても、時刻とセルが一致すれば補給を適用する。
明示的な補給記号と自動的な通過補給の両方を理解すると、候補の燃料推移を追いやすい。

補給区間は時刻付きなので、合流地点が近いだけでは十分でない。
巡回車が早すぎれば待機で時間を失う。
遅すぎれば補給機会を逃す。
補給車が複数の拠点を巡る場合、先の拠点への移動時間も切替時刻に影響する。
したがって拠点と切替時刻は巡回順と一緒に探索する。

## 11. 得点の各項を分ける

`unique` は既取得集合 `seen` と当日候補の和集合に含まれる系列数である。
同じ系列の別店舗を回っても、全期間系列は一つしか増えない。
`daily` は当日取得した系列数である。
既取得系列でも当日にもう一度取れば、当日系列には入る。
`udon` は店舗ごとの在庫を上限にした訪問台数の合計である。

例えば在庫2の店舗を3台が通る場合、玉数への寄与は2である。
3台目の通過は、同じ系列だけを狙うなら玉数上の価値がない。
一方、その経路が別の店舗も通るなら別の価値があり得る。
このため他車の通過集合を見ずに単車の経路だけ採点すると過大評価になる。

通常日の `unique` 係数は5000である。
当日系列の係数は30000である。
玉数の係数は10である。
最終日は `unique` の係数を1000000へ上げる。
これらは探索候補の順位付け用である。
テスタが返す得点と係数が一致するわけではない。

翌日が残る場合は日末燃料と位置を評価する。
燃料だけが多くても、補給車や未取得系列から遠い終点は有利とは限らない。
`mobility_table` は端点と残燃料の組を入力にし、翌日の時間内に届く系列数などを見る。
5台以下では複数店舗を回るのに必要な燃料の概算も加える。
この表は今日の訪問を少し犠牲にしても明日の選択肢を残すための補正である。

## 12. 初期案から改善まで

初期案は補給車の候補を列挙して作る。
各候補で巡回車からの平均的な距離が小さい拠点を選ぶ。
2台目があれば、その初期位置に近い拠点を置く。
`greedy` が店舗や補給の訪問記号を入れ、評価が良い案を探索の出発点にする。

焼きなましは現在案を少し変更して評価する。
改善なら採用しやすい。
悪化でも温度が高い序盤は確率的に採用する。
局所的に良い訪問順から抜け出すためである。
温度は経過時間に応じて大きく下がる。
終了間際は悪化をほぼ許さない。

近傍は店舗の挿入、削除、置換、交換、反転、車両間移動を含む。
補給拠点と切替時刻も変える。
経路モードと燃料余力も変える。
変更後の候補は毎回 `evaluate` で比較する。
修復近傍は160反復ごとに、巡回列の一部を取り除いて入れ直す。
小さな1回の入替えでは到達しにくい構造を作るためである。

最後の `beam_rebuild` は選んだ1台の訪問列を広く作り直す。
他車の取得済み店舗と在庫消費を固定する。
候補状態には位置、時刻、燃料、訪問集合を持たせる。
次に取れる店舗や補給を展開する。
同じ訪問集合と終点で、より遅く燃料も少ない状態は残さない。
各層の上限192で探索量を制御する。
上位40件を全車の `evaluate` に掛ける。
単車の局所優先値だけで最終案を決めない。

## 13. 確認するときの観点

出力された方向列を見るときは、まず補給車の位置と時刻を追う。
次に巡回車が補給前の燃料で合流地点へ着けるかを見る。
さらに合流が補給可能区間内かを見る。
店舗の取得は明示的訪問と通過取得の両方を数える。
同一店舗へ複数車が行ったら、玉数は在庫で切る。

`Genome` の評価値と正式得点が違う場合は、
終点補正や探索用係数を含むかどうかを確認する。
予測が翌日まで及んでいるように見える場合は、
明示的な翌日の経路ではなく `mobility_table` の補正であることを確認する。
補給の境界時刻で違いが出た場合は `refill_intervals` を見る。
最後に実行可否は `Game::play_day` の結果で判断する。

保存版は時間制限付き探索である。
同じ問題でも実行環境の負荷により候補を調べた数は変わる。
ここに書いた評価式は意図と実装の読み方を説明するもので、
最適解や正式runと同一の行動を保証するものではない。

## 14. 一つの候補を評価する順序

以下は `evaluate` を読むときの概念的な順序である。
実装では高速化のため、いくつかの計算をまとめている。

```text
入力: 現在位置と燃料、取得済み集合、Genome
補給車ごとに拠点の滞在区間を作る
巡回車ごとに現在位置、時刻、燃料を置く
訪問列を左から右へ読む
  店舗なら選んだ経路モードで移動する
  補給記号なら合流可能な区間と時刻を調べる
  経路上を通った店舗も記録する
  補給成立なら燃料を容量へ戻す
日末の系列数と玉数を計算する
翌日があるなら終点の機動性を加える
出力が必要なときは方向と待機の列へ展開する
```

訪問列を読む途中では、次の一手が成立するとは限らない。
燃料不足、日末超過、補給時刻の不一致があれば採用を止める。
候補の列に記号があるだけで、その訪問が得点に入るわけではない。
移動中に通った店舗は取得の候補として残る。
最終的には全車の訪問集合を合わせて在庫上限を適用する。

### 状態の最小例

巡回車の開始状態を「端点A、時刻0、燃料9」とする。
Aから店舗Bへの経路が時刻4、燃料3を使う。
Bへ着いた後の状態は「B、時刻4、燃料6」である。
その経路の途中に店舗Cがあれば、Cも取得集合へ入る。
次に合流地点Pへ時刻3、燃料4で向かうなら、
Pでの補給前状態は「P、時刻7、燃料2」である。
Pの補給可能区間が時刻8からなら、1時刻待つ。
補給後の燃料は容量へ戻る。
そこから先の経路は補給後の容量で判定する。

この例でPへ向かう経路が燃料7を使うなら、
Bで燃料6しか残っていないので合流は成立しない。
Pで満タンになる予定を使って不足1を帳消しにできない。
またPの区間が時刻6で終わる場合は、
時刻7着の巡回車は補給できない。
合流は位置、時刻、補給前燃料の三条件を満たす必要がある。

## 15. 車種選択を読む順序

車種選択時には全車を一度巡回車として初期化する。
各車両の初期位置と燃料上限を `context` に渡す。
候補の補給車番号を変えながら初期 `Genome` を作る。
2台目を使う条件なら番号の組も列挙する。
補給車にした車は店舗巡回の候補から除く。
巡回車の初期訪問列を `greedy` で埋める。
探索値で良い `Genome` を選ぶ。
選ばれた番号を車種の配列として返す。

ここでの選択評価は当日分の `Context` を使う。
翌日の全行動をエンジンで試走して全期間成績を比べる処理ではない。
翌日の影響は、当日終点の機動性表へ入る。
この違いは第2世代以降の全日程試走と比較する際に重要である。

補給車が少なければ巡回車は多い。
その代わり、遠い店舗を回ると燃料切れを起こしやすい。
補給車が多ければ合流機会は増える。
その代わり店舗を取る巡回車は少なくなる。
候補列挙はこの関係を問題の初期位置と道路で評価する。

## 16. 翌日の機動性表

`mobility_table[pos][f]` は日末端点と残燃料を引く表である。
翌日がなければ将来補正は要らない。
翌日があるときは、その日のステップ数を時間の目安にする。
各系列について、端点から届く店舗があるかを調べる。
届くための必要燃料の最小値を系列ごとに記録する。
残燃料 `f` で届く系列数を数える。

巡回車一台あたりに取りたい系列数の目標も置く。
届く系列が目標より少なければ減点する。
5台以下では、複数店舗を続けて回るための燃料見積りを加える。
近い一店舗だけでなく、その先へ続けられるかを見るためである。
孤立しやすい終点には追加の減点がある。
残燃料が多ければ小さく加点する。

この表は今日の日末状態を比べるための近似である。
補給車の明日の詳細な走行は作っていない。
翌日の道路状態は観測されていない。
今日と同じ経路表を用いた概算なので、
翌日の正式な行動可否と同一視しない。
次の要求では、観測された交通で新しい表を作る。

## 17. ビームの枝刈りを例で見る

同じ店舗集合を取って同じ端点Pへ着く状態AとBがある。
Aは時刻10、燃料8である。
Bは時刻12、燃料6である。
以後の選択肢はAの方が少なくとも同程度に広い。
このときBを捨てられる。
これは同じ集合と終点を比べるときに限る。

終点が違う場合は、時刻と燃料だけで優劣を決められない。
未取得系列に近い終点が有利なことがある。
訪問集合が違えば、同じ系列数でも玉数や次の店舗候補が違う。
そのためキーに訪問集合と位置を含める。
ビーム幅192は計算量を抑える上限である。
すべての可能な訪問列を残すわけではない。

優先値は子状態を広げる順番を決める。
最終採用には全車評価を使う。
例えば単車が店舗aを取ると局所的には得点が高くても、
別車がすでにaの在庫を使い切っていれば全体の玉数は増えない。
上位40状態を `evaluate` へ戻すのは、
その重複と日末の機動性を含めて比較するためである。

## 18. 実装上の数字をまとめる

| 項目 | 保存版の値 | 役割 |
| --- | ---: | --- |
| 経路モード | 3 | 時間と燃料の折合いを変える |
| 補給拠点の段階 | 最大3 | 一日の補給車の滞在場所 |
| 修復近傍の周期 | 160反復 | 訪問列を部分的に組み直す |
| 焼きなましの時間割合 | 78% | 多様な候補を探索する |
| ビーム幅 | 192 | 各層に残す状態数 |
| 全体評価する上位状態 | 40 | 単車の候補を全車で比べる |
| 車種選択の既定上限 | 100秒 | 環境変数で変更可能 |
| 日別探索の既定上限 | 48秒 | 要求時間でも制限する |

これらの値は実装に固定された探索設定である。
値を変えると計算量と候補の広さが変わる。
正式なスコアやゲームのルール値ではない。
要求時間の上限が短ければ、表の既定上限より先に探索が終わる。

## 19. 保存したソースの対応

`entry.rs` は通信とJSONの処理を受け持つ。
`horizon.rs` は車種選択と日別探索を受け持つ。
`solver01.rs` は両者を単一ファイルへ展開した保存版である。
この文書で挙げた `Solver::context` は `horizon.rs` にある。
`Genome`、`evaluate`、`optimize` も同じファイルにある。
実装を確認するときは、まず `context` で探索日数を確認する。
次に `evaluate` と `optimize` の日数の使い方を読む。
最後に `plan` のエンジン検査を読むと、回答まで追える。

## 20. 用語の短い対照表

| 用語 | この実装で指すもの |
| --- | --- |
| 端点 | 店舗、補給候補、現在の車両位置を表すセル |
| 区間経路 | 二つの端点の間の方向列と時間・燃料 |
| 訪問列 | 店舗番号と補給記号を並べた探索用の列 |
| 拠点 | 補給車が待つ端点 |
| 切替時刻 | 補給車が次の拠点へ移る目安 |
| 補給可能区間 | 巡回車が同じセルで燃料を戻せる時刻 |
| `seen` | 以前の実行で取得した店舗の集合 |
| `brand_masks` | 同一系列の店舗をまとめた集合 |
| `mobility_table` | 日末位置・燃料から翌日を概算する表 |
| `Evaluation` | 候補の近似評価と出力計画 |
| `pending` | 次要求で採否を確認する前回回答 |

この表で「端点」は地図全セルのことではない。
「訪問列」はそのまま送信する行動でもない。
「補給可能区間」は距離だけで決まらない。
「翌日の概算」は翌日の明示計画でもない。
これらを区別すると、探索値と実行結果の差を追いやすい。
