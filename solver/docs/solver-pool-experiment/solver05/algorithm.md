# 第5世代の探索アルゴリズム

[一覧](../algorithms.md#solver05) / [単一ファイル](../solver05.rs) / [設定](settings.md) / [検証](validation.md)

第5世代は、補給車の時刻表を作って巡回車ごとのビーム探索を行い、複数車の経路を焼きなましで共同改善する。
車種選択では全日程の試走を行い、日別回答では問題条件に応じて翌日の試走や2日共同改善も行う。
候補8で追加した燃料優先の経路が昇格版の特徴である。

## 1. 通信と状態の維持

`main` はJSON Linesで車種選択と日別要求を処理する。
探索seedは第1引数で、未指定なら0。
`Planner` は取得済み店舗、乱数、車種選択時の初日案、翌日用の経路ヒントを保持する。
日別要求が来るたび、前回回答が不採用なら待機計画を使って内部 `Game` を進め、その後に観測された車両位置・燃料・交通を設定する。

探索期限は要求時間から40 msを引いた値の97%で、通信と検証の時間を残す。
選んだ日別計画は `Game::play_day` で検査し、不正なら待機計画へ切り替える。

## 2. 経路表と端点

`Network` は店舗と車両位置のほか、地図を3×3に分けて選んだ通行可能セルを合流候補にする。
道路状態から移動元セルの時間 `t` と燃料 `f` を計算し、`10t + wf` を辺重みとするDijkstra法で経路を前計算する。

| モード | 燃料重み `w` | 役割 |
| --- | ---: | --- |
| 0 | 0 | 時間優先 |
| 1 | 5 | 時間と燃料の両立 |
| 2 | 22 | 燃料節約を強める |
| 3 | `地図セル数×40+1` | 燃料を最優先する |

通常の日別計画で車両数が4台なら4モード、その他は3モードを作る。
車種選択では `with_variants(..., 3)` を使う。
端点対ごとに方向列、通過セル、実時間、実燃料を保存し、探索中は同じ区間の最短路を計算し直さない。
`route_anchors` は実行済み経路から必要な中間端点を復元し、2日共同改善で同じ位置を両日の経路表へ登録する。

## 3. 候補と補給の表現

| 構造 | 内容 |
| --- | --- |
| `Route` | 1台の方向・待機行動、訪問店舗集合、日末燃料と終点 |
| `Solution` | 全車の経路、補給車の停車計画、必要なら直接の補給行動、評価値 |
| `Stop` | 補給車の停車端点と待機時間 |
| `Schedule` | 時刻×セルの補給可否、補給可能区間、補給車の終点 |
| `Waypoint` | 改善探索で使う端点、そこまでの待機、区間経路モード |

`make_schedule` は補給車の停車計画から、`raw_schedule` は直接の行動列から時刻表を作る。
巡回車の経路評価はその時刻表に沿って燃料回復を適用する。
`exact_support` は巡回経路に合わせて補給車の行動を再探索し、`reschedule_route` は補給車が変わった後に巡回車の行動を時刻合わせする。

## 4. 巡回車のビーム探索

`patrol_route` は現在位置・時刻・燃料・訪問集合・経路モードを含む状態を広げる。
店舗への移動、経路上で通過した店舗、補給車との合流、日末の残燃料を評価する。
車両数が4台以下の日別探索では基本ビーム幅120、その他では90を使い、車種選択時はより小さい幅で全日程を試走する。

`optimize` は補給車の停車位置・待機時間を変えながら巡回車を順に作る。
巡回車の順序を変えたり、一部だけ作り直したりして、他車の訪問済み店舗と在庫消費を反映する。
`pack_routes` は車両別の経路候補をビームで組み合わせる。
探索後には補給車の直接行動を改善し、巡回車を再時刻合わせする。

## 5. 評価と局所改善

`solution_value` は新規系列、当日系列、在庫上限を適用した玉数を大きな順序付きの重みで評価する。
翌日がある場合だけ、燃料余力、補給車への到達性、終点の店舗密度、翌日の配置を補正する。
日別探索中の近傍比較には `fleet_score` を使い、採用候補の更新では `solution_value` を再確認する。

`polish_fleet` と `soft_polish_fleet` は `Waypoint` の列を使い、店舗の挿入・削除・移動・反転、経路モードの変更、巡回車間の交換、補給車の停車変更を試す。
温度付きで悪化候補も受け入れ、合法な最良行動列を別に保存する。
`soft_polish_fleet` は時間・燃料違反のある中間案も罰則付きで通し、複数編集が必要な改善を探す。
実際に返す候補は違反がないものへ戻す。

## 6. 車種選択

`Planner::select` は各車を補給車1台にした配置を候補にする。
全日程の燃料が十分な条件では補給車なしも加える。
各配置の全日程を `Game::play_day` で試走し、種類数・日別種類数・玉数の順に重み付けした値で比較する。
探索時間に合わせて試走回数と局所改善の反復数を調整する。
5台以下では採用配置の初日案を `opening` に保存し、最初の日別回答で再利用する。

車種選択用の `Network` は3モード。
昇格版で追加した第4モードは車両4台の日別計画側だけに使うため、選択段階の候補数は変わらない。

## 7. 翌日試走と2日共同改善

`Planner::plan` は燃料と残り日数によって分岐する。
5台以下で燃料が厳しい場合、当日案と翌日案を先に作り、`two_day_polish` で2日分の巡回・補給を共同変更する。
現在日の取得系列を落とさない制約を持ち、翌日の位置と燃料も変わるたびに再評価する。
翌日案は位置付きのヒントとして保持する。

別の条件では当日の複数案をアーカイブに残し、共通エンジンで1日進めてから翌日を探索する。
翌日の交通は当日の観測と試走結果から保守的に作る。
2日で得る系列と玉数に加え、さらに日程が残るときは燃料余力を少し評価する。
期限や燃料条件が満たされない場合は当日の最良案を使う。

## ビーム探索の状態と補給時刻

`patrol_route` の `State` は端点、時刻、燃料、訪問店舗のビット集合、利得、親状態、経路モード、待機時間を持つ。
端点間を移動するときは `Network` の経路を用い、移動中に通過した店舗も訪問集合へ加える。
`Schedule` は時刻×セルの真偽値を持ち、補給車がその時刻にいるセルへ巡回車が到達した場合だけ燃料を回復する。

`terminal` は日末の得点に加え、残燃料と補給車への距離を評価する。
探索中には同じ系列を複数台で取る価値を抑えるため、既に構築した巡回経路の店舗数と系列集合を次の巡回車へ渡す。
`patrol_route` は時間・燃料を満たす行動列を返し、残り時間は待機行動で埋める。

## 探索の2段階

`optimize` の前半は、補給車の停車候補を変更しながら巡回車を順にビーム探索する。
補給地点は無作為な変更だけでなく、良い巡回経路の終点や合流候補からも作る。
一部の巡回車だけを再構築する反復、複数巡回経路を組み合わせる反復、補給車の直接行動を作り直す反復がある。

後半は `soft_polish_fleet` または `polish_fleet` が車両全体の `Waypoint` を変更する。
店舗の挿入・削除・順序変更、車両間の店舗交換と後半交換、経路モード、補給車の停車地点と待機時間を試す。
候補の受理には温度と近似値を使い、最良候補の更新には `solution_value` を使う。
悪化候補や一時的な違反を経由しても、返す行動列は合法な最良候補から選ぶ。

`rebuild_neighborhood` は一部の巡回車から訪問を落とし、経路増分の小さい挿入位置を優先して未訪問店舗を追加する。
これを仕上げ段階へ差し込み、局所的な訪問順だけでは得られない組合せを探す。

## 得点と残燃料の優先関係

`solution_value` は当日に新しく得る系列へ1000000、当日系列へ100000、玉数へ1000の係数を掛ける。
翌日が残る場合だけ、終点の燃料、補給車からの救援可能性、店舗密度、翌日配置の価値を補正する。
これは探索の選好であり、正式な対戦順位はテスタが決める。

`fleet_score` は局所変更のたびに使う高速な値で、温度に応じて系列への重みを変える。
近似値が良くても `solution_value` が最良候補を下回る場合には、保存する最良を入れ替えない。
補給車の経路変更後は巡回車の行動を再時刻合わせし、合法性を保つ。

## 2日共同改善と通常の翌日試走

燃料が厳しい5台以下の問題では、まず当日を探索して共通エンジンで1日進める。
翌日の巡回・補給候補を作り、`two_day_polish` で両日の `Waypoint` を同時に変える。
今日の訪問の一部を翌日に移す、翌日の先頭を今日へ動かす、車両を入れ替えるといった操作を含む。
どちらかの日の時間や燃料に違反がある候補は罰則で評価するが、保存する最良は両日とも実行可能で、現在日の取得系列を落とさないものに限る。

通常の翌日試走は、当日の最良だけでなくアーカイブした終点の異なる候補を比べる。
候補ごとに `Game::play_day` を実行し、翌日用の交通を設定して短い探索を行う。
2日分の新規系列、日別系列、玉数の増分と、まだ日程が残るときの燃料余力を使って当日候補を選び直す。

## 限界と再現性

4番目の経路モードは4台の日別計画にだけ加わる。
車種選択は3モードのままで、選択段階と当日計画段階の探索は同じではない。
すべて実時間の期限で打ち切るため、探索seedを固定しても計算機負荷が変われば反復回数や回答が変わり得る。
第5世代の単一ファイル版は保存した分割ソースをインライン化したもので、正式評価run当時の実行ファイルとバイト単位で同一であるとは主張しない。

## 経路表の付加情報

`Network` は単なる最短経路表ではない。
店舗セルから系列IDを圧縮したビット集合を作り、経路上で訪れた店舗を高速に系列集合へ変換する。
5台以下ではセルから端点番号を直接引く表と、8ビット単位の系列集合参照表を作る。
探索中に同じ店舗集合を何度も評価するための高速化である。

各端点について、近い店舗がどの程度集まるかを表す密度と、終点から次の訪問に必要な燃料の目安も計算する。
`route_anchors` は行動列を調べて端点間の経路として表現できる区切りを求め、共同先読みで日をまたいだ行動の位置関係を保持する。

## 補給計画から巡回経路への依存

補給車の停車地点と待機時間を先に決めると、巡回車がいつどのセルで燃料を受け取れるかが決まる。
`make_schedule` はその占有時刻表を作る。
巡回車のビーム探索はこの表を参照し、補給前に燃料が足りる区間だけを広げる。
補給車側の行動を局所変更した場合、以前の巡回車の行動をそのまま使うと補給時刻がずれることがあるため、`raw_schedule` と `reschedule_route` で再評価する。

巡回車の行動は方向と待機の列で保存する。
一方、焼きなましでは `Waypoint` の列を使い、端点や経路モードをまとめて変更する。
`route_from_points` はこれを実行可能な方向列へ戻す。
`faithful_points` は既存の行動列をできるだけ同じ時刻・位置で再現するための表現で、2日共同改善の初期案に使う。

## 車両別探索と全車探索の役割

`patrol_route` は1台だけを見るときに速く、補給時刻表と既訪問集合から有望な経路を選ぶ。
ただし全車の玉数は店舗在庫で共有されるため、車ごとの最良を単純に並べても全体最良とは限らない。
`pack_routes` は各巡回車の候補をビームで組み合わせ、重複訪問と系列集合を全車で数え直す。
`polish_fleet` はその結果へ車両間の訪問移動や後半交換を加える。

`soft_polish_fleet` は時間超過と燃料不足を一時的な罰則として保持できる。
例えば1台から別車へ店舗を移すには、先に片方の時間が超える中間案を通ることがある。
探索中はその状態を試せるが、保存する最良は再構築された合法な行動列に限る。
近似的な温度付き受理と、厳密な最良候補の更新を分ける理由はここにある。

## 車種選択の全日程試走

車種選択では各車を補給車にした案を作り、全日を `optimize` と `Game::play_day` で進める。
試走の時間は問題の日数、日別ステップ数、要求時間から決め、1配置に費やせる反復数を調整する。
失敗した日別行動は待機で進めるため、試走が止まらない。
最終比較は `unique_brands`、`daily_brands`、`udon` の順序を重視する大きな係数で行い、5台以下では最良配置の初日案を実回答へ渡す。

燃料上限が全日程に十分大きい場合だけ全車巡回の案も候補になる。
昇格時に重要だった4番目の燃料優先経路は4台の日別計画へ加わり、車種選択は3経路モードのままである。
この違いを[設定](settings.md)にも記録している。

## 翌日を選ぶ2つの方法

燃料が厳しい小規模問題では2日共同改善を使う。
今日と翌日の `Waypoint` を同時に保持し、訪問の移動、車両の入替え、補給車経路の変更を温度付きで試す。
今日の取得系列を落とさず、両日とも時刻・燃料を満たす案だけを最良として保持する。
2日目の開始位置と燃料が今日の変更によって動くたび、翌日案の行動を更新する。

通常の先読みは、今日のアーカイブから終点の異なる案を数件選び、それぞれを共通エンジンで1日実行して比較する。
翌日の道路状態は現在の観測と試走後の状態を組み合わせて保守的に設定する。
残り時間を候補数で割って翌日の探索を行い、2日分の種類数・日別種類数・玉数の増分で今日の案を選び直す。
実際の翌日要求では予測交通の案を固定せず、新しい観測で計画し直す。

## 日別分岐の具体的な条件

`Planner::plan` は残り時間と燃料で次のいずれかを選ぶ。
以下の「1日」は現在の日を指し、「翌日」は予測用の試走である。

| 経路 | 主な条件 | 時間の使い方 |
| --- | --- | --- |
| 2日共同改善 | 5台以下、初日のステップ数に対して燃料上限が厳しい、翌日がある、残り1秒以上 | 当日案を先に作り、翌日案を作成して残り時間で両日を改善 |
| 通常の翌日試走 | 5台以上、翌日がある、残り20秒以上、現在日の燃料条件を満たす | 当日の候補生成に約65%、残りをアーカイブ候補の翌日比較へ配分 |
| 当日のみ | 上記以外、または最終日 | 期限まで当日の巡回・補給を改善 |

通常の先読みでは、当日の最良から評価値が大きく劣る候補を除き、残時間に応じて上位3〜4件を比較する。
候補を共通エンジンで実行した後、翌日用の交通状態と取得済み店舗を設定する。
明日の探索が時間切れや不正行動で終わった場合、その候補はそこで打ち切る。

## 車種選択の予算調整

`select` は問題の日ごとのステップ数の二乗和と要求時間から、1配置の試走に使える探索反復と反復回数を調整する。
5台以下では選択用の反復を最低4、仕上げの試行を最低2500に保つ。
車両が多く要求時間が短い場合はラウンド数を減らす。
1配置の全日程試走を時間内に終えられる範囲で、複数回の乱数系列を試す。

得点比較には全期間種類数、日別種類数、玉数の順を保つ大きな係数を使う。
これは車種選択に限った評価であり、日別探索の `solution_value` と係数が異なる。
前者は配置の長期効果、後者は残り時間内での今日の行動を比較するために使う。

## 保存版と当時の実行との差

単一ファイルの `solver05.rs` は分割ソースの関数と構造を保ってインライン化し、Rustfmtで整形した。
Cargoの保存用バイナリ名は `pool-solver-05` であり、当時の `solver` バイナリとは別である。
探索は実時間で打ち切られるので、ソースとseedが一致しても当時の正式runと同じ行動・得点になるとは限らない。
昇格判定は保存済みの[正式run](validation.md)で示す。

## 9. 三つの表現を使い分ける

第5世代では同じ行動を三つの粒度で扱う。
端点間の候補を探すときは `Waypoint` の列を使う。
補給車がどこにいるかは `Schedule` で時刻ごとに見る。
実際の回答は方向と待機からなる `Route` にする。

`Waypoint` は目的セル、待機、区間経路モードをまとめる。
店舗の挿入や順序変更には、この粒度が扱いやすい。
`Route` はゲームへ送る行動列なので、時刻と方向が確定している。
`Schedule` は補給車の行動から作られ、巡回車の燃料回復を判定する。
一つの `Waypoint` を変えたら、展開した `Route` と `Schedule` との整合を取り直す。

`faithful_points` は既存の行動列を端点列に写す。
`route_from_points` は端点列を方向・待機へ戻す。
`route_anchors` は行動中の重要な位置を端点として登録する。
これらは局所改善や2日共同改善で、元の位置関係を失わず編集するために使う。

## 10. 経路モードを選ぶ場面

第5世代の経路は `10t + wf` を最小化する。
`w=0` は時間だけを重視する。
`w=5` は燃料も少し見る。
`w=22` は燃料をさらに重く見る。
第4モードは地図セル数に応じて非常に大きな燃料重みを使う。

例えば時間優先経路が短くても燃料容量を超えるなら使えない。
燃料節約モードの経路なら訪問を成立させられる場合がある。
しかし燃料を節約した道が日末を超えればやはり使えない。
訪問先の順番と補給時刻も合わせて変える必要がある。
各 `Path` は目的関数の値だけでなく実時間、実燃料、方向列、通過店舗を持つ。
実行可能性は実量で判定する。

第4モードは全ての問題で作るわけではない。
日別計画で車両数が4のときに追加される。
車種選択は3モードで全配置を試す。
よって車種選択で予測した初日案と、実際の日別計画で選び直す案は異なり得る。
これは同じソルバ内の探索段階による候補空間の違いである。

## 11. 補給表を作る

`Stop` は補給車の停車端点と待機時間を表す。
`make_schedule` は停車列から時刻×セルの占有表を作る。
`raw_schedule` は既にある補給車の方向列から同じ表を作る。
巡回車がその時刻に補給車のいるセルにいれば、燃料を回復できる。
途中で経路上の店舗を通れば、訪問集合も更新する。

例えば補給車がPに時刻5〜9いる。
巡回車が時刻7にPへ着くなら、補給が成立する。
時刻4に着いて時刻5まで待つ経路も候補になる。
時刻10に着く経路は、その停車を利用できない。
Pへ到達する前に燃料が尽きる場合も利用できない。
補給後の燃料で次の店舗へ進めるかも別に確かめる。

`exact_support` は巡回経路に合う補給車の行動を探し直す。
`reschedule_route` は補給車を変えたあと巡回車の時刻を合わせ直す。
先に巡回を改善しても補給車が追いつかなければ無効になる。
逆に補給車だけ改善しても、巡回の到着時刻が変われば利益が出ない。
両者を往復して調整する必要がある。

## 12. ビーム探索の一状態

`State` は現在の端点と時刻を持つ。
残燃料と訪問店舗の集合を持つ。
親状態への参照を持ち、採用後に方向列を復元する。
次に進む店舗と経路モードを選んで子状態を作る。
区間で通った店舗も取得集合へ足す。
補給表に合えば、その時刻に燃料を回復する。

移動後に時刻や燃料が条件を満たさない子は残さない。
残った状態の得点、日末位置、燃料を使って優先順位を付ける。
ビーム幅を超えた状態は落とす。
4台以下で幅120、その他で幅90が基本である。
車種選択では全日程・複数配置を試すため、さらに軽い探索にする。

一台の訪問だけを良くしても全車最良とは限らない。
他車が同じ店舗を取ると、玉数は在庫上限で頭打ちになる。
同じ系列ばかりを複数車が取るより、別系列を分担した方がよい場合がある。
そのため、次の巡回車には先に組んだ車の取得情報を渡す。
`pack_routes` は車別候補を組み合わせて全体得点を評価する。

## 13. 局所改善の意味

ビームで得た候補は、構築順の影響を受ける。
最初の車が取った店舗を後の車が避けるためである。
`polish_fleet` は全車の `Waypoint` をまとめて変える。
店舗を別車へ移す。
訪問順を反転する。
補給停車を変える。
経路モードを変える。
全車の値で再比較する。

`soft_polish_fleet` は違反候補も途中で罰則付き評価に置く。
例えば店舗をAからBへ移すとき、最初の編集でBが時間超過になることがある。
次の編集でBの順番や補給時刻を変えれば合法になる可能性がある。
違反した中間案を全部捨てると、その改善経路へ届きにくい。
ただし返す最良案は合法なものとして別に保持する。

`rebuild_neighborhood` は訪問をいくつか落として入れ直す。
小さな交換だけでは組み替えられない経路を作る。
`fleet_score` は局所探索の速い比較に使う。
`solution_value` は最良候補の確認に使う。
二つの値が違う役割である点に注意する。

## 14. 得点を分解して読む

`solution_value` は新規系列へ1000000を掛ける。
当日系列へ100000を掛ける。
在庫上限を適用した玉数へ1000を掛ける。
翌日が残るときだけ日末の燃料と位置を補正する。
この補正は翌日の自由度を見るもので、明日の行動を保証しない。

車種選択では別の大きな係数を用いる。
全期間系列、日別系列、玉数を優先順で比較するためである。
日別探索の値をそのまま全日程の比較へ使わない。
局所改善ではさらに `fleet_score` を使う。
同じ候補でも、用途により参照する値が異なる。

例として今日の新規系列が同じ候補を比べる。
一方が当日系列を1つ多く取れば、その分が強く評価される。
当日系列も同じなら玉数が差になる。
これも同じなら日末の燃料や位置が判断材料になる。
実際の正式順位ではテスタが得点を集計する。
探索値の係数を正式得点の計算式として読まない。

## 15. 車種選択の流れ

初期位置ごとに補給車の候補を作る。
燃料が全日程に十分な条件では補給車なしも試す。
配置ごとに日々の `optimize` を走らせる。
各日の行動を共通エンジンで実行する。
実行できなかった日は待機へ切り替える。
全日程の結果から系列と玉数を比較する。
採用配置の初日案は、5台以下なら `opening` へ保存する。

補給車1台を選ぶと、その車は店舗取得に使えない。
一方で他の巡回車の燃料を回復できる。
補給車なしでは巡回台数が増えるが、燃料を使い切ると後日不利になる。
全日程試走はこの差を比較する。
時間予算が限られるので、配置数と日別ステップ数に応じて反復数を調整する。

## 16. 二種類の翌日評価

通常の翌日試走は、今日のアーカイブから数件を選ぶ。
終点が違う候補を残すことが重要である。
それぞれ今日の行動を共通エンジンで実行する。
翌日の開始位置、燃料、取得済み系列を得る。
保守的な翌日交通を置き、翌日を短時間探索する。
今日と明日の得点増分で今日の候補を選ぶ。

2日共同改善は、今日と明日の `Waypoint` を同時に変える。
今日の店舗を明日へ移す変更も扱える。
今日の終点が動けば、明日の出発状態も更新する。
両日で時刻と燃料の違反を評価する。
現在日の取得系列を落とさない条件を置く。
最良として保存する案は両日とも実行可能なものにする。

燃料が厳しい5台以下では共同改善が候補になる。
5台以上で時間と燃料条件を満たす場合は通常の翌日試走が候補になる。
条件を満たさない日は当日の改善に集中する。
翌日予測は次の実要求で新しい観測が届くまでの暫定評価である。
実際の翌日行動を今日の時点で確定するわけではない。

## 17. 例で追う二日間

今日A案は系列Xを取り、燃料が少ない位置Pで終わる。
今日B案も系列Xを取り、燃料を残して位置Qで終わる。
明日の未取得系列YはQの近くにあるとする。
当日値が同じなら、通常の翌日試走はB案を選びやすい。

ただしB案が今日の系列Xを失う変更なら、現在日の価値も比較する。
2日共同改善では今日の店舗訪問を他車へ移し、
空いた車を明日のYへ向けるような変更を試せる。
その変更で補給車の停車も変われば、
両日の巡回経路と燃料を再評価しなければならない。
この例は評価の関係を示すもので、実際の店舗位置や得点を指定しない。

## 18. 調査時の手順

まず問題の車両数と燃料条件を見る。
日別で3モードか4モードかを確認する。
補給車の停車列から `Schedule` を作る。
巡回車が補給前燃料で合流できるかを見る。
経路途中の店舗通過を取得集合へ加える。
複数車の同一店舗は在庫で玉数を切る。
日末の位置と燃料を確認する。
先読みが動いた場合は、どちらの分岐か確認する。
最後に `Game::play_day` の合法性判定を見る。

当時の正式runと保存版の行動が違う場合は、
実時間による反復数、交通予測、保存時のバイナリ差を考慮する。
この文書は保存版の仕組みを説明する。
正式な昇格成績は[検証記録](validation.md)を参照する。

## 19. 数値と分岐の見取り図

| 項目 | 値・条件 | 役割 |
| --- | --- | --- |
| 通常の経路モード | 3 | 時間と燃料の候補 |
| 4番目の経路モード | 日別計画で4台 | 強い燃料優先 |
| 巡回ビーム幅 | 4台以下で120、それ以外90 | 一層の状態上限 |
| 新規系列係数 | 1000000 | `solution_value` |
| 当日系列係数 | 100000 | `solution_value` |
| 玉数係数 | 1000 | 在庫上限後の個数 |
| 通常先読み | 5台以上、残り20秒以上など | 当日候補の翌日比較 |
| 2日共同改善 | 5台以下、燃料が厳しいなど | 今日と明日を同時編集 |
| 出力前の検査 | `Game::play_day` | 行動の合法性 |

この表は異なる場所の設定をまとめたものだ。
車種選択の重みは日別 `solution_value` と異なる。
先読みの条件は残り日数や燃料も含む。
上の条件だけで常にその分岐へ入るわけではない。
実行時間による打切りもある。

## 20. 一日計画を追う順序

車種選択で決めた補給車を確認する。
当日の車両位置と観測交通で `Network` を作る。
補給車の停車候補を作る。
各候補から `Schedule` を作る。
巡回車をビームで順に構築する。
車別経路を `pack_routes` で組み合わせる。
部分再構築と全車の局所改善を試す。
採用候補の `solution_value` を確認する。
条件が合えば翌日試走または2日共同改善を行う。
出力する当日計画を共通エンジンで検査する。
不正なら待機計画に切り替える。

この順序で `Schedule` が変わるたびに、
巡回車の補給時刻を再確認する。
訪問店舗の集合が変わるたびに、
系列と在庫上限付き玉数を全車で数え直す。
先読みが今日の候補を選び直しても、
実際に返すのは今日一日分の行動だけである。

## 21. 制約を見落とさないために

補給地点へ行く燃料は補給前に必要である。
待機している時間も日末制限に入る。
同じ店舗を複数台が通っても玉数は在庫を超えない。
経路途中の店舗も取得へ入る。
経路重みと実時間・実燃料は別である。
翌日の交通は予測で、次要求では更新される。
共同改善の途中で違反案を評価しても、
保存する最良案と最終回答には合法性を要求する。
