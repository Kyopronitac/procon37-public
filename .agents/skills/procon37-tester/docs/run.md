# 実行

以下のコマンドは対象チェックアウトのルートで実行するgameの例。soloでは `-p game` を `-p tester` に置き換える。単一スレッドのフルテストは件数もgameの30件からsoloの60件へ変更する。


- 必要環境はRust / Cargo 1.94以降。`cargo run --release -p game` はテスタを更新し、`run` は既定でソルバも一度ビルドする。`--no-build` は必要な全ソルバがビルド済みのときに使う。gameでは相手のビルドも省略される。
- 問題のseedとソルバの探索seedは別。既定ソルバには `-- 0` で探索seed 0を渡せる。比較では探索seed・制限時間・並列数を揃え、設定ファイルや継承した環境変数の影響も確認する。
- `--jobs` は同時に実行するケース数。既定ソルバは内部単一スレッド。対象ソルバが内部並列なら `--solver-parallel` を指定する。gameの自動並列数は `max(1, CPU数 / 5)`。相手の `solverParallel` を含め、いずれかが内部並列なら自動値は1試合になる。相手4枠はGUIまたは設定JSONの `opponents` で変更できる。

- 対戦のオプション・設定JSON → [tester/game/docs/usage.md](../../../../tester/game/docs/usage.md)
- 単独のオプション・設定JSON → [tester/solo/docs/usage.md](../../../../tester/solo/docs/usage.md)
- ソルバの時間・乱数設定 → [solver/docs/settings.md](../../../../solver/docs/settings.md)

## 目的に合うコマンドを選ぶ

目的に合うコマンドを選ぶ。`--label` は、履歴一覧だけで変更内容・比較上の役割・テスト範囲が分かる名前にする。例えば「補給計画改善前・game基準・フル30件」「補給計画改善後・solo・フル60件」のように付ける。「テスト」「フルテスト」だけのラベルは避け、以下の例も実際の作業内容に合わせて変更する。

```sh
# フルテスト以外の保存先。比較する実行では同じ一時ディレクトリを使う
procon37_test_dir="$(mktemp -d "${TMPDIR:-/tmp}/procon37-test.XXXXXX")"

# 単一ケースを実行し、失敗や得点を再現する
cargo run --release -p game -- run --seed 42 --format final --label '補給計画改善後・決勝seed42確認' --output-dir "$procon37_test_dir" -- 0

# 公式サンプル3件を実行する
cargo run --release -p game -- run 3 --label '補給計画改善後・公式サンプル3件' --output-dir "$procon37_test_dir" -- 0

# 単一スレッドのgameフルテスト：seed 0〜29、形式自動選択、既定制限時間
cargo run --release -p game -- run 30 --label '補給計画改善後・game・フル30件' -- 0

# 単一スレッドのsoloフルテスト：seed 0〜59、形式自動選択、既定制限時間
cargo run --release -p tester -- run 60 --label '補給計画改善後・solo・フル60件' -- 0

# ソルバを動かさず、問題だけを生成する
cargo run --release -p game -- generate --seed 42 --format final --output "$procon37_test_dir/problem.json"
```

フルテストの定義は [ルートREADME](../../../../README.md#テスト) を正とする。現時点では特段の指定がなければ対象ソルバを単一スレッドとして扱う。対象ソルバ内部が単一スレッドならgameは30件、soloは60件。内部並列・分散の場合は従来どおり60件を明示する。`--jobs` はこの区分を変更しない。

フルテストでは `--output-dir` を指定せず、対象チェックアウトの既定の保存先（gameは `.game/runs/`、soloは `.tester/runs/`）に履歴を残す。変更前・変更後とも同じ保存先を使い、GUIの履歴一覧とCUIの比較から参照できるようにする。
フルテスト以外は `mktemp -d` で作った一時ディレクトリを `--output-dir` に指定し、通常の `.game/runs/`・`.tester/runs/` の履歴に残さない。一時ディレクトリ内にも問題・リプレイ・ログは保存されるので、必要な確認・比較が終わるまで保持する。比較する実行は同じ一時ディレクトリに保存する。

フルテストでは時間を短縮する設定を使わない。テスタの `--time-limit-ms` だけでなく、ソルバの引数・設定・継承した環境変数に、探索時間や反復数を短縮する上書きが残っていないことも確認する。
現在の対象ソルバは要求の制限時間に合わせて探索する。短縮した実行は動作確認として区別し、フルテストの代わりにしない。

形式自動選択は `seed % 3` により1回戦・準決勝・決勝を巡回する。seed 0＋1回戦、1＋準決勝、2＋決勝だけが公式サンプル。練習場マップを含める場合は `seed % 4 == 3` にその形式の取り込みケースを使い、残りは生成ケースになる。

## 非公式練習場のマップを切り替える

game・solo・server共通で、既定は「含める」（`arenaMaps: true`）。連続する4 seedに1件、非公式練習場から取り込んだ盤面を使う。各サイズ5枚を用意し、既存3件を各サイズの先頭に残す。自動形式のseed 0〜59では全15枚を各1回使い、取り込み盤面の選択は60 seed周期で繰り返す。対象と出典は [取り込みケース](../../../../common/fixtures/arena/README.md) を参照する。

```sh
# 通常の生成マップだけで短縮確認する（公式サンプル3件は残る）
cargo run --release -p game -- run 12 --no-arena-maps --time-limit-ms 1000 --label '通常マップのみ・game12件・1秒確認' --output-dir "$procon37_test_dir" -- 0

# 取り込みを明示して確認する（seed 3・7・11は取り込みケース）
cargo run --release -p game -- run 12 --arena-maps --time-limit-ms 1000 --label '練習場込み・game12件・1秒確認' --output-dir "$procon37_test_dir" -- 0

# generateにも同じ設定を適用できる
cargo run --release -p game -- generate --seed 3 --no-arena-maps --output "$procon37_test_dir/problem.json"
```

設定JSONでは `"arenaMaps": false` / `true` を指定する。コマンドライン指定がJSONより優先される。`serve --no-arena-maps` はGUIの初期値も「含めない」にする。GUIの実行設定と問題プレビューからも変更でき、再実行は履歴に保存した設定を引き継ぐ。保存済みの問題・リプレイは変更しない。

この設定の導入前の履歴には `arenaMaps` がないため、読み込み時は「含めない」として復元する。新規実行用の設定JSONで省略した場合の既定値は「含める」のままとする。

変更前後の比較では、時間・探索seed・並列数に加えて `arenaMaps` を揃える。設定が異なる履歴では同じseedの問題が異なることがあり、そのケースは比較から除外される。

## フルテストの完了監視をAutomationへ引き継ぐ

フルテスト中の使用量を抑えるため、起動と監視設定を済ませたら **Codexの作業を一時停止する（現在のターンを終了する）**。テストのプロセスは継続させる。「一時停止」はエージェントの待機を終える意味であり、テストの中断やCodexアプリの終了ではない。

1. ターン終了後も動作を継続できる方法でテストを起動し、起動成功を確認する。対象チェックアウトの絶対パス、モード、実行ID（未発行ならラベル・開始時刻）、保存先、ログのパス、プロセス識別子を記録する。後続の実行で参照できるようにし、セッション内のシェル変数だけに依存しない。
2. `automation_update` ツールを探し、その時点の仕様に従って、現在のタスクに紐づく **heartbeat** の監視を設定する。同じ実行の監視があれば更新し、重複作成しない。既定の確認間隔は10分を目安に、予想所要時間やユーザーの指定に合わせる。
3. 監視指示には下記の情報と終了条件を含める。設定が成功したことを確認し、実行ID・保存先・監視間隔を短く伝えてターンを終了する。`sleep` やプロセス待機ツールを繰り返して完了まで居続けない。

監視指示に含める内容：

- 記録した対象とプロセス・ログ・`run.json` を軽く確認する。進行中で対処不要なら、定例の進捗報告や長い分析をせず、その回のターンを終了する。
- 完了時は [結果確認・比較](compare.md) に従って完了件数・判定・成績を確認する。比較が依頼されている場合は、引き継いだ基準の実行IDと比較して報告する。今回の監視を無効化し、不要な起動を止める。
- 失敗・中断・ユーザーの対応が必要な場合は、ログから状況を短く報告して監視を無効化する。正常完了として扱わず、自動で同じバッチを再起動しない。

待機ツールのタイムアウトだけではテスト失敗と判断しない。プロセス終了だけでも成功と判断せず、保存記録を確認する。

Automationが利用できない、または設定に失敗した場合は、監視が設定できていないことと実行状況・保存先を明示してターンを終了する。監視中だと主張したり、無断で別方式の常駐監視を作ったりしない。

Automationの操作仕様は利用可能なツールを優先し、必要なら [公式ドキュメント](https://developers.openai.com/codex/app/automations/) を確認する。

- 生成ケースの分布や上限未達率を評価する場合 → [tester/solo/docs/generator-calibration.md](../../../../tester/solo/docs/generator-calibration.md)
