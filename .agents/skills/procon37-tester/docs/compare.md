# 結果確認・比較

以下のコマンドは対象チェックアウトのルートで実行するgameの例。soloでは `-p game` を `-p tester` に置き換える。

新しい実行が必要なら [実行手順](run.md)、視覚確認が必要なら [GUI手順](gui.md) を読む。

## 変更前の基準を確保する

ソルバ変更の評価では、ブランチ開始時の結果と変更後の結果をCUIで比較する。ブランチ開始時のテスト結果が保存されていれば、その記録を比較の基準に使い、同じテストを再実行する必要はない。記録がなければ、ソルバを変更する前に基準となる結果を保存する。変更後の結果を「変更前」として扱わない。

## 実行結果を確認する

1. CUIのサマリーから実行IDと保存先を控える。フルテストはgameが `.game/runs/<実行ID>/`、soloが `.tester/runs/<実行ID>/`、それ以外は指定した一時ディレクトリの `<実行ID>/` に保存される。
2. `run.json` の実行状態・完了件数・判定を確認する。得点だけで成功を判断せず、CE・RE・TLE・WAやフォールバックを先に調べる。
3. `config.arenaMaps` を確認する。比較する実行では取り込み設定を揃える。既定は `true`。切り替え方法は [実行手順](run.md#非公式練習場のマップを切り替える) を参照する。

不具合は各seedの個別ログ（gameの対象とsoloは `stderr.log`、gameの相手は `stderr-1.log`〜`stderr-4.log`）と `replay.json` の失敗理由・提出回答・採用計画から調べる。採用計画が待機でも、ソルバの提出回答が待機だったとは限らない。

## 履歴を比較する

```sh
# フルテストの比較。実在する実行IDに置き換える。最初のIDが基準
cargo run --release -p game -- compare BASELINE_ID CANDIDATE_ID

# 集計を機械可読形式で取得する
cargo run --release -p game -- compare BASELINE_ID CANDIDATE_ID --json

# フルテスト以外の比較には、実行時と同じ一時保存先を指定する
cargo run --release -p game -- compare BASELINE_ID CANDIDATE_ID --output-dir "$procon37_test_dir"
```

`procon37_test_dir` は実行時の一時保存先を指す。別のシェルで比較する場合は、記録したパスを設定する。

比較は「問題本体と形式が一致し、全履歴でAC」のケースだけを対象とする。gameでは相手4枠の実行条件・実装識別情報も一致し、5人全員がACのケースを対象とする。同じseedでも生成器が違えば問題が変わり得るため、比較対象数と除外理由を見る。フルテスト以外の比較では `--output-dir` に実行時と同じ一時ディレクトリを渡す。
勝敗の優先順は **種類数 → 日別種類数 → 玉数**。回答時間は別に比較し、時間制探索の実行負荷による変動も考慮する。

## 結果を報告する

GUI・CUIの比較結果では、全体の **種類数・日別種類数・玉数の合計** と、**以前に対してA勝B同点C敗** の両方を確認する。勝敗は変更後から見た件数で、合計と同じ比較対象集合を使う。

比較結果の報告とソルバ変更時のPRは、[READMEのPRテンプレート](../../../../README.md#pr-の書き方)に合わせ、3指標の合計を以前・変更後で並べた表と「A勝B同点C敗」にまとめる。PRの比較基準はブランチ開始時とする。形式別の内訳や詳細な実行条件は、求められた場合や問題の説明に必要な場合に補足する。
未完了・非AC・比較対象の不一致など、結果の解釈に影響する問題があれば短く添える。

- 対戦の保存形式・比較・ZIP → [tester/game/docs/history.md](../../../../tester/game/docs/history.md)
- 単独の保存形式・比較・履歴の移動 → [tester/solo/docs/history.md](../../../../tester/solo/docs/history.md)
