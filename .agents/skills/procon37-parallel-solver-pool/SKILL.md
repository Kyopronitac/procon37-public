# 並列ソルバの世代育成

目的は、多様な強い並列ソルバ4体を育てること。このPCをserverとし、SSH先の並列4体と固定の単一スレッド2体、合計6体を対戦させる。[元のpoolスキル](../procon37-solver-pool/SKILL.md)と同様に、親agentはフルテスト・共通環境や他枠の配置変更・昇格判断を担当し、開発subagentは候補の構築・改善、自分の対象ソルバの配置、単独および6体での短縮テストを担当する。commit・pushとその記録は親が昇格手続きとして行う。

「`$procon37-parallel-solver-pool` で3世代育成して」のように実行する。世代数が未指定なら確認する。スキルの作成・編集・相談だけではSSH先の環境構築や育成を開始しない。

## 固定構成とSSHの事前許可

| PC | IP | SSHユーザー | パスワード | CPU資源 | 配置 |
| --- | --- | --- | --- | --- | --- |
| VOIDLINUX-1 | `192.168.0.11` | `voidlinux-1` | `114514` | 16C32T | 並列P0・P1（各15スレッド） |
| VOIDLINUX-2 | `192.168.0.22` | `voidlinux-2` | `114514` | 8C16T | 単一スレッドS0（第6世代）・S1（第8世代） |
| VOIDLINUX-3 | `192.168.0.33` | `voidlinux-3` | `114514` | 16C32T | 並列P2・P3（各15スレッド） |

**指定3台の実験PCに対するSSH関連操作は、すべて事前に許可されている。** SSH接続、リモートコマンド実行、ファイル転送・作成・変更・削除、ソフトウェア導入、環境設定、ビルド、プロセスの起動・停止などを、その都度ユーザーに確認せず実施してよい。3台は自由に環境構築とファイル作成・削除を行える実験環境である。実行環境の権限機構には従う。

- **15は制御を含むソルバ内部の総スレッド数の上限。** 例は制御1＋探索14。別プロセスのserver-bridgeはこの数に含めない。S0・S1のソルバ内部は各1スレッドとする。
- 各PCの2体は物理コアを分け、実行ディレクトリ・ログ・ビルド出力を分離する。ホスト・CPU割り当て・チーム番号は育成中固定する。
- CPU差を補正しない。追加の性能ベンチマークやVOIDLINUX-1と3の入れ替え評価は行わない。配置を含む実行環境での強さを評価する。

初期配置・接続・CPU割り当てには [実行環境と評価](docs/runtime.md) を読む。

## 初期構築と共通基準

1. **共通基準を保存する。** 育成開始時点の「現在最強の単一スレッドソルバ（現行ソルバ）」を、必要なソース・専用モジュール・設定・依存を含めて独立ビルド可能な基準版として保存する。コミットIDと内容ハッシュを記録し、この育成中は更新しない。ユーザーの未コミット変更があれば基準に含め、ハッシュで識別する。
2. **固定2体を用意する。** 元のpool育成で保存された単一スレッドの第6世代をS0、第8世代をS1として固定する。指定した世代の保存版であることを識別情報で確認し、実行ファイルのハッシュ・再現用のビルド方法を記録する。強さによる再選定や別世代への差し替えは行わず、S0・S1は順位が低くても世代交代させない。保存版の実装は閲覧せず、許可されたビルド・実行・識別用ハッシュの確認で扱う。
3. **並列4体を構築する。** P0〜P3をそれぞれ共通基準から構築する。探索方針の多様性を意識するが、手法は開発者に任せる。アルゴリズムの改変・置き換えも許可する。初期構築の開発者にも、他の並列実装や設計資料を参照させない。
4. **6体を配置して初回評価する。** 全員ACのserverフルテスト12件を最初の基準結果とする。初期構築は指定された世代数に数えず、4体それぞれに単独首位を要求しない。

共通基準と候補は、保護されたサンプル・保存版と別の管理領域（例：`solver/parallel-pool/`）に置く。元スキルの「ゼロから作る」「相手をsamplesに移す」という手順は適用しない。

## 開発者と参照範囲

元スキルと同じく、特別な指定がなければ親agentは **GPT-6 Sol / medium**、開発subagentは **GPT-6 Astra / xhigh**。親のモデルはchat側で選択し、自動切り替えしない。開発者は `collaboration.spawn_agent` で `fork_turns="none"`、`model="gpt-6-astra"`、`reasoning_effort="xhigh"` を指定する。ユーザーのモデル指定があれば優先する。

- 初期の各候補および各世代に新しい開発者を起動し、同じ候補の改善は同じ開発者が続ける。利用可能なagent枠に合わせて進める。
- [開発依頼](docs/developer-task.md) に、共通基準・編集範囲・公開仕様・起動方法・固定対戦構成・評価条件と必要な結果だけを渡す。共通基準のソースと資料は読んでよい。親の会話・旧並列実装・他候補の設計履歴は渡さない。
- ファイル共有があるため、履歴なし起動だけで隔離されたとみなさない。読み取り対象外のパスを明示し、検索・コピー・Git履歴にも同じ制限を適用する。
- 開発者は6体での短縮対戦の起動・監視・集計・結果に基づく改善も担当する。必要な実行手順・ブラックボックスの起動情報・自身の短縮結果を渡す。自分の対象枠への候補バイナリと専用ランチャー・起動設定の配置は開発者が行ってよい。配置前後のパス・ハッシュ・起動設定を記録し、親へ返す。他5体、共通環境、固定のホスト・チーム番号・CPU割り当ては変更しない。親は短縮対戦を代行しない。
- 開発者が変更するのは対象候補とその資料だけ。相手ソルバ、server・bridge・採点器・固定対戦設定の変更、自分の対象枠以外の配置管理、commit・pushは開発作業に含めない。
- `tester/game/samples/` と `solver/docs/solver-pool-experiment/` は [ルートの閲覧規則](../../../AGENTS.md) に従う。実装を閲覧・検索・コピー・履歴調査・逆解析せず、全体検索からも除外する。ビルド・実行・公開通信仕様・成績・リプレイ・識別用ハッシュは利用できる。固定相手の選定のために保護実装を読む必要はない。

## 指定世代数だけ繰り返す

1. **最下位を選ぶ。** 現在の6体を正式評価し、P0〜P3の平均順位最下位を再構築対象にする。同率最下位は固定IDの昇順で選ぶ。全員ACで識別情報・配置・評価条件が一致する保存結果は再利用してよい。S0・S1は選ばない。
2. **共通基準から再構築する。** 対象枠の旧並列実装は開発者に引き継がず、独立した作業場所に共通基準を用意する。ゼロからではなく、この基準から15スレッド以内の候補を構築する。並列化に限定せず、アルゴリズムの変更を認める。
3. **単独首位まで改善する。** 開発者が自分の候補を同じチーム・ホスト・CPU割り当てへ配置し、6体での短縮対戦と改善を繰り返す。短縮テスト全体で1位を確認したら、開発者は評価済み候補を凍結し、短縮結果・識別情報・起動設定を親へ返す。親が正式フルテストを行い、未達なら必要な正式成績を同じ開発者に返して改善を続ける。設計・短縮テストのたびにユーザーの確認を求めない。
4. **昇格・commit・pushする。** 保存結果で昇格条件と識別情報を確認し、評価した実装一式と記録をcommit・通常pushする。push成功までを1世代と数え、残る3並列＋2固定はそのまま次世代に進む。評価した実行ファイルをそのまま昇格させ、評価後の変更を混ぜない。

残る5体は候補の変更から独立してビルド・実行でき、ソースまたは保護実装の許可されたビルド手順から再現可能な状態を保つ。候補の変更・再ビルド・再配置で識別情報が変わった場合、以前の評価を新しい候補の昇格根拠にしない。

## 正式評価と昇格条件

フルテストには時間がかかるため、世代交代候補は、同じ6体による短縮テスト全体の平均順位（順位合計）で1位になるまで、正式フルテストへ進まないことを推奨する。短縮対戦は開発者が実行・集計し、未達なら同じ開発者が結果に基づいて改善を続ける。1試合だけの1位で判定せず、短縮結果は正式評価・昇格の根拠にはしない。

**このスキルのserverフルテストは12件。** ユーザー指定により、ルートREADMEやtesterスキルの内部並列60件という一般規定より、この条件を優先する。game・soloのフルテストを追加の必須条件にしない。

```sh
cargo run --release -p server -- run 12 --players 6 \
  --label '並列pool・第N世代・候補P0・正式12件'
```

- seed 0〜11、形式自動（各形式4件）、既定制限時間、練習場マップは既定で含める。短縮オプション・探索予算の短縮を残さない。`--output-dir` を指定せず `.server/runs/` に保存する。
- **12試合すべてで6体全員AC、候補の平均順位が他5体すべてより厳密に小さいこと。** 同率首位は不可。欠落・非ACを除外して達成扱いにしない。
- `run.json` の各ケースの `players` に保存された順位を集計し、丸めた平均ではなく順位合計で比較する。チーム0だけの集計で代用しない。
- 正式評価中は候補と相手5体、実行ファイル・設定・乱数設定・配置を固定する。元スキルと同様に短縮テストは自由だが、昇格判定には使わない。
- 変更前との比較には対象選定時の結果を使い、種類数・日別種類数・玉数の合計、候補から見た勝・同点・敗を記録する。条件が違う場合は差を明記し、比較用の追加フルテストを先に行わない。

起動・保存記録の確認・長時間テストの完了監視は [実行環境と評価](docs/runtime.md) に従う。親が再開を管理し、開発者の実験と正式評価を重複起動しない。

## 記録と完了

各世代の6体の対応、共通基準、ソース・実行ファイル・bridge・公式サーバーの識別情報、起動設定、CPU割り当て、評価条件・実行ID・順位合計と平均順位、前後比較、commit・push結果を `solver/docs/parallel-pool/` に残す。保護された保存版配下には置かず、開発者へ管理記録全体を渡さない。

再開情報は `.server/parallel-pool-state.json` に保存する。初期構築の進捗、指定・完了世代数、段階、対象ID、共通基準、6体の配置・ハッシュ、基準／候補の実行ID、開発者ID、プロセス・ログ・監視、commit・push状態を記録し、再開時に実状態と照合する。

ユーザーの変更を保ち、今回の育成に属する変更のみをリポジトリの規約に従ってcommit・通常pushする。指定数のpush完了が終了条件。未達・失敗を成功として数えない。停止指示・予算上限・解消できない障害では状態と再開事項を報告する。終了時は完了世代数、順位、commit・push結果、記録先、残るリモートプロセスと停止方法を簡潔に伝える。
