# 実行環境と評価

## 初期配置

このPCでserverを実行し、SSH先で各チームのsolver＋server-bridgeを動かす。チーム番号は以下で固定する。

| solver ID | チーム番号 | ホスト | ソルバ内部スレッド上限 |
| --- | ---: | --- | ---: |
| P0 | 0 | VOIDLINUX-1 | 15（制御を含む） |
| P1 | 1 | VOIDLINUX-1 | 15（制御を含む） |
| P2 | 2 | VOIDLINUX-3 | 15（制御を含む） |
| P3 | 3 | VOIDLINUX-3 | 15（制御を含む） |
| S0（第6世代） | 4 | VOIDLINUX-2 | 1 |
| S1（第8世代） | 5 | VOIDLINUX-2 | 1 |

接続先は [SKILL.md](../SKILL.md) の表を使う。既存環境を確認し、必要に応じてVoid Linuxに適した方法で依存を導入する。各ソルバの専用ビルド出力を使い、他チームのバイナリを上書きしない。実験用ソルバの環境構築に保護ディレクトリ全体のコピーは使わない。

準備は [server側](../../../../tester/server/docs/server-pc.md) と [solver側](../../../../tester/server/docs/solver-pc.md) の手順に従う。ただしこのスキルは1台に2チームを置くため、ドキュメントの「チームごとに1台」は専用プロセス・実行ディレクトリで代替する。

- 公式簡易サーバーの実体と実行権限を確認する。既定は `tester/server/procon-server`、別パスなら `--server-program` で指定する。見つからなければ既存の配布物を確認し、入手できない場合は準備段階の障害として報告する。試験用の代役を正式評価に使わない。
- 実際に3台から到達できるこのPCのLANアドレスを確認し、各チームの `SERVER` に設定する。`run.sh` の既定アドレスを無確認で使わない。窓口は既定TCP 11451。
- サーバーPCと3台の時刻同期を確認する。締切はUNIX時刻で伝えられるため、Void Linuxの利用可能なNTPサービス等で合わせる。
- 各チームの実行ディレクトリを分け、`stderr.log` の衝突を防ぐ。試合ごとに上書きされるログが必要なら、チーム・試合ごとに退避する。

## CPU割り当てと15スレッド

`lscpu -e=CPU,CORE,SOCKET,CACHE` とSMTの兄弟関係を読み取り、同じPCの2体に重ならない物理コアを割り当てる。CPU番号だけを半分に分けると、同じ物理コアのSMTを別ソルバへ割り当てる場合がある。

2026-10-06の確認では、VOIDLINUX-1は9955HX3D（L3は96＋32MiB）、VOIDLINUX-3は9955HX（32＋32MiB）。両方ともCPU `i` と `i+16` が同じ物理コア、物理コア0〜7と8〜15が別L3共有グループだった。両グループから各4物理コアずつ使う例は以下。実行時のトポロジーと一致することを確認してから使う。

| 同一PC内の枠 | 論理CPU集合（各15個） |
| --- | --- |
| 1体目（P0またはP2） | `0-3,8-11,16-19,24-26` |
| 2体目（P1またはP3） | `4-7,12-15,20-23,28-30` |

この例では27・31をソルバ集合から外す。両ソルバの物理コアは共有しないが、外したCPUは割り当て済み物理コアのSMT兄弟なので、専用の空き物理コアが2個あるという意味ではない。S0・S1も異なる物理コアへ固定する。

`taskset` 等でソルバに割り当てを適用する。run.sh全体を固定するとbridgeにも同じ集合が継承されるため、必要なら `SOLVER` にソルバだけを固定する専用ランチャーを指定する。

```sh
#!/bin/sh
# ソルバ専用ランチャーの例。実パス・CPU集合・必要な固定引数を設定する。
exec taskset -c '0-3,8-11,16-19,24-26' /absolute/path/to/P0/solver "$@"
```

CPU集合を15個にするだけではスレッド数は制限されない。ソルバの実装・設定で制御を含む総数を15以下にし、短縮実行で `/proc` または `ps -L` 等のスレッド数も確認する。ライブラリの隠れたスレッドや二重の並列化にも上限を適用する。

## チームの起動

[run.sh](../../../../tester/server-bridge/run.sh) は1試合ごとにbridge・solverを起動し直す。同じチーム番号で複数の常駐プロセスを起動しない。SSH切断後も継続する方法（tmux等）で6体を試合開始前から待機させる。

各チームの専用ディレクトリから起動する例：

```sh
SERVER='http://<このPCのLANアドレス>:11451' TEAM=0 \
  SOLVER='/absolute/path/to/P0/launcher' \
  BRIDGE='/absolute/path/to/server-bridge' \
  /absolute/path/to/repo/tester/server-bridge/run.sh
```

`TEAM`・`SOLVER` は対応表に合わせる。トークンは `token-p<TEAM>`。探索乱数・スレッド設定等はソルバ設定またはランチャーの固定引数で渡し、実値を記録する。`run.sh` 自体にはソルバ引数を渡す環境変数はない。必要ならbridgeの `--args` / `--` を使う専用起動方法を用意する。bridgeやサーバーの通信・採点の実装は変えない。

6体での短縮対戦は開発者が起動・監視・集計する。親は初期の共通環境・固定対戦構成を用意する。開発者は自分の対象枠の候補バイナリと専用ランチャー・起動設定を配置してよく、配置前後の識別情報を親へ報告する。他5体・共通部品と固定ホスト・チーム番号・CPU配置は変更しない。正式評価中は対象候補も差し替えない。初回も開発者の短縮テストで6体の通信・提出・終了・次試合への参加を確認してよい。フルテスト以外の履歴は `mktemp -d` の一時保存先へ置く。自分の短縮テストと正式評価を重ねない。

## 正式評価と集計

リポジトリルートで [SKILL.mdの12件コマンド](../SKILL.md#正式評価と昇格条件) を使う。チーム名を設定する場合は [serverの設定JSON](../../../../tester/server/docs/usage.md#実行設定) を使用し、件数・人数・形式・制限時間・練習場設定を変えない。serverは試合を順番に実行するため `--jobs` は付けない。GUIが同じ対戦窓口を使用していれば、重複してCUIのrunを起動しない。

正式評価前に、6体のソースとバイナリ、ランチャー、設定、bridge、公式サーバーの識別情報を記録する。評価後も一致を確認し、同じ実行ファイルを昇格させる。評価後に変更した候補には正式評価をやり直す。

集計は `.server/runs/<実行ID>/run.json` の実際のスキーマを確認して行う。

1. seed 0〜11が重複・欠落なく完了し、各ケースにチーム0〜5が1体ずつあることを確認する。
2. 各ケースの全6体の判定を確認する。1体でも非ACなら、ACだけの平均順位で対象選定や昇格をしない。原因を調べ、正式評価を満たす結果を確保する。
3. チームごとに保存された順位を12件合計し、12で割って平均を表示する。対象選定はP0〜P3だけ、昇格判定の比較相手は他5体。
4. 得点は種類数・日別種類数・玉数の順で比較し、対象枠の変更前後の合計と勝・同点・敗を計算する。同じseedでも問題と条件が違えば比較の差を明記する。

serverの標準 `compare` はチーム0を比較するため、対象がチーム1〜3の場合は `cases[].players` の対象チームを集計する。表示名の変更やチーム0への移動で代用しない。

## フルテストの完了監視と再開

[testerのAutomation監視手順](../../procon37-tester/docs/run.md#フルテストの完了監視をautomationへ引き継ぐ) をserverに適用する。件数は12、保存先は `.server/runs/` とし、共通の60件やgameへの置き換えはしない。

ターン終了後も継続する形で正式評価を起動し、実行ID・ラベル・保存先・プロセス・ログ・段階を `.server/parallel-pool-state.json` に記録する。現在のchatに紐づくheartbeatを設定し、進行中で対処不要なら通知せず、ターンを終了する。sleepやポーリングを繰り返して待ち続けない。

監視の完了時は保存結果を確認し、今回の監視を無効化して親の育成処理を再開する。初回／対象選定の評価なら最下位を選んで開発者を起動し、候補評価なら未達を開発者に返すか、昇格・commit・pushして次世代へ進む。1回のテスト完了を育成全体の終了と取り違えない。

失敗・中断なら成功扱いせず、ログと再開情報を保存して報告する。同じバッチを監視から無条件に再起動しない。Automationが利用できない場合は実行状況・監視未設定・再開方法を報告する。停止指示や予算上限があればそれに従う。
