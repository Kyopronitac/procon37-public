# server-bridge

2026年10月10日の試合用C013は [3台の本番配置](competition/README.md) と [選定結果](../../solver/docs/distributed/resume-20261009/frequency16-20261010/result.md) を参照してください。VOID1の `~/procon37-competition/run.sh` が当日の入口です。

公式対戦サーバー(HTTP)とソルバの入出力形式を相互変換する道具です。
各ソルバPC上で、ソルバ本体と一緒に使います。通常は同じディレクトリの [run.sh](run.sh) から起動します。

## 役割

```
公式対戦サーバー(HTTP) ── server-bridge ── 標準入出力 ── ソルバ
```

- 公式対戦サーバーに対しては「1チームの回答クライアント」として振る舞います。
- ソルバに対しては、既存のテスタ(`game`/`solo`)と同じ形式の要求を送ります。
- 公式API(`/setting`・`/agent`・`/`)だけを使います。本番の競技サーバーにも、練習用の [対戦サーバー](../server/README.md) にも同じ手順で接続できます。

結果の計算は行いません。提出の翻訳と送受信だけを行い、結果はサーバー側で再現されます。

## run.sh

ソルバPCで常駐させる起動スクリプトです。試合が始まるたびに server-bridge を起動し、1試合ずつ担当させます。
端末にはノード／問題サーバーへのアクセス、問題受信、ソルバ起動、現在の日、提出秒数、採否、ソルバ終了だけを表示します。bridgeとソルバの詳細ログはリポジトリ内の `.server/bridge-logs/` へ保存します（`BRIDGE_LOG_DIR` で変更可能）。
取得した問題・マップ・日別道路状態と提出の通信は、試合ごとに `.server/submissions/` へJSON形式で保存します（`RECORD_DIR` で変更可能）。通常版の提出は既定で55秒です。表示・保存ファイル・提出設定は [run.shの表示と保存](docs/run-logs.md) を参照してください。
リポジトリでビルドしておけば、練習ではチーム番号を指定するだけで参加できます。本番では冒頭の「本番の設定」を書き換えて起動します。

```sh
cargo build --release -p solver -p server-bridge
TEAM=0 ./tester/server-bridge/run.sh
```

詳しくは [ソルバPCのセットアップ](../server/docs/solver-pc.md) を参照してください。

## 三台分散版の本番操作

2026年10月10日の試合用C013は、VOID1の `/home/voidlinux-1/procon37` にリポジトリ全体と起動設定を配置済みです。`tester/server-bridge/distributed/run.sh` 冒頭の `SERVER` と `TOKEN` を当日の値へ編集し、リポジトリルートから `./tester/server-bridge/distributed/run.sh` を実行します。VOID2/3も自動起動します。[C013の操作手順](distributed/README.md#配置済みc013を使う2026年10月10日)を参照してください。

以下は従来D0を新規配置する場合の手順です。

採用済みD0をVOID1から三台へ配置する場合は [distributed.py](distributed.py) を使います。VOID1でD0とbridgeをコンパイルし、生成した実行ファイルを有線LANのSSHで配布します。VOID2/3にリポジトリは不要です。

```sh
./tester/server-bridge/distributed/compile.sh
./tester/server-bridge/distributed/deploy.sh
./tester/server-bridge/distributed/run.sh
./tester/server-bridge/distributed/run.sh status
./tester/server-bridge/distributed/run.sh stop
```

操作はVOID1のリポジトリルートで行います。`distributed/run.sh` は三台の詳細ログをファイルへ保存し、端末には上記の進行だけを表示して待機します。`Ctrl+C` で停止します。`status` / `stop` は別端末から実行できます。指定するURL・トークン、ログの見方、設定変更、再コンパイルは [分散ソルバD0を3台で本番に使う](../server/docs/solver-pc.md#分散ソルバd0を3台で本番に使う) を参照してください。

## 使い方

```sh
server-bridge \
  --server http://HOST:PORT \
  --token TOKEN \
  --solver /path/to/solver
```

| オプション | 説明 |
|---|---|
| `--server` | 対戦サーバーのURL (必須) |
| `--token` | チームのトークン (必須) |
| `--solver` | ソルバ実行ファイル (必須) |
| `--args` | ソルバへ渡す引数（ハイフンで始まらないものだけ） |
| `--` | 以降の引数をすべてそのままソルバへ渡す（`-- --threads 4` のようにハイフンで始まる引数も渡せる） |
| `--cwd` | ソルバの作業ディレクトリ |
| `--record-dir` | 試合データの保存先。bridge直接起動時は作業ディレクトリの `.server/submissions`、両 `run.sh` からはリポジトリ内の `.server/submissions` が既定値 |
| `--select-ms` | 車種選択の制限時間(ms)。省略時は下記のとおり決める |
| `--submit-at-ms` | 各フェーズ開始からの提出時刻(ms)を昇順CSVで指定。例: `55000`、`5000,15000,25000,35000,45000,55000` |
| `--stream-responses` | 1要求への途中解JSONLを受信する。`--submit-at-ms`との併用が必要 |

1回の起動で1試合を担当し、試合の終了を確認してから終了します。
トークンが認められない(HTTP 401)ときは終了コード2で終わります。

## 動き

1. `GET /setting` が200を返すまで待ちます(試合開始と同時に問題が取得可能になる)。問題を取得したらソルバを起動します。1日目が始まった後に参加した場合(再起動など)は、車種選択は締め切られているので、ソルバへ問題を渡すだけで車種を提出しません。
2. 車種選択を要求し、`POST /agent` で提出します。ソルバが答えられなかった場合は全車0を提出します。全車0で代替した場合や、車種が受理されなかった・提出しなかった場合は、1日目の要求の `previousAccepted` を false にし、ソルバが状態から実際の車種を読み直せるようにします。
3. 各日: `GET /` で状態を取得 → ソルバへ計画を要求 → `POST /` で提出します。

   提出の応答を受け取れず採否が分からない場合は、翌日の状態が前日から計画どおりに進み、全車待機とは区別できるときだけ受理とし、`previousAccepted` に反映します(区別できなければ未受理として進めます。計画の実行でも説明できる場合は、観測に表れない獲得が変わったかもしれないので、判断できないとして警告を表示します)。比べるのは車の位置・燃料と、1チームの試合では道路状態です(同じ位置・燃料に戻っても、道路の滞在が変われば見分けられます)。

   受理の応答を受け取ったのが締切(`endsAt`)以降だった場合も、翌日の計画として適用されたかもしれないので、同じく翌日の状態で確かめます。再送の末に却下の応答を受け取った場合も、先に応答を受け取れなかった送信が受理されたかもしれないので、同じく翌日の状態で確かめます。

   採否が不明だった提出が後の日の計画として残って実行されないよう、次に状態を観測した日（何日か飛ばした場合も）は最初に全車待機を提出して上書きしてから、ソルバの回答を提出します。この上書きを確かめられなかった場合は警告を表示します。

   送信が遅れて何日か後に処理され、その日を観測できず上書きできないまま後の日の状態を観測した場合も、提出した日から次に観測した日の前日までのどの日に実行されたか（または実行されなかったか）を状態から判断します。後の日に実行されていれば、控えをそのとおりに進めて警告を表示します。ただし対戦（他チームあり）では、観測できなかった日の道路状態が他チームの滞在で決まり再現できないため、提出した日に実行されたと分かる場合のほかは判断せず（全車待機で観測と一致しても、飛ばした日に往復して獲得した場合を除けないため）、全車待機として進めて警告を表示します。ソルバには自分の前日の回答の採否しか伝えられないため、前に回答した計画が後の日に実行されるとソルバの状態を合わせる手段がありません。

   最後に回答した状態と日・締切が合わない前の日の状態や、試合開始後の開始前(403)、締切がこの試合の日程から全日程ぶん以上遅い状態(最初の状態を含む)が返った場合は、次の試合のものとして終了します。

   途中から参加した・何日も通信が途絶えたなどで日を飛ばした場合は、飛ばした日を全車待機で進めた状態を共通エンジンで作ってソルバへ1日ずつ渡し(回答は使わない)、ソルバを実際の日まで追いつかせてから回答します。途中で再起動した場合など、それより前に自チームの車が動いていた（この変換器が知らない計画が実行されていた）ときは、全車待機で進めた状態が観測と一致しないので警告を表示します。ソルバには前日の回答の採否しか伝えられないため、同梱ソルバの状態は合わせられず、その試合の残りの日は回答できないおそれがあります（次の試合からは通常どおり参加します）。
4. 最終日の提出後、この試合の終了を確認して終了します。`match has ended` のほか、次の試合の開始前(403)や、最後に回答した日と異なる日・締切の状態が返った場合も終了とみなします(対戦サーバーが続けて開いた次の試合を待ち続けないように)。

### 制限時間

| 対象 | 決め方 |
|---|---|
| 車種選択 | 問題を最初に取得した時刻から数える。`--select-ms` があればその値。無ければマップの大きさから本選の時間(16×16は60秒、24×24は90秒、32×32は120秒。[本選マップに関するお知らせ](../../official/本選マップに関するお知らせ.pdf)) |
| 各日 | 状態の `endsAt` (UNIX秒) とこのPCの時計の差。PCの時計がずれていると制限時間もずれる |

どちらも、締切までの残り時間から通信の余裕として500msを引いてソルバへ渡します。ソルバが確保する余裕(制限時間の1%)はソルバ内の処理のためのもので、LAN越しに状態を受け取り提出が届くまでの時間は含まないためです。

練習用の対戦サーバーで制限時間を短縮しているときだけ、`/setting` の応答に `Procon37-Select-Remaining-Ms` ヘッダ(車種選択の残り時間)が付きます。`--select-ms` が無ければこれを使います。本番のサーバーはこのヘッダを返さないので、マップの大きさから決めます。

練習用の対戦サーバーは試合を続けて開くので、進行中の試合への応答に `Procon37-Match-Id` ヘッダ(試合ID)を付けます。`/setting` で受け取った試合IDと違う応答は次の試合のものとみなし、同じ問題の試合が続いても取り違えません。本番のサーバーはこのヘッダを返しません。

### 提出時刻の固定と途中提出

`--submit-at-ms 55000` は車種選択と各日の55秒時点で提出します。車種選択の公式時間が90秒・120秒の場合も55秒です。サーバーの締切や各日の制限時間は変更しません。固定の既存ソルバは実行ファイルを変更せず、このbridgeオプションだけで利用できます。

開発中の分散ソルバは、対応するソルバを `--stream-responses` 付きで動かし、bridgeにも以下を指定します。

```sh
server-bridge --server http://HOST:PORT --token TOKEN --solver /path/to/streaming-solver \
  --submit-at-ms 5000,15000,25000,35000,45000,55000 --stream-responses \
  -- --stream-responses
```

車種選択は、練習サーバーが返す `Procon37-Select-Started-At-Ms`・`Procon37-Select-Deadline-Ms` があればその実際の開始・締切を使用し、問題の取得遅延で提出時刻をずらしません。これらの情報がない公式サーバーでは開始時刻を正確に取得できないため、問題を最初に取得した時刻を開始の代わりにします。使用した時刻と情報源は `metadata.json` に保存します。各日は `endsAt * 1000 - daySeconds[day] * 1000` を開始時刻にし、状態取得の遅延では時刻をずらしません。`endsAt` の秒未満は切り捨てられているため、日別の提出は実際の開始から最大1秒早い見積もりになります。探索時間は最終提出時刻までの残り時間から通信・シリアライズの余裕500msを引いて渡します。練習の時間短縮で最終指定時刻が締切以降になる場合は、全チーム共通で実際の締切500ms前へ最終提出を移します。その安全な最終時刻より前の途中提出は保持し、同時刻を重複させません。たとえば10秒制限では固定側9.5秒、分散側5秒・9.5秒です。500ms以下の極短いフェーズでは開始時刻までに丸めます。途中参加で既に過ぎた提出時刻は飛ばしますが、全時刻を過ぎていて締切前なら、その時点の代替回答を即時提出します。選択が終了してから参加した場合は従来どおり選択を提出しません。

1フェーズにつきソルバへの要求は1回です。対応ソルバは `{"requestId":1,"answer":[[-100]],"final":false}` の形式で途中解を出力し、完了時に `final:true` を出します。`final` を省略した従来の応答は完了として扱います。bridgeは要求IDと解の妥当性を検証し、各提出時刻で最新の有効な解を確認します。同じ車種選択・同じ日の2回目以降は、`answer` のJSON値が直前に送信した内容と同じなら提出を省略します。応答の要求IDや付加メタデータ、得点はこの比較に含めません。A→Aは省略し、A→B→Aはそれぞれ送信します。比較対象は各フェーズでリセットするため、翌日の最初の回答は同じ内容でも提出します。未取得なら全車0の車種・全車待機の計画を提出します。不正な応答や別要求IDの応答で、直前の有効な解を消しません。

重複判定の比較対象は、受理・却下・通信結果不明にかかわらず、実際にHTTP送信処理を開始した最後の内容です。送信間隔の待機中などに締切となりHTTP送信を開始しなかった場合は、比較対象を更新しません。1回の提出内での通信再試行は従来どおり行います。省略したチェックポイントは詳細ログと `scheduledSubmissionSkipped` イベントに記録し、コンソールへ提出・受理の表示は追加しません。受理済みの解・採否も変更しません。

途中解が受理され、その後の提出が明示的に却下されても、受理済みの途中解を保持します。ストリームモードでは次の要求に `previousAnswer` を付け、実際に受理された解をソルバへ伝えます。ソルバは提出した途中解ごとの状態を保持し、その解へ復帰できる必要があります。代替回答は `previousAccepted:false`・`previousAnswer:null` です。通信切断で採否が不明な場合は従来どおり次の観測で確認し、複数の提出候補を区別できない場合は警告します。提出の記録は `.server/submissions/` のHTTPログと `scheduledSubmission` イベントで確認できます。

指定しなければ、bridgeの従来の「応答取得後すぐ1回提出」の動作を維持します。

### 公式の条件への対応

- リクエストは200ms以上の間隔を空けて送ります(公式の目安「秒間5リクエストほど」、問い合わせと回答その2 A42)。
- 提出の採否は公式仕様どおり、HTTP 200かつ `revision` が0以上なら受理とし、次の要求の `previousAccepted` に反映します。
- 回答が遅れて日が進んでいた場合は、間の日を飛ばして現在の日に回答します(飛ばした日は全車待機扱い)。
- 通信できなくなっても試合を諦めず、再接続を待ちます(ケーブルが抜けた場合など)。途絶と復旧はそれぞれ1回ずつ表示します。
  - 状態の取得は、つながるまで繰り返します。復旧したらその時点の日から回答を続けます。ただし現在のソルバは1日ずつ要求を受ける前提なので、状態を受け取れなかった日があると終了します(既知の制限)。
  - 提出は、その日(車種選択なら選択)の締切まで再送します。再提出は公式に認められています。行動計画は `endsAt`(秒未満を切り捨てた締切で、実際の締切として最も早い時刻)の100ms前で打ち切り、翌日の計画として受理されないようにします。
  - 中継(対戦サーバーの対戦窓口など)が上流と通信できずに返す HTTP 502〜504 も、通信エラーと同じく再送・再試行します。
  - 試合の終了予定(最後に受け取った `endsAt` と残りの日数から見積もる)を30秒過ぎてもつながらなければ、試合は終わったものとみなして終了します。
- 1回のリクエストは5秒で打ち切り、再接続を早く検知できるようにしています。

公式対戦サーバーのHTTP挙動は [server/docs/behavior.md](../server/docs/behavior.md) を参照してください。

## ログの検証

模擬HTTPサーバーとJSON Linesソルバを使い、英語出力、再送と復旧、提出受理・却下・未提出、選択の代替回答、認証拒否、マップ・道路状態・提出内容の保存、保存失敗時の提出継続を検証できます。実際の対戦サーバーやチームトークンは不要です。

```sh
cargo build -p server-bridge
python3 tester/server-bridge/tests/check_bridge_logs.py target/debug/server-bridge
```

途中提出・55秒相当の時刻指定は、ローカル模擬HTTPとJSONLソルバで検証できます。

```sh
python3 tester/server-bridge/tests/check_scheduled_submissions.py target/debug/server-bridge
```
