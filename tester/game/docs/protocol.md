# 通信と対戦ルール

基本は [JSON Lines v1](../../solo/docs/protocol.md)。標準入力で1行の要求を受け取り、標準出力に1行のJSON回答を出してflushする。診断ログはstderrへ出す。1試合につき各プレイヤーのプロセスを1つずつ維持する。

`select` では `problem.players = 5`。対象は0、相手は1〜4。全員に同じ問題と初期位置を渡す。車種選択回答の形式は単独テスタと同じ。

`plan` では以下を渡す。

| 値 | 内容 |
| --- | --- |
| `state.agents` | 受け手自身のチームの車両状態 |
| `state.others` | 他の4チームの `{ "id": プレイヤー番号, "agents": 車両状態配列 }` |
| `state.traffics` | 全員共通の当日の道路状態 |
| `state.day` / `endsAt` | 日付と回答期限 |
| `previousAccepted` | 自分の直前の回答が受理されたか |
| `steps` / `timeLimitMs` | 当日のステップ数・回答制限 |

他チームの在庫・訪問履歴・得点を通信に追加しない。各チームが自身の履歴を保持する。自分の番号は `others` に含まれない番号で判別できる。

5人に要求を並行送信し、全員の回答が揃うか各期限を迎えてからその日を進める。回答時刻の早いチームが先に商品を獲得する仕組みではない。

## 在庫と交通

在庫・燃料・獲得系列・訪問履歴はチームごとに独立する。全員が同じ初期位置でも、他チームによる在庫消費や補給は起きない。補給車は自チームの巡回車だけを補給する。移動と得点処理は共通エンジンを使用する。

道路状態は前日と前々日の5チームの滞在数を足し、5で割った値で閾値判定する。2で割る日数平均ではない。実装は合計と `閾値 × 5` を整数比較する。1日目は通常道路。

対象ソルバが内部でシミュレーションする場合も、当日は受信した `state.traffics` を使う。自チームだけから予測した道路状態との一致を要求してはいけない。ルートの `main.rs` は他チームを含む観測を受け取ると、共通エンジンの `set_observed_traffic` で道路状態を設定する。これにより、探索・提出前の検証・次の要求での前日再計算に同じ道路状態を使う。

## エラー・順位

不正な車種選択は該当チームを全巡回車にする。不正計画は一切状態を変更せず、そのチームだけ全車待機に置き換える。TLE・異常終了・起動失敗も該当チームの代替動作だけを適用し、他の4人は継続する。時間切れ後も次の日の要求を送り、要求IDが古い回答は読み捨てる。遅れて届いた出力を別の日へ流用しない。

順位は種類数、日別種類数、玉数の辞書順の降順。自分より高得点の人数+1を順位とし、同点なら `1, 1, 3, ...` のように同順位とする。回答時間・プレイヤー番号は順位を決めない。回答時間の集計は単独テスタと同じく採用した日の計画だけで、車種選択は別に保存する。
