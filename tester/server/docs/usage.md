# 操作と実行設定

## CUI

リポジトリルートから `cargo run --release -p server --` に続けて指定する。

```sh
run 12 --players 2 --label '改善版 vs 基準版'
run --seed 10 --format final --players 3 --label '決勝形式の再現'
generate --seed 10 --format final --players 3 --output /tmp/problem.json
serve --port 8082
compare RUN_ID_A RUN_ID_B --baseline RUN_ID_A
compare RUN_ID_A RUN_ID_B --format final --json
```

| オプション | 内容 |
| --- | --- |
| `--players N` | チーム数（1〜16、既定1） |
| `--label NAME` | 履歴に表示する実行名 |
| `--seed SEED` / 件数 | 単一seed、またはseed 0からの件数（1〜10000、既定12）。排他 |
| `--format FORMAT` | `first` / `semifinal` / `final` / `auto`（既定auto: seed % 3） |
| `--time-limit-ms N` | 車種選択と各日の制限時間を上書き。各日の回答時間は問題の形式に合わせて秒単位に切り上げる |
| `--server-program FILE` | 公式簡易サーバーの実行ファイル（既定 `tester/server/procon-server`） |
| `--match-port PORT` | 対戦窓口のポート（既定11451） |
| `--port PORT` | GUIのポート（既定8082、`serve` のみ） |
| `--output-dir DIR` | 履歴の保存先（既定 `.server/runs`） |
| `--config FILE` | 下記の実行設定JSON |

`run` は対戦窓口を開き、seedごとに公式簡易サーバーを起動して試合を公開する（`/setting` が問題を返し始める）。各ソルバPCの `run.sh` が参加していない場合も試合は時間どおりに進み、そのチームは全車待機・TLEとして記録される。Ctrl+Cで中断すると完了した試合を保存し、公式簡易サーバーを終了する。

対戦窓口のポートは1つのプロセスだけが使える。GUI（`serve`）の起動中に同じポートで `run` を実行すると、開始前にエラーで終了する。GUIは窓口を開けなくても起動し、履歴の閲覧だけができる（対戦の開始は断る）。

終了時に単独・対戦テスタと同じスコア合計・判定件数と、チーム別の平均順位・スコア合計を表示する。AC以外の試合が含まれると終了コードは1になる。

## 実行設定

GUIの「新しく実行」と同じ内容をJSONで `--config` に渡せる。GUIサーバーの `/api/config` は既定値を返す。

| フィールド | 内容 |
| --- | --- |
| `count` / `seed` | seed 0からの件数、または単一seed（文字列）。どちらか一方 |
| `format` | `"first"` / `"semifinal"` / `"final"`。`null` で自動 |
| `label` | 実行名（80文字以内） |
| `players` | チーム数（1〜16） |
| `teamNames` | チームの表示名の配列。空欄・省略は「チームN」 |
| `timeLimitMs` | 制限時間の上書き（ms）。`null` で公式条件 |
| `serverProgram` | 公式簡易サーバーの実行ファイル |

## GUI

画面構成・操作は [対戦テスタのGUI](../../game/docs/usage.md#gui) と同じ。違いは次のとおり。

- 「新しく実行」ではチーム数・チーム名・seed・形式・制限時間を指定する。ビルドやソルバの設定は各ソルバPCで行う。
- サイドバーに対戦窓口のURLを表示する。ソルバPCの `run.sh` の既定値（`http://192.168.0.81:11451`）と異なる場合は、`SERVER` としてこのURLを指定する。
- 「対戦順位」はチーム別の平均順位（全員ACの試合のみ）と順位分布、「スコア合計」はチーム別の合計を表示する。
- 結果一覧はチームごとに「順位 · 種類数 · 日別種類 · 玉数」を並べる。AC以外のチームには判定を添え、その試合の順位は「参考」になる。
- 「ヒートマップ」で各セルの巡回車・補給車の延べ滞在ステップ数を合算し、セル内の数字を表示せず対数スケールの色の濃淡で示す。通常盤面の道路状況は外枠の色で表示し、ヒートマップには枠線を表示しない。合計／車種別、当日／全日、選択チーム／全チームを切り替えられる。詳しい集計方法は[単独テスタの画面説明](../../solo/docs/gui.md#滞在時間のヒートマップ)を参照。
- リプレイはチームのカードまたは選択欄で詳細対象を切り替え、他チームの車両と経路を重ねて表示できる。全巡回車・補給車の当日全体の経路を参照ページと同じ点線で表示し、日付が変わると更新する。
- 「ログ」には選択チームの提出記録（問題の取得・車種選択・各日の提出時刻と採否・回答時間）と、公式簡易サーバーのログを表示する。
- 「履歴を比較」はチーム0の得点で勝敗・合計を比べる。チーム数や制限時間が異なる実行は問題相違として集計から外れる。
- 実行中は「中断」で公式簡易サーバーを止め、完了済みの試合だけを残す。
- ZIPの入出力はない。履歴はサーバーPCの `.server/runs/` に集まる。

## 結果の再現

公式簡易サーバーは最終結果を返さないため、対戦窓口の記録から共通エンジンで再現する。

- 車種選択・各日の計画は、最後に受理された提出を使う。受理は公式仕様どおりHTTP 200かつ `revision` が0以上。計画は並行提出で応答の順が前後しても、`revision` が最大の受理を最後の受理とする。
- 行動計画の提出は、遅らせずにすぐ公式簡易サーバーへ中継し、提出の直後に現在の日を問い合わせて記録先を決める（日の境界をまたいだ提出を正しい日に割り当てるため）。中継の前に観測していた状態の日と締切（`endsAt`、秒未満切り捨て）、各日の秒数から求めた各日の締切、提出の送受信時刻、直後の日とで処理した日を絞り込む。締切の1秒の幅で処理されて判断できない提出は、ソルバが回答していた日に記録し、「ログ」に推定と表示する（公式APIは提出を適用した日を返さないため）。その提出（受理・採否不明とも）がある日は、採用した計画としてその日に適用されたと翌日の状態で確かめられたときだけ確定し、確かめられなければ、翌日に適用されたかもしれないのでその日と翌日を `unconfirmed_plan` とする。最終日の締切をまたいで試合が終わった場合は最終日に割り当てる。
- 公式簡易サーバーの応答を受け取れなかった提出は「採否不明」として記録する。再現時は、各日の状態で観測した自チームの車と照らし合わせ、採用中の計画（または全車待機）で翌日の車を説明できないときだけ、説明できる採否不明の計画を受理として扱う。1チームの試合では、翌日に観測した道路状態も比べる（自チームの滞在だけで決まるので、同じ位置・燃料に戻る計画も見分けられる）。車種選択は観測できた最も早い日の状態の車種と照合する（車種は試合を通して変わらない）。採用した車種と違う内容の採否不明の車種選択が最後の受理より後に残り、観測でも確かめられなければ `unconfirmed_selection`（WA扱い）とする（車種選択はチームごとに1件ずつ中継するので、最後の受理より前の選択はその受理で上書きされている）。翌日の状態が無い日（最終日など）に採否不明の提出があれば、確かめられないので `unconfirmed_plan`（公式の結果と異なる可能性、WA扱い）として記録する。ただし採否不明の提出がどれも採用する計画（受理が確かな計画、無ければ全車待機）と同じ内容なら、どれが実行されても結果は同じなので確定する（応答を失った提出の再送が受理された場合など）。
- 再現の道路状態は、各チームの状態で観測した値（公式簡易サーバーが全チームの滞在から求めた値）があればそれを使い、無ければ再現した滞在から求める。確かめられない日の後で道路状態を観測できなかった日も `unconfirmed_plan` とする（確かめられない計画の滞在が以降の道路状態に影響しうるため）。同じチームの以降の日もすべて `unconfirmed_plan` とする（獲得した系列・玉数は状態に含まれず観測できないので、後の日に観測した車が再現と一致しても公式と同じ状態に戻ったとは言えないため）。
- 受理された計画が無い日は全車待機とし、提出が無ければ `timeout`（TLE）、すべて却下なら `invalid_plan`（WA）として記録する。車種選択も同様に `timeout` / `invalid_selection` とする。
- 公式簡易サーバーが受理した計画を共通エンジンが不正と判定した場合は、全車待機に置き換えて警告（WA）を残す。
- 交通量は全チームの滞在数を合算して判定する（対戦テスタと同じ）。
- 回答時間は、そのチームが当日の状態を初めて取得してから、採用された計画を提出するまでの時間。

## 保存形式

`.server/runs/<実行ID>/` に保存する。

| ファイル | 内容 |
| --- | --- |
| `run.json` | 実行全体。単独・対戦テスタの `run.json` schema 3 と同じ形で、`config` だけが上記の実行設定。`cases[].players` にチーム別の順位・得点・判定、`cases[].score` はチーム0の得点 |
| `<seed>/problem.json` | 生成した問題（`players` はチーム数） |
| `<seed>/config.json` | 公式簡易サーバーへ渡した設定 |
| `<seed>/replay.json` | 対戦リプレイ schema 2（対戦テスタと同じ）。本体がチーム0、`opponents` がチーム1以降 |
| `<seed>/team-N.log` | チームNの提出記録 |
| `<seed>/server.log` | 公式簡易サーバーの出力 |

## 対戦窓口

ソルバPCが接続するHTTPの受け口。公式簡易サーバーと同じAPI（`/setting`・`/agent`・`/`）だけを中継し、トークンはクエリの `token` と `Procon-Token` ヘッダのどちらでも受け付ける。本番の競技サーバーとの対応は [README](../README.md#本番との互換性) を参照する。

- 試合が無いときは、各APIが終了済みの試合と同じ `403 match has ended` を返す（中断後に待ち続けるソルバを止めるため）。
- 制限時間を短縮しているときだけ、`/setting` の応答に `Procon37-Select-Remaining-Ms` ヘッダ（車種選択の締切までの残り時間、ms）を添える。
- 進行中の試合への応答には `Procon37-Match-Id` ヘッダ（試合ID）を添える。試合を続けて開くので、server-bridge が同じ問題の前後の試合を取り違えないようにするため。

## 非公式練習場の取り込みケース

生成器v24は、取り込みを有効にすると `seed % 4 == 3` に非公式練習場の盤面を挿入する。各サイズ5枚を用意し、既存の #937・#941・#916 を先頭に、追加分はサイズ別に固定シャッフルしている。自動形式のseed 0〜59では15枚を各1回使用し、0〜29では7枚を含む。取り込み盤面の選択は60 seed周期。形式指定時はそのサイズの盤面を `floor(seed / 12) % 5` で選ぶため、同じ12 seed区間内では繰り返す。出典・使用順・参加人数の違いは [取り込みケース](../../../common/fixtures/arena/README.md) を参照。

### 取り込みの切り替え

既定は「含める」。CUIでは `--arena-maps` で有効、`--no-arena-maps` で無効にする。`run`・`generate`・`serve` で使え、`--config` の `"arenaMaps": true` / `false` よりコマンドライン指定が優先される。無効にすると取り込み対象のseedにも通常の生成マップを使う。公式サンプル3件は引き続き利用する。

GUIでは「新しく実行」と「問題を生成」の「非公式練習場のマップを含める（4ケースに1ケース）」で切り替える。`serve --no-arena-maps` は初期値をオフにする。設定は履歴に保存し、「この設定で再実行」へ引き継ぐ。保存済みの問題・リプレイは変更しない。

```sh
# 通常の生成マップで問題を確認
cargo run --release -p server -- generate --seed 3 --no-arena-maps --output /tmp/problem.json

# 練習場を含めるGUI（既定）
cargo run --release -p server -- serve --arena-maps
```

比較する実行は取り込み設定も揃える。設定が異なる場合、同じseedでも問題が変わるケースは比較対象から除外される。
